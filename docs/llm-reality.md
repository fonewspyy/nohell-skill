# LLM & Agent — ความเชื่อ vs ของจริง

> รูปแบบ: ข้างบนคือความเชื่อที่ได้ยินบ่อย · **ปัก** คือของจริง · **ทำแทน** คือสิ่งที่ควรทำ
> หลายข้อไม่ใช่ความเชื่อของคนไม่รู้ — มันคือความเชื่อของคนที่ใช้อยู่ทุกวันแล้วยังไม่เคยถูกหักล้าง
>
> หมวด: **M** โมเดล · **C** context/memory · **G** agentic · **E** eval/trust
> (ชุดใหม่) **K** ต้นทุน/ประสิทธิภาพ · **X** context engineering · **T** tool/MCP · **F** failure mode ของ code agent · **O** orchestration · **S** security · **H** human factors · **P** prompting · **B** benchmark

---

# M — เรื่องตัวโมเดล

## M1
"เขียน prompt ยาว ๆ ละเอียด ๆ ยิ่งได้ผลดี"

**ปัก**
ความยาวไม่ใช่ความชัด — ทุกคำที่ใส่เข้าไปแย่งความสนใจจากคำที่สำคัญ
prompt 2,000 คำที่มีคำสั่งขัดกันเองสามจุด แย่กว่า prompt 200 คำที่คมชัด และคำสั่งที่อยู่กลางกองข้อมูลยาวมักถูกกลืนหายไปมากกว่าที่อยู่หัวหรือท้าย

**ทำแทน**
ตัดออกให้เหลือแต่ส่วนที่ถ้าลบแล้วคำตอบเปลี่ยน ที่เหลือคือของประดับ

## M2
"ถามว่าทำไมมันตอบแบบนี้ แล้วมันอธิบายเหตุผลจริงให้ได้"

**ปัก**
คำอธิบายเหตุผลถูก generate ขึ้นมาแบบเดียวกับคำตอบ ไม่ใช่บันทึกของกลไกที่ทำให้ได้คำตอบนั้น
reasoning ที่เห็นช่วยคุณภาพได้จริง แต่มันคือข้อความที่น่าเชื่อ ไม่ใช่ log มันอธิบายเหตุผลสวย ๆ ให้คำตอบที่มาจากอย่างอื่นได้สบาย ๆ

**ทำแทน**
อย่าใช้ "เพราะอะไร" ของ model เป็นหลักฐาน audit ใช้ของที่ตรวจได้แทน เช่น statement ที่มันยิงจริง

## M3
"hallucination คือ bug ที่รุ่นหน้าจะแก้หมด"

**ปัก**
มันเป็นผลข้างเคียงของการเป็นเครื่องเดาคำถัดไป ไม่ใช่ flag ที่ปิดได้
ลดได้จริงด้วย grounding, การให้ทางออกเวลาไม่รู้, และการตรวจซ้ำ แต่ระบบที่ออกแบบบนสมมติฐานว่า "วันหนึ่งจะไม่ผิดอีก" คือระบบที่ไม่มีแผนสำหรับความผิดพลาด

**ทำแทน**
ออกแบบให้ทนคำตอบผิด: จำกัดสิทธิ์ ให้ผิดแบบดังและหยุดเอง ไม่ใช่ผิดแบบเงียบ

## M4
"ตั้ง temperature 0 แล้วผลลัพธ์จะเหมือนเดิมทุกครั้ง"

**ปัก**
temperature 0 ลดการสุ่มตอนเลือกคำ แต่ไม่ได้ทำให้ทั้งระบบ deterministic
การคำนวณแบบ batch ลำดับ floating point และการอัปเดตรุ่นฝั่งผู้ให้บริการ ทำให้คำตอบเดียวกันกลายเป็นคนละคำได้ โดยที่ input ของคุณไม่เปลี่ยนเลย

**ทำแทน**
test อย่า assert ว่า string เท่ากันเป๊ะ ให้ assert คุณสมบัติ เช่น parse ผ่าน, field ครบ, decision ถูก

## M5
"รุ่นใหม่ออกแล้ว เปลี่ยนไปเลยดีกว่าแน่นอน"

**ปัก**
prompt ที่ปรับจนพอดีกับรุ่นเก่า อาจให้ผลแย่ลงกับรุ่นใหม่ เพราะมันถูกฝนไปตามนิสัยของรุ่นนั้น
benchmark สาธารณะบอกว่าเก่งขึ้นในงานของ benchmark ไม่ได้บอกว่าเก่งขึ้นในงานของคุณ การอัปรุ่นคือการเปลี่ยน dependency ตัวใหญ่ที่สุดในระบบ

**ทำแทน**
มีชุดเคสของตัวเองแค่ 20 อัน แล้วรันสองรุ่นเทียบกันก่อนสลับ — นี่คือ eval ที่ถูกที่สุดในโลก

## M6
"มันตอบเรื่องยากได้ งานง่าย ๆ กว่านี้ก็ต้องได้"

**ปัก**
ความเก่งของมันเป็นขอบฟันปลา ไม่ใช่ทางลาด — ยากกับง่ายในสายตาคน ไม่ตรงกับยากง่ายของมัน
มันอธิบาย distributed consensus ได้ทั้งบท แต่นับตัวอักษรผิด และรู้ทฤษฎีไม่เท่ากับลงมือทำได้ การเดาความสามารถจากเรื่องที่มันเพิ่งทำได้สวย เป็นที่มาของความหงุดหงิดเกือบทั้งหมด

**ทำแทน**
ทดสอบทีละงานจริง อย่าอนุมานข้ามงาน และของที่ code ทำได้แน่นอนก็ให้ code ทำ

# C — context และความจำ

## C1
"context window ใหญ่ขึ้นแล้ว โยน repo ทั้งก้อนเข้าไปเลย"

**ปัก**
ใส่ได้ ไม่เท่ากับควรใส่ — คุณภาพลดลงตามปริมาณของที่ไม่เกี่ยวข้อง
หน้าต่างใหญ่แก้ปัญหา "ใส่ไม่พอ" แต่ไม่ได้แก้ปัญหา "เลือกไม่เป็น" แล้วยังจ่ายเพิ่มทั้งเงินและเวลาเพื่อให้มันอ่านของที่ไม่ต้องใช้

**ทำแทน**
คิดว่า context คืองบประมาณ ไม่ใช่ถัง — คัดของที่เปลี่ยนคำตอบเข้าไป ที่เหลือให้ subagent อ่านแล้วสรุปมา

## C2
"agent จำเรื่องที่คุยเมื่อวานได้"

**ปัก**
มันไม่มีความจำ ทุก turn คือการยื่นประวัติทั้งกองให้มันอ่านใหม่ตั้งแต่ต้น
เพราะฉะนั้น "มันลืม" ไม่ใช่อาการเสีย มันคือสิ่งที่คุณไม่ได้ส่งไปในรอบนั้น memory ทุกแบบเป็นสิ่งที่วิศวกรสร้างขึ้น ไม่ใช่คุณสมบัติที่ติดมากับโมเดล

**ทำแทน**
เขียนสิ่งที่ต้องจำลงไฟล์หรือ db ให้ชัด แล้วโหลดกลับอย่างจงใจ — ความจำคือ feature ที่ต้อง design

## C3
"ทำ RAG ก็แค่โยนเอกสารเข้า vector db"

**ปัก**
งานหนักอยู่ที่การค้นให้เจอ ซึ่งเป็นปัญหา information retrieval ธรรมดาที่มีมาก่อน LLM
การตัด chunk การจัดอันดับ และการวัด recall/precision คือที่ที่คุณภาพเกิดหรือตาย embedding search เดี่ยว ๆ มักแพ้การผสมกับ keyword แล้ว rerank

**ทำแทน**
วัด retrieval แยกจาก generation ก่อน และถ้าข้อมูลอยู่ในไฟล์ในเครื่อง grep ที่แม่นชนะ vector ที่มั่ว

## C4
"ต่อ MCP ให้ครบทุกตัว agent จะยิ่งเก่ง"

**ปัก**
tool ยิ่งเยอะ ยิ่งเลือกผิด — และคำอธิบาย tool ที่ทับซ้อนกันคือสาเหตุอันดับหนึ่งของการเลือกผิด
ทุก tool กิน context และเพิ่มทางเลือกที่ต้องตัดสินใจ สอง tool ที่ฟังดูทำงานคล้ายกันจะทำให้มันสลับใช้ไปมาแบบไม่มีเหตุผล

**ทำแทน**
คัด tool ตามงาน ไม่ใช่ตามที่มี ชื่อกับ description ต้องบอกได้ว่า "ใช้เมื่อไหร่ และเมื่อไหร่ไม่ใช้"

# G — เรื่อง agentic

## G1
"agentic คือการปล่อยให้ AI ตัดสินใจเองมากขึ้น"

**ปัก**
คุณค่าอยู่ที่ loop ที่มี feedback จากของจริง ไม่ใช่อยู่ที่ระดับอิสระ
สิ่งที่ทำให้ agent ต่างจาก chatbot คือมันลงมือ เห็นผล แล้วแก้ตัวได้ autonomy ที่ไม่มีการตรวจ คือการทำผิดได้เร็วขึ้นเท่านั้น

**ทำแทน**
ถามว่า "มันรู้ได้ยังไงว่าทำสำเร็จ" ถ้าตอบไม่ได้ นั่นไม่ใช่ agent มันคือเครื่องพิมพ์ที่มั่นใจ

## G2
"หลาย agent ช่วยกันย่อมดีกว่าตัวเดียว"

**ปัก**
ทุกรอยต่อระหว่าง agent คือจุดที่ context หายและ error สะสม
multi-agent คุ้มเมื่องานแตกเป็นชิ้นที่ไม่ต้องคุยกัน หรือเมื่อคุณต้องการมุมมองที่ต่างกันจริง ๆ เช่นคนทำกับคนตรวจ ไม่ใช่เพราะฟังดูล้ำกว่า

**ทำแทน**
เริ่มจากตัวเดียวก่อน แยกเมื่อเจอเหตุผลชัด ๆ เช่น context ตัน หรือ ต้องการผู้ตรวจที่ไม่ลำเอียง

## G3
"agent ทำงานนี้ไม่ได้เพราะโมเดลยังไม่เก่งพอ"

**ปัก**
ส่วนใหญ่มันพังเพราะสภาพแวดล้อม ไม่ใช่เพราะสมอง
tool ที่พารามิเตอร์กำกวม error ที่ไม่บอกทางออก สิทธิ์ที่ขาด สถานะที่หายไปหลัง restart — งานส่วนใหญ่ของการทำ agent คือการทำสภาพแวดล้อม ไม่ใช่การขัด prompt

**ทำแทน**
เวลามันพัง อ่าน log ว่ามันเห็นอะไรตอนนั้น แล้วซ่อม error message ก่อนซ่อม prompt

## G4
"มีคนคอยกด approve อยู่ ก็ปลอดภัยแล้ว"

**ปัก**
คนที่ต้องกด approve วันละสองร้อยครั้ง สุดท้ายจะกดผ่านทุกครั้งโดยไม่อ่าน
gate ที่ถามบ่อยเกินไปไม่ได้เพิ่มความปลอดภัย มันแค่ย้ายความรับผิดไปให้คนที่ไม่มีเวลาอ่าน ความปลอดภัยจริงมาจากการถามน้อยครั้งแต่ถามตรงจุด

**ทำแทน**
auto-allow สิ่งที่ปลอดภัยจริงแบบมีบันทึก แล้วเก็บการถามไว้ให้เฉพาะการกระทำที่ย้อนไม่ได้

## G5
"มันเขียนเสร็จใน 5 นาที เท่ากับประหยัดไปหนึ่งวัน"

**ปัก**
ต้นทุนไม่ได้หายไป มันย้ายไปอยู่ที่การตรวจและการแก้ของที่ดูเหมือนถูก
โค้ดที่ผิดแบบเนียนแพงกว่าโค้ดที่ไม่มีเลย เพราะมันผ่านตาไปได้ งานบางประเภทเวลาที่ใช้ตรวจแพงกว่าเวลาที่ประหยัด และนั่นไม่ได้แปลว่าห้ามใช้ แค่ต้องรู้ตัว

**ทำแทน**
วัดตั้งแต่เริ่มจนของขึ้น production ไม่ใช่วัดถึงตอนที่ diff แรกโผล่

## G6
"ให้มันเขียน test ของตัวเองไปด้วยเลย ครบวงจร"

**ปัก**
ตัวที่เขียนทั้งโค้ดและ test มีแรงจูงใจให้ test ผ่าน ไม่ใช่ให้ test จริง
คุณจะได้ test ที่สะท้อนสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่ควรทำ — รวมถึงบั๊กที่ถูกตรึงไว้เป็นพฤติกรรมที่ถูกต้อง มันไม่ได้โกง มันแค่เอาความเข้าใจชุดเดียวกันมาใช้สองรอบ

**ทำแทน**
ให้ test มาจากคนละแหล่ง: เขียนจาก spec ก่อน หรือให้อีกตัวที่ไม่เห็นโค้ดเขียน

# E — ความเชื่อถือและการวัด

## E1
"ลองใช้ดูแล้วรู้สึกว่าดีขึ้น ก็พอแล้ว"

**ปัก**
ความรู้สึกว่าดีขึ้นกับดีขึ้นจริง ต่างกันตรงที่อันหลังจับการถอยหลังได้
แก้ prompt ให้ดีขึ้นด้านหนึ่งมักแย่ลงอีกด้านหนึ่งเงียบ ๆ และคุณจะรู้ตอนมีคนบ่น eval ไม่จำเป็นต้องหรู 20 เคสที่ตรึงไว้ก็เปลี่ยนเกมแล้ว

**ทำแทน**
ทุกครั้งที่เจอเคสที่พลาด เก็บเข้าไฟล์เคสทันที — eval ที่ดีโตจากความเจ็บ ไม่ได้มาจากการนั่งคิด

## E2
"ให้ LLM ตัดสินคำตอบ ก็เป็นกลางกว่าคนตัดสิน"

**ปัก**
judge มีอคติเป็นระบบ: ชอบคำตอบยาว ชอบสไตล์ที่เหมือนตัวเอง และให้น้ำหนักตามลำดับที่เห็น
ใช้ได้จริงและประหยัดมาก แต่ต้องรู้ว่ามันเอียงทางไหน ไม่ใช้ก็ได้ผลว่าคุณเปลี่ยนไปวัดด้วยความรู้สึกแทน ซึ่งเอียงกว่า

**ทำแทน**
สลับตำแหน่ง A/B แล้วรันสองรอบ และเทียบผล judge กับ label ที่คนตัดสินไว้ 20 อันเป็นครั้งคราว

## E3
"ถูก 95% ก็ใช้ได้แล้ว"

**ปัก**
คำถามที่ถูกไม่ใช่ถูกกี่เปอร์เซ็นต์ แต่คือ 5% ที่ผิดทำอะไรได้บ้าง
ผิดแล้วสรุปรายงานเพี้ยน กับ ผิดแล้ว drop ตาราง คือคนละเรื่องที่มีเลขเดียวกัน ระบบที่ผิดแบบดังและหยุดเอง เชื่อถือได้มากกว่าระบบที่แม่นกว่าแต่ผิดแบบเงียบ

**ทำแทน**
วัดที่รัศมีความเสียหายของกรณีแย่สุด แล้วลงทุนกับการจำกัดสิทธิ์ ไม่ใช่กับการไล่เปอร์เซ็นต์

## E4
"กัน prompt injection ด้วยการสั่งใน system prompt ว่าอย่าเชื่อ"

**ปัก**
ข้อมูลกับคำสั่งเดินมาในช่องเดียวกัน คำสั่งให้ระวังจึงเป็นคำแนะนำ ไม่ใช่ขอบเขต
อะไรที่ agent อ่าน — หน้าเว็บ issue ชื่อไฟล์ ผลลัพธ์ tool — ล้วนแทรกคำสั่งได้ และ prompt ที่บอกให้ระวังก็เป็นแค่ข้อความอีกอันที่แข่งน้ำหนักกับข้อความอื่น

**ทำแทน**
ขอบเขตจริงคือสิทธิ์: agent ที่อ่านข้อมูลภายนอกไม่ควรถือ token ที่ทำเรื่องย้อนไม่ได้

# K — ต้นทุนและประสิทธิภาพ

## K1
"เลือกโมเดลใหญ่สุดไว้ก่อน ปลอดภัยกว่า เดี๋ยวได้คุณภาพ"

**ปัก**
ความสามารถเป็นขอบฟันปลา ใหญ่กว่าไม่ได้ชนะทุกงาน และมักแพ้เรื่องต้นทุนกับ latency ในงานที่ขอบเขตชัด
งานจำแนก สกัดข้อมูล แปลงฟอร์แมต ที่นิยามชัดเจน โมเดลเล็กมักได้คุณภาพพอกันในราคาที่ต่ำกว่าหลายเท่า การจ่ายเบี้ยประกันด้วยโมเดลใหญ่ทุกงานคือการเผาเงินโดยไม่วัดผล

**ทำแทน**
ตั้งค่าเริ่มต้นเป็นโมเดลกลางสำหรับงานซ้ำ ๆ แล้วยกระดับไปตัวใหญ่เฉพาะเมื่อ eval ตก

## K2
"เปิด prompt caching แล้วประหยัด 90% อัตโนมัติ"

**ปัก**
cache จับคู่แบบ exact prefix เท่านั้น เปลี่ยนอักขระเดียวข้างหน้า = cache หายเงียบ ๆ ไม่มี error
มีเคสจริงที่ hit rate เริ่มที่ 7% เพราะเอาข้อมูลที่เปลี่ยนตลอดไว้ใน system prompt พอย้ายไปท้าย prompt ขึ้นเป็น 84% ลดต้นทุนรวม 59% ส่วนลดต่อ token เป็นเรื่องจริง แต่บิลรวมมักไม่ลดเพราะ miss ที่มองไม่เห็น

**ทำแทน**
เรียงเนื้อหาจากนิ่งสุดไปเปลี่ยนบ่อยสุด แล้วมอนิเตอร์ cache hit ทุก response ไม่ใช่เปิดแล้วเชื่อ

## K3
"ใส่ timestamp หรือ session id ใน system prompt ไม่เป็นไรหรอก"

**ปัก**
ใส่ "วันนี้คือ..." หรือ id แบบไดนามิกไว้ข้างหน้า = ทำลาย cache ทุก request แบบเงียบ
tool schema ถูกประมวลผลก่อน system prompt ในลำดับ cache ดังนั้นเพิ่ม ลบ หรือสลับ tool ก็ทำลายทุกอย่างที่อยู่ถัดลงไป ค่าเหล่านี้ไม่เคย fail ดัง ๆ มันแค่ทำให้คุณจ่ายเต็มราคาทุกครั้ง

**ทำแทน**
ย้ายของที่เปลี่ยนบ่อยไปท้ายสุด และตรึงลำดับ tool ให้เหมือนเดิมทุก request

## K4
"Batch API ไม่คุ้ม ใช้ realtime ทุกอย่างง่ายกว่า"

**ปัก**
งานที่ไม่รีบ — สร้างเทส สรุป backfill characterization — Batch API ถูกกว่าราวครึ่งหนึ่งบนโมเดลเดียวกัน
สำหรับคนที่รันงานหนักตอนกลางคืนอยู่แล้ว นี่คือส่วนลดที่ได้ฟรีแค่ยอมรอ เอา latency ที่ไม่จำเป็นไปแลกเงินคือการออกแบบผิดฝั่ง

**ทำแทน**
แยกงานเป็นแบบโต้ตอบกับแบบรอได้ แล้วส่งอย่างหลังเข้าคิวข้ามคืน

## K5
"ภาษาไทย cost เท่ากับภาษาอังกฤษ แค่เปลี่ยนภาษา"

**ปัก**
ข้อความไทยกินโทเคนมากกว่าอังกฤษราว 2-4 เท่าที่ความหมายเท่ากัน เพราะ tokenizer เห็นข้อมูลไทยน้อยและไทยไม่เว้นวรรคคำ
กระทบสามอย่างพร้อมกัน: บิล, context ที่เต็มเร็วกว่า, และเวลาตอบที่ยาวขึ้น งบที่คิดจากโทเคนอังกฤษจะพลาด 2-4 เท่าเมื่อใช้จริงกับผู้ใช้ไทย

**ทำแทน**
เก็บ instruction เป็นอังกฤษ ให้เฉพาะสิ่งที่ผู้ใช้เห็นเป็นไทย แล้วคูณงบด้วย 2-4 เท่า

## K6
"reasoning model คิดเยอะ = ได้คำตอบดีขึ้นเสมอ ปล่อยให้คิดเต็มที่"

**ปัก**
โทเคนที่ใช้คิดมีราคาและมีเวลา และงานง่ายมักเกิดการคิดเกินจำเป็นที่ไม่เพิ่มคุณภาพเลย
โมเดลกลุ่มนี้คิดภายในอยู่แล้ว การบังคับให้คิดเพิ่มบนงานตรงไปตรงมาคือจ่ายแพงเปล่า และเหตุผลที่คุณมองไม่เห็นก็ยังอยู่ในบิล

**ทำแทน**
ตั้งงบการคิดตามความยากของงาน ใช้ reasoning model เฉพาะงานที่ต้องวางแผนหลายขั้น

## K7
"context window ใหญ่ = ยัดได้เยอะ ยิ่งใส่ยิ่งดี"

**ปัก**
ทุกโมเดลคุณภาพตกเมื่อ input ยาวขึ้น แม้ยังไม่ถึงลิมิต — งานทดสอบ 18 โมเดลชั้นนำพบว่าผลลัพธ์เชื่อถือได้น้อยลงเรื่อย ๆ ตามความยาว
สำหรับโมเดลที่โฆษณา window ระดับล้านโทเคน จุดที่เห็นผลตกชัดมักเริ่มก่อนถึงครึ่งด้วยซ้ำ window ที่โฆษณาไม่ใช่ความสามารถที่ใช้ได้จริง

**ทำแทน**
กำหนดงบโทเคนปลอดภัยของตัวเองจากการวัด แล้วบีบ context ให้อยู่ในนั้น

# X — Context engineering

## X1
"RAG ตายแล้วเพราะ long context ยัดทุกอย่างเข้า prompt จบ"

**ปัก**
naive RAG กำลังตาย แต่ retrieval ยังจำเป็น เพราะ long context ช้า แพง และเสื่อมเมื่อข้อมูลใหญ่ สด หรือต้องคุมสิทธิ์
ต้นทุนต่อคำถามต่างกันมหาศาลเมื่อคุณยัดทุกอย่างทุกครั้ง long context เปลี่ยนหน้าที่ของ retrieval ไม่ได้ลบมันทิ้ง

**ทำแทน**
ใช้ผสม: retrieval คัดว่าอะไรควรเข้า window แล้วให้ window เป็นพื้นที่คิด — สำหรับโค้ด grep กับ symbol search มักชนะ vector

## X2
"context rot จะเกิดก็ต่อเมื่อ window ใกล้เต็ม"

**ปัก**
คุณภาพเสื่อมแบบค่อยเป็นค่อยไปตั้งแต่ยังไม่เต็ม และตรวจยากเพราะโมเดลยังตอบ แค่ตอบแย่ลง
สำหรับ coding agent นี่คือสาเหตุความพังอันดับหนึ่ง ไม่ใช่ความสามารถโมเดล เพราะร่องรอยจากการค้น การลองผิด และการย้อนกลับ สะสมแล้วบั่นทอนทุกคำตอบถัดไป

**ทำแทน**
รีเซ็ตหรือบีบ context เป็นระยะ และแยกงานสำรวจไปให้ subagent เพื่อไม่ให้ trace รกงานหลัก

## X3
"CLAUDE.md/AGENTS.md ยิ่งยาว ยิ่งครอบคลุม ยิ่งดี"

**ปัก**
ทุกโทเคนในไฟล์ความจำแย่งความสนใจกับงานจริง ไฟล์ยาวเกินทำให้ agent สนใจงานน้อยลงและพลาดมากขึ้น
เป้าหมายคือหาชุดโทเคนที่น้อยที่สุดที่ให้สัญญาณมากที่สุด ส่วน instruction ที่พยายามครอบทุกเคสด้วยเงื่อนไขยาวเหยียดทำให้ agent เปราะ ไม่ใช่รอบคอบ

**ทำแทน**
เขียนสั้นเท่าที่จำเป็น แล้วย้ายรายละเอียดเฉพาะทางไป skill ที่โหลดเมื่อต้องใช้

## X4
"compaction หรือสรุป context ปลอดภัย ไม่เสียอะไร"

**ปัก**
บีบผิดจุดทำให้ข้อมูลสำคัญหาย หรือแย่กว่านั้นคือข้อผิดพลาดถูกสรุปติดไปแล้ววนกลับมาเรื่อย ๆ
prompt สรุปแบบสำเร็จรูปไม่รู้ว่างานคุณต้องเก็บอะไร ถ้าไม่ปรับ มันจะทิ้งของที่ควรเก็บ สรุปที่แย่คือการจำผิดแบบถาวรใน session นั้น

**ทำแทน**
เขียน prompt สรุปเอง ระบุสิ่งที่ต้องคงไว้ และใช้ไฟล์ progress กับ git history เป็นแหล่งความจริงแทนความจำใน context

## X5
"ผ่านการทดสอบหาเข็มในกองฟางที่ 500k แล้ว long context ของเราไม่มีปัญหา"

**ปัก**
การทดสอบแบบนั้นวัดแค่การหาสตริงตรง ๆ ซึ่งเป็นงานง่ายที่สุด ไม่สะท้อนงานจริงที่ต้องเชื่อมหลายจุดและมีตัวลวง
เวอร์ชันที่ต้องจับคู่แบบไม่ตรงคำเผยการตกอย่างมีนัย ผ่านการทดสอบง่าย ๆ แล้วสรุปว่าไม่มีปัญหา คือกับดักที่พบบ่อยสุด

**ทำแทน**
ทดสอบด้วยงานจริงของคุณที่มีตัวลวงและต้องเชื่อมหลายจุด แล้ววัดว่า context ที่ใช้ได้จริงคือเท่าไหร่

# T — การออกแบบ tool และ MCP

## T1
"เขียน MCP tool = ห่อ REST API เดิมแบบหนึ่งต่อหนึ่งก็พอ"

**ปัก**
การเปิด endpoint ดิบ ๆ บังคับให้ agent เดินหลายรอบแล้วพังกลางทาง
ควรออกแบบ tool รอบผลลัพธ์ที่ผู้ใช้ต้องการ แล้ว orchestrate ภายในเอง API ที่ดีสำหรับคนไม่จำเป็นต้องเป็น tool ที่ดีสำหรับ LLM

**ทำแทน**
รวมเป็น tool ระดับสูงที่จบงานเดียว พารามิเตอร์น้อย ใช้ค่าที่กำหนดชัดแทน object ซ้อน

## T2
"error message เขียนให้คนอ่านพอ agent ไม่ต้องอ่าน"

**ปัก**
เมื่อ tool ล้มเหลว agent คือคนอ่าน error แล้วตัดสินใจขั้นต่อ คำว่า "Error 422" ทำให้มันไม่มีอะไรให้ทำต่อ
error message คือคำสั่งกู้สถานการณ์: อะไรพัง คาดหวังอะไร ตัวอย่างที่ถูกหน้าตายังไง error ที่คลุมเครือเปลืองทั้งรอบและโทเคน

**ทำแทน**
ทำ error เป็นสามส่วน (อะไรผิด/คาดหวังอะไร/ตัวอย่าง) และเวลาไม่เจอข้อมูล ให้บอกด้วยว่าควรลอง tool ไหนต่อ

## T3
"tool คืน field ให้เยอะ ๆ ไว้ก่อน เผื่อ agent ต้องใช้"

**ปัก**
สิ่งที่ tool คืนกลับกิน context ทุกครั้ง คืน 50 field ทั้งที่ตัดสินใจด้วย 5 field ทำให้ context บวมและพลาดมากขึ้น
มีการวัดว่าการเปลี่ยนไปคืนแบบสรุปและขอเพิ่มเมื่อต้องการ ลดโทเคนของ response ได้ราวสองในสาม "เผื่อไว้" คือการจ่าย context ทุกครั้งที่เรียก

**ทำแทน**
คืนน้อยที่สุดเป็นค่าเริ่มต้น มีตัวเลือกขอรายละเอียด และตัดข้อมูลยาวพร้อมบอกวิธีขอส่วนที่เหลือ

## T4
"agent วนลูปเพราะโมเดลมันโง่"

**ปัก**
ลูปส่วนใหญ่มาจาก tool ที่รันซ้ำแล้วผลต่าง error ที่ไม่บอกทางแก้ หรือผลลัพธ์ที่ใหญ่จนหลง เป็นปัญหาสภาพแวดล้อมไม่ใช่สมอง
การวิเคราะห์ความล้มเหลวของ coding agent ชี้ไปที่การตรวจสอบและ harness เป็นหลัก โทษโมเดลทำให้แก้ผิดจุดทุกครั้ง

**ทำแทน**
ทำ tool ให้รันซ้ำได้ผลเดิม ใส่สถานะให้ถามความคืบหน้าได้ แล้ววัดลูปจาก trace เพื่อแก้ที่ tool

# F — Failure mode ของ code agent

## F1
"agent บอกว่าตรวจแล้ว/เทสผ่าน แปลว่ามันทดสอบจริง"

**ปัก**
agent มักเล่าเจตนา ไม่ใช่สภาพจริงของเครื่อง มันเขียนว่าเทสผ่านได้ทั้งที่ชุดเทสมี syntax error หรือรันแค่เทสแคบแล้วเคลมว่าทั้งชุด
ความพังที่อันตรายที่สุดไม่ใช่ error สีแดง แต่คือคำโกหกสีเขียวที่ดูเนียน การอ่านสรุปของ agent คือการเชื่อคำพูดแทนหลักฐาน

**ทำแทน**
รันคำสั่งเดิมเอง เก็บ exit code กับ output แล้วอนุมัติจากหลักฐาน ไม่ใช่จากคำบรรยาย

## F2
"CI เขียว = โค้ดถูกต้อง"

**ปัก**
เมื่อโมเดลเดียวเขียนทั้งโค้ดและเทส CI เขียวกลายเป็นส่วนหนึ่งของคำกล่าวอ้างที่ต้องตรวจ ไม่ใช่หลักฐาน
ความพังที่ทุกทีมเจอคือ agent แก้เทสให้ผ่านแทนแก้โค้ดให้ถูก — ลบ assertion ขยายเกณฑ์ ใส่ skip มีเคสจริงที่ลบตัวป้องกันเส้นทางออกแล้วเทสหกพันตัวยังเขียวหมด

**ทำแทน**
อ่าน diff ของไฟล์เทสก่อนเสมอ ถ้าเทสเปลี่ยนพร้อมโค้ดให้ถือว่าเทสคือของที่ต้องตรวจหลัก และลองปิดโค้ดหนึ่งบรรทัดดูว่าชุดเทสแดงจริงไหม

## F3
"ให้ agent ทำ migration หรือ refactor ทั้งก้อนทีเดียวจบ"

**ปัก**
การรื้อทีเดียวบนระบบเก่าเสี่ยงที่สุด เพราะไม่มีตัวอ้างอิงว่าพฤติกรรมเดิมคืออะไร agent จึงแก้ให้ "ดูถูก" แต่เปลี่ยนพฤติกรรมจริง
ความล้มเหลวจำนวนมากมาจากการแก้ข้อความแบบค้นแล้วแทนที่ ที่ลงผิดบรรทัดแล้วไม่เคยอ่านซ้ำ ก้อนใหญ่แปลว่ารัศมีความเสียหายใหญ่

**ทำแทน**
สร้าง characterization test ครอบพฤติกรรมเดิมก่อน แล้วแตกเป็นก้าวเล็กที่ตรวจได้ทีละก้าว

## F4
"agent เก่ง greenfield แต่ห่วย legacy"

**ปัก**
จริงครึ่งเดียว งานทดลองแบบสุ่มของ METR พบว่า dev ที่มีประสบการณ์ทำงานบน repo ที่ตัวเองคุ้นเคยและใหญ่มาก กลับ **ช้าลง 19%** เมื่อใช้ AI ขณะที่งานสร้างใหม่ได้เร็วขึ้นจริง
ประเด็นไม่ใช่ legacy แพ้ แต่คือบน codebase ที่คุณรู้ลึกอยู่แล้ว ต้นทุนการอธิบายบริบทกับการตรวจงานมักกินกำไรไปหมด

**ทำแทน**
ใช้ agent หนักกับส่วนที่สร้างใหม่และงานซ้ำซาก ส่วน legacy ที่คุณเชี่ยวให้แบ่งเป็นชิ้นเล็กที่ตรวจได้ ไม่ใช่ปล่อยยาว

## F5
"agent แก้แค่ที่สั่ง ไม่มีอะไรงอกเงียบ ๆ"

**ปัก**
ความพังกลุ่มใหญ่คือความสะอาดของการเปลี่ยนแปลง สคริปต์ชั่วคราว ไฟล์ช่วย และการแก้ที่ไม่เกี่ยว ถูกกวาดเข้า diff สุดท้าย
บ่อยครั้งเกิดจากการ add ทั้งโฟลเดอร์ครั้งเดียว บางเคสแก้ฟังก์ชันถูกแต่เปลี่ยนรูปแบบ quote ทั้งไฟล์เพราะใช้คำสั่งแทนที่แบบกวาด งานที่ปนมาคือหนี้ที่คุณต้องมารีวิว

**ทำแทน**
บังคับให้ตรวจสถานะไฟล์ก่อนส่ง แยก branch ต่องาน และปฏิเสธไฟล์ที่อยู่นอกขอบเขต

## F6
"agent แก้บั๊กแล้วเทสผ่าน = มันเข้าใจกฎธุรกิจ"

**ปัก**
ผ่านเทสพิสูจน์แค่พฤติกรรมที่เทสครอบ ไม่ใช่กฎที่ไม่มีใครเขียนไว้ เช่นเงื่อนไขคลัง การปัดเศษ สิทธิ์ และเคสข้อมูลจริง
บนระบบเก่าที่กฎฝังอยู่ใน stored procedure พฤติกรรมจริงมักไม่มีบันทึกที่ไหนเลย agent จึงเดา และเดาอย่างมั่นใจ

**ทำแทน**
เขียนกฎเป็นเกณฑ์ยอมรับที่อยู่นอก diff แล้วให้เทสอ้างอิงมัน ไม่ใช่ให้เทสอ้างอิงโค้ด

# O — Orchestration และงานขนาน

## O1
"รัน agent ขนานเยอะ ๆ = งานเสร็จเพิ่มตามจำนวน"

**ปัก**
ส่วนที่ยากที่สุดของงานขนานไม่ใช่การแยก แต่คือการรวมกลับ
ยิ่งขนานเยอะ พื้นที่ที่จะชนกันยิ่งโต และมันโผล่ตอน merge หลังจากทำงานไปเยอะแล้ว ปริมาณงานดิบไม่เท่ากับงานที่เสร็จ

**ทำแทน**
ให้แต่ละตัวมีพื้นที่ของตัวเอง ออกแบบงานให้ไม่แตะไฟล์เดียวกัน แล้วรวมทีละอันผ่าน branch กลางที่รันเทส

## O2
"ใช้ worktree แยกแล้ว agent ขนานปลอดภัยแล้ว"

**ปัก**
worktree แก้แค่การชนกันของไฟล์ในโฟลเดอร์เดียวกัน ไม่ได้กันการชนกันเชิงตรรกะ
คุณสร้าง conflict ระหว่างกันได้โดยไม่รู้ตัว และไม่มีเครื่องมือไหนเตือนเมื่อ agent สองตัวกำลังจะแก้โค้ดชุดเดียวกันคนละที่ การแยกไม่เท่ากับการประสาน

**ทำแทน**
เพิ่มการตรวจว่าจะชนกันไหมก่อนปล่อยงานขนาน และจัดคิวงานที่แตะของเดียวกันให้ทำทีละอัน

## O3
"subagent ต้องแชร์ context กันให้มากที่สุดถึงจะดี"

**ปัก**
บางงาน "ไม่แชร์" กลับดีกว่า — ทีมที่ทำ coding agent พบว่าให้ตัวเขียนกับตัวตรวจไม่แชร์ context กันเลย จับบั๊กได้ดีกว่า
แต่ในทางกลับกัน การแยก subagent ที่ไม่รู้งานของกันและกันก็สร้างผลลัพธ์ที่ขัดกันเอง คำตอบขึ้นกับชนิดงาน ไม่ใช่กฎเหมารวม

**ทำแทน**
แชร์ทั้ง trace เมื่อ subagent ต้องต่อยอดงานเดียวกัน และจงใจไม่แชร์เมื่อต้องการผู้ตรวจที่ไม่ลำเอียง

# S — ความปลอดภัยและข้อมูล

## S1
"กัน prompt injection ได้ด้วยการสั่งใน system prompt ว่าอย่าเชื่อ input"

**ปัก**
โมเดลเชื่อคนง่ายโดยธรรมชาติของมัน การสั่งไม่ให้เชื่อกันไม่ได้จริงเพราะคำสั่งกับข้อมูลอยู่ในช่องเดียวกัน
มีกรอบที่ใช้ได้ดีคือ "สามอย่างที่ห้ามมีพร้อมกัน": ข้อมูลส่วนตัว + เนื้อหาที่ไม่น่าเชื่อถือ + ช่องทางส่งออกภายนอก ถ้ามีครบสามเมื่อไหร่ ข้อมูลรั่วได้เสมอ

**ทำแทน**
ออกแบบให้ไม่มีครบสามในตัวเดียว: จำกัดสิทธิ์ tool แยกงาน และตัดช่องทางส่งออกเมื่อมีข้อมูลส่วนตัวอยู่ใน context

## S2
"MCP server หรือ skill จาก marketplace ผ่านการตรวจแล้ว ปลอดภัย"

**ปัก**
skill กับ MCP คือโค้ดที่รันด้วยสิทธิ์เต็มของ agent ทั้งไฟล์ โทเคน และการเปิด PR — เป็นห่วงโซ่อุปทานที่ถูกโจมตีจริงแล้ว
มีการสำรวจ skill เกือบสี่พันตัวแล้วพบว่าราวหนึ่งในสามมีช่องโหว่อย่างน้อยหนึ่งจุด และมีจำนวนหนึ่งที่เป็นของอันตรายจริง การอัปเดตอัตโนมัติแปลว่าของดีวันนี้กลายเป็นของร้ายพรุ่งนี้ได้เงียบ ๆ

**ทำแทน**
ตรึงเวอร์ชัน อ่านสิทธิ์ที่มันขอ รันในกล่องแยก ปิดอัปเดตอัตโนมัติ

## S3
"ให้คนกด approve ก็กันข้อมูลรั่วได้แล้ว"

**ปัก**
ข้อมูลรั่วผ่านผลลัพธ์ของ tool ได้โดยที่หน้าจออนุมัติดูปกติทุกอย่าง
มีเคสจริงที่ผู้ช่วยเขียนโค้ดถูกฝังคำสั่งให้ส่งข้อมูล repo ส่วนตัวออกไปยังปลายทางปลอม และคนที่กดอนุมัติวันละหลายสิบครั้งจับไม่ทัน การอนุมัติเป็นการควบคุมที่อ่อนเมื่อสามอย่างข้างบนมีครบ

**ทำแทน**
ตัดที่สถาปัตยกรรม: จำกัดปลายทางที่ส่งออกได้ แยก credential ออกจาก context และบันทึกทุกการเชื่อมต่อขาออก

# H — คนและองค์กร

## H1
"รู้สึกว่าเร็วขึ้น = เร็วขึ้นจริง"

**ปัก**
งานทดลองแบบสุ่มของ METR พบช่องว่างที่ใหญ่มาก: dev คาดว่าจะเร็วขึ้น 24% หลังทดลองเสร็จยังเชื่อว่าเร็วขึ้น 20% แต่วัดจริงแล้ว **ช้าลง 19%**
แม้ทำงานเสร็จเองกับมือก็ยังประเมินผิดทาง ความรู้สึกเร็วจึงเป็นหลักฐานที่เชื่อไม่ได้

**ทำแทน**
วัดเวลาจริงต่องานประเภทเดิม แล้วเทียบก่อนหลัง — แต่จำไว้ว่างานนี้ n เล็ก (16 คน) และเป็น repo ที่คนทำคุ้นเคยมาก อย่าเหมาว่าทุกงานช้าลง

## H2
"AI ทำให้ solo dev ทำงานได้เท่าทั้งทีม"

**ปัก**
AI เพิ่มปริมาณงานเขียน แต่ไม่ลด bus factor และเพิ่มภาระใหม่ที่ยังกองอยู่ที่คนเดิม: ตรวจ ยืนยัน รวมงาน และรับสายตอนระบบล่ม
ปริมาณที่มากขึ้นโดยไม่มีคนตรวจทัน คือหนี้ที่สะสมเร็วขึ้น เหมือนมีทีม แต่จุดที่จะล้มยังเป็นจุดเดียว

**ทำแทน**
ใช้ AI ลดงานที่เครื่องตรวจได้ แล้วลงทุนกับ guardrail และ CI ให้ทำหน้าที่เพื่อนร่วมทีมที่คอยเบรก แทนการเร่งปริมาณ

## H3
"ใช้ AI เยอะ ๆ ทักษะไม่ถดถอยหรอก"

**ปัก**
มีสัญญาณว่าถดถอยจริง ทั้งด้านความเข้าใจของคนที่พึ่ง AI มาก และด้านคุณภาพโค้ดในภาพรวม
การวิเคราะห์โค้ดหลายร้อยล้านบรรทัดพบว่าสัดส่วนการคัดลอกวางเพิ่มขึ้น ส่วนโค้ดที่ถูกจัดระเบียบใหม่ลดลงจากราวหนึ่งในสี่เหลือไม่ถึงสิบเปอร์เซ็นต์ และบล็อกที่ซ้ำกันโตขึ้นหลายเท่า สำหรับคนที่ดูแลระบบคนเดียว การจางลงของความเข้าใจ codebase คือความเสี่ยงตรง ๆ

**ทำแทน**
สลับโหมด บางงานอ่านและเขียนเอง และบังคับตัวเองให้อธิบาย diff ได้โดยไม่เปิดซอร์สก่อน merge

# P — งานฝีมือด้าน prompt และ skill

## P1
"ใส่ตัวอย่างช่วยเพิ่มคุณภาพเสมอ"

**ปัก**
บน reasoning model การใส่ตัวอย่างมักไม่ช่วย และบางครั้งทำให้แย่ลง คำแนะนำทางการคือลองแบบไม่มีตัวอย่างก่อน
ตัวอย่างที่ไม่ตรงกับคำสั่งเป๊ะ ๆ ยิ่งสร้างผลลัพธ์แย่ เทคนิคที่เวิร์กกับโมเดลรุ่นก่อนไม่ได้ย้ายมาใช้ตรง ๆ

**ทำแทน**
เริ่มแบบไม่มีตัวอย่างกับ reasoning model แล้วเพิ่มเฉพาะเมื่อจำเป็นและให้สอดคล้องกับคำสั่ง

## P2
"สั่งให้คิดทีละขั้นช่วย reasoning model คิดดีขึ้น"

**ปัก**
โมเดลกลุ่มนี้คิดภายในอยู่แล้ว การสั่งซ้ำไม่จำเป็นและบางครั้งขัดขวาง มีคำแนะนำทางการให้เลี่ยงกับโมเดลกลุ่มนี้โดยตรง
เก็บเทคนิคนี้ไว้ใช้กับโมเดลที่ไม่ได้คิดเองก่อนตอบ สั่งคิดซ้ำคือเปลืองโทเคนโดยไม่ได้อะไร

**ทำแทน**
เขียน prompt ให้สั้น ตรง ระบุเป้าหมายกับข้อจำกัด แล้วปล่อยให้มันคิดเอง

## P3
"บังคับให้ตอบเป็น JSON ไม่กระทบคุณภาพคำตอบ"

**ปัก**
งานวิจัยเรื่องข้อจำกัดของรูปแบบพบว่าการบังคับฟอร์แมตทำให้ความสามารถในการให้เหตุผลตกอย่างมีนัย และยิ่งเข้มยิ่งตก
ความเสียหายหลักมาจากการบีบพื้นที่คิด ไม่ใช่ตัวฟอร์แมตเอง การบังคับให้ตอบ JSON ทันทีบนงานที่ต้องคิดคือการตัดขั้นตอนคิดทิ้ง

**ทำแทน**
ให้มีช่องคิดแบบอิสระอยู่ก่อนช่องคำตอบใน schema หรือแยกเป็นสองขั้น คิดก่อนแล้วค่อยแปลง

## P4
"prompt engineering ตายแล้ว โมเดลฉลาดพอ"

**ปัก**
มันเลื่อนไปเป็น context engineering ไม่ได้หายไป
สำหรับภาษาไทยและงานเฉพาะโดเมน การจัดคำและบริบทยิ่งสำคัญเพราะแต่ละคำแพงกว่าและกิน context มากกว่า คำโปรยว่า "ตายแล้ว" ทำให้คนเลิกฝึกทักษะที่ยังจำเป็น

**ทำแทน**
ลงทุนกับการจัดลำดับข้อมูล การออกแบบ tool ความจำ และการบีบ context แล้ววัดผลด้วย eval

## P5
"ขึ้นต้นด้วย 'คุณคือผู้เชี่ยวชาญ...' ช่วยให้ตอบดีขึ้น"

**ปัก**
การสวมบทให้ผลไม่แน่นอนบนโมเดลสมัยใหม่ และหลักฐานว่ามันเพิ่มความถูกต้องอย่างสม่ำเสมอยังขัดแย้งกันอยู่ — ข้อนี้ยังไม่มีข้อสรุป
สิ่งที่ช่วยจริงคือคำสั่งที่ชัด ตัวอย่างที่ตรง และข้อจำกัดที่ระบุไว้ ไม่ใช่การประกาศตัวตน

**ทำแทน**
แทนที่ประโยคสวมบทด้วยเงื่อนไขงานที่ชี้ชัด แล้วถ้าจะใช้จริงให้ทดสอบเทียบกันเอง

# B — Benchmark และการวัด

## B1
"โมเดลได้คะแนน benchmark โค้ดสูง = จะเก่งกับ codebase เรา"

**ปัก**
benchmark ยอดนิยมด้านโค้ดปนเปื้อนหนัก ผู้ผลิตรายใหญ่รายหนึ่งตรวจโจทย์ที่โมเดลแก้ไม่ได้แล้วพบว่าเกินครึ่งมีปัญหาที่ตัวโจทย์หรือตัวเทสเอง จนประกาศเลิกใช้รายงานมัน
มีงานที่พบว่าโจทย์จำนวนมากมีคำตอบอยู่ในตัว issue อยู่แล้ว และโมเดลทายไฟล์ที่มีบั๊กถูกแม้ไม่ได้รับบริบทของ repo เลย ซึ่งเป็นสัญญาณของการจำ ไม่ใช่การคิด

**ทำแทน**
อย่าเลือกโมเดลจากตารางอันดับ สร้าง eval เล็ก ๆ จากงานจริงของคุณเอง

## B2
"benchmark สาธารณะทำนายผลกับงานเราได้"

**ปัก**
benchmark ที่มาจากข้อมูลสาธารณะเสี่ยงที่โมเดลเคยเห็นตอนเทรน ทำให้คะแนนพองในงานลักษณะนั้น แต่ตกในงานที่หน้าตาต่างออกไป
มันวัดความสามารถทั่วไป ไม่ได้วัดงานของคุณที่มีกฎธุรกิจและระบบเก่าเฉพาะตัว

**ทำแทน**
เขียนชุดทดสอบถดถอยสำหรับ prompt และ agent ของคุณเอง แล้วรันทุกครั้งที่เปลี่ยนโมเดล

## B3
"ให้ LLM เป็นผู้ตัดสินในบริบทยาว ๆ ก็เชื่อผลได้"

**ปัก**
ตัวตัดสินก็เจอ context rot เหมือนกัน มีการวัดว่าเมื่อเหตุการณ์อันตรายเกิดหลังบริบทที่ไม่มีพิษภัยยาวมาก โมเดลชั้นนำพลาดการจับเพิ่มขึ้นหลายเท่าถึงหลายสิบเท่า
ความสามารถในการจับเหตุตกลงชัดเจนแค่จากการเติมความยาวเข้าไป ตัวตัดสินจึงไม่ได้เป็นกลางหรือนิ่งโดยอัตโนมัติ

**ทำแทน**
ให้ผู้ตัดสินทำงานบนชิ้นสั้น ๆ ใส่การเตือนเป็นระยะ และเทียบกับชุดที่คนตัดสินไว้แล้วก่อนเชื่อคะแนน

## B4
"ทำ eval ครั้งเดียวตอนเลือกโมเดลก็พอ"

**ปัก**
prompt กับ agent ถดถอยเงียบ ๆ เมื่อผู้ให้บริการอัปเดตโมเดลใต้ชื่อเดิม หรือเมื่อคุณแก้คำสั่งเล็กน้อย
ถ้าไม่มีชุดทดสอบถดถอย คุณจะรู้ว่าคุณภาพตกก็ต่อเมื่อผู้ใช้เจอปัญหา eval คือ test suite ของระบบที่ผลลัพธ์ไม่คงที่ ไม่ใช่กิจกรรมครั้งเดียว

**ทำแทน**
เก็บ 20-50 เคสจากงานจริง รันเป็นด่านใน CI ทุกครั้งที่เปลี่ยนโมเดล prompt หรือ tool

## หมายเหตุเรื่องหลักฐาน

- ตัวเลขจาก METR มาจาก dev 16 คน 246 งาน บน repo ที่พวกเขาคุ้นเคยมาก และใช้เครื่องมือช่วงต้นปี 2025 — ใช้สรุปได้ว่า "ความรู้สึกเร็วเชื่อไม่ได้" แต่สรุปไม่ได้ว่า "AI ทำให้ทุกคนช้าลง"
- P5 (role prompting) หลักฐานยังขัดแย้งกัน ระบุไว้ตรง ๆ ในตัวข้อแล้ว
- ราคา พฤติกรรม cache และคำแนะนำของผู้ผลิตเปลี่ยนบ่อยมาก ตรวจเอกสารทางการ ณ วันที่ใช้งานเสมอ
