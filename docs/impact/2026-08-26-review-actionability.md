> เลนส์: agent จะทำอะไรกับกฎนี้ได้จริงไหม — ไม่ใช่กฎเขียนดีไหม
> วิธีตรวจ: อ่าน `HELL-CATALOG.md` เต็มบริบท (ไม่เชื่อคำอ้างในคอมมิต), จำลอง edge case จริงบนสำเนา repo,
> เทียบกับ `hell-rules.yaml` ที่มีอยู่เพื่อดูว่าอยู่ในระดับเดียวกับกฎเดิมหรือไม่

## สรุปเป็นตัวเลข

| คำถาม | ผลนับ |
|---|---|
| ข้อใหม่ 5 ข้อ — "กฎแทน" สั่งงานเป็นขั้นตอนได้ทันทีโดยไม่ต้องเขียนใหม่ | **2 / 5** (MEAS-11, SHIP-17) |
| ข้อใหม่ 5 ข้อ — ต้องเสนอถ้อยคำใหม่ให้สั่งงานได้ (สั่งงานได้แต่ต้องอ่านตีความก่อน) | **3 / 5** (TEST-17, SEC-21, CODE-27) — ร่างไว้ด้านล่างทุกข้อ |
| เขียนเป็น regex pattern ที่ใส่ `hell-rules.yaml` ได้ (ระดับ experimental เดียวกับกฎเดิม) | **2 / 5** (MEAS-11, CODE-27-เฉพาะ candidate-flagging) |
| ตรวจได้แค่ manual/คนอ่าน หรือ dataflow ที่ regex ทำไม่ได้จริง | **3 / 5** (TEST-17, SEC-21, SHIP-17 เชิงเนื้อหา แม้จะมี checklist ที่รันได้) |

(จุดที่สี่ยังเงียบอยู่ ในไฟล์คนละไฟล์กับสามจุดที่ commit message อ้าง) และกฎใหม่ 3/5 ข้อเขียนในโทน "อธิบายเคส"
มากกว่า "สั่งขั้นตอน" — ใช้ได้กับคนอ่านที่มีสามัญสำนึกด้านนี้อยู่แล้ว แต่ agent ที่ไม่มีบริบทเพิ่มจะทำตามลำดับขั้นไม่ได้
ตรงตามที่ D1 ในคอมมิตเขียนไว้ (ไม่ทับของเดิม) — ปัญหาไม่ใช่ความซ้ำซ้อน แต่คือ "รันได้จริงไหม"

## 1) TEST-17 — เทสที่ผ่านเพราะทั้งสองฝั่งพังเหมือนกัน (P1)

**กฎแทนเดิม:** "ตัวเทียบต้องไม่ให้ผล 'ผ่าน' เมื่อผลลัพธ์ทั้งสองฝั่งเป็นสัญญาณความล้มเหลว ... ก่อนเชื่อชุดเทส
ต้องเปิดผลลัพธ์ดูว่าเป็นข้อมูลจริง"

**ทำไมยังไม่ใช่ขั้นตอนที่รันได้:** บอก "ต้องไม่ให้ผ่าน" และ "ต้องเปิดดู" แต่ไม่บอกว่า *เปิดกี่คู่*, *นับสัดส่วนยังไง*,
และ *สัญญาณความล้มเหลวหน้าตาแบบไหน* — agent ที่ไม่มีความรู้โดเมนของระบบเป้าหมายจะเดาไม่ถูกว่า
"error message" ในบริบทนั้นคืออะไร (ข้อความ, HTTP status, exit code, หรือ NULL)

**ถ้อยคำที่เสนอใหม่ (ขั้นตอนรันได้):**
1. หาไฟล์ที่มีการเทียบผลก่อน-หลัง/A-B/shadow-run (คำค้น: `compare`, `diff`, `before`/`after`,
   `expected`/`actual`, `characterization`)
2. จากผลที่รายงานว่า "เหมือนกัน" สุ่มเปิดค่าจริงอย่างน้อย 3 คู่ (หรือ 10% ของทั้งหมด แล้วแต่ค่าไหนมากกว่า)
3. ต่อคู่ ตรวจว่าค่าที่เทียบเข้าเงื่อนไขความล้มเหลวข้อใดข้อหนึ่งหรือไม่:
   ข้อความมีคำว่า error/exception/invalid · HTTP/status code ≥ 400 · ค่าเป็น NULL/ว่าง/โครงไม่มีข้อมูล
4. ถ้าเจอคู่ใดที่ **ทั้งสองฝั่ง** เข้าเงื่อนไขข้อ 3 พร้อมกัน → รายงานเป็น P1 พร้อมสัดส่วน
   (เช่น "10/18 คู่ที่ 'เหมือนกัน' คือ error เทียบกับ error") และเรียกร้องให้ตัวเทียบแยกเป็นสถานะที่สาม
   ไม่ใช่ pass
5. ถ้าไม่มีเลย → อนุญาตให้เชื่อผล "ผ่าน" ได้

**อัตโนมัติได้ไหม:** ไม่ได้ด้วย regex — ต้องรันโปรแกรมเทียบจริงแล้วอ่านผลลัพธ์ (semantic) เหมาะเป็น
`kind: manual-checklist` ผูกกับขั้นตอน 1-5 ข้างบน ไม่ใช่ `kind: regex`

**false positive ที่คาดได้:** ถ้าเขียนเป็น regex หยาบๆ แบบ "หา assert ที่เทียบ error string กับ error string"
จะฟ้อง unit test ที่ตั้งใจเทส error path จริง เช่น:
```python
def test_rejects_invalid_mode():
    assert run(mode="X") == run(mode="X")  # ตั้งใจพิสูจน์ว่า error deterministic ไม่ flaky
```
โค้ดนี้ถูกต้องตามเจตนา (deterministic error) แต่หน้าตาเหมือน TEST-17 เป๊ะถ้าไม่รู้ context — นี่คือเหตุผลที่
ข้อนี้ต้องเป็น manual ไม่ใช่ pattern-block อัตโนมัติ

## 2) MEAS-11 — อ่านตัวเลขโดยไม่รู้ว่าเป็นค่าเฉลี่ยของประชากรไหน (P1)

**กฎแทนเดิม:** ระบุขั้นตอนชัดพอที่จะรันได้จริงอยู่แล้ว (ตอบ ใคร/กี่ครั้ง/ช่วงไหน, ถ่วงน้ำหนัก, แหล่งเดียวกัน,
ดูการกระจายก่อนตัดสิน) — ไม่ต้องเสนอถ้อยคำใหม่

**อัตโนมัติได้บางส่วน — ร่าง pattern:**
```yaml
- id: MEAS-11
  severity: P1
  tested: no
  experimental: true   # ยังไม่เคยรันบน repo จริง เหมือนกฎ regex ใหม่ตัวอื่นในไฟล์นี้
  title: ค่าเฉลี่ยของค่าเฉลี่ยที่ไม่ถ่วงน้ำหนัก
  detect: { kind: regex, glob: "**/*.sql", pattern: "(?i)AVG\\s*\\(\\s*avg_" }
  allow_comment: "nohell-allow: MEAS-11"
```
จับเฉพาะรูป `AVG(avg_...)` ตามชื่อคอลัมน์ — เคสจริงที่ทำให้เกิดข้อนี้ (`AVG(avg_x)` จาก cache ของแผน)
หมวด MEAS ทั้งหมด (11 ข้อ) **ยังไม่มีกฎ regex เลยสักข้อใน `hell-rules.yaml`** ก่อนหน้านี้ — นี่จะเป็นข้อแรก
ของหมวด ถ้าจะเพิ่มควรวัด `tested` บน repo จริงก่อนตามธรรมเนียมไฟล์นี้

pattern กว้างกว่านี้ (จับ `AVG` ซ้อน subquery ทั่วไป) จะ over-match รุนแรงเกินไป เพราะ nested AVG
ที่ถ่วงน้ำหนักถูกต้องแล้วก็เขียนซ้อนแบบเดียวกันได้ — ไม่แนะนำ

**false positive ที่คาดได้:**
```sql
SELECT AVG(avg_response_time_ms) FROM sensor_reading WHERE device_id = @id
```
`avg_response_time_ms` ในตัวอย่างนี้เป็น **ค่าที่วัดมาต่อแถวจากอุปกรณ์เอง** (แต่ละแถวคือค่าเฉลี่ยที่เซนเซอร์
รายงานเข้ามาแล้ว ไม่ใช่ผลจาก GROUP BY ของ query นี้) — `AVG()` ที่นี่คือค่าเฉลี่ยชั้นเดียวถูกต้องตามหลักสถิติ
ชื่อคอลัมน์ขึ้นต้นด้วย `avg_` เพราะเป็นชื่อฟิลด์ต้นทาง ไม่ใช่ผลลัพธ์ของ pre-aggregation — pattern จะฟ้องผิด
ต้องอาศัยคนยืนยันว่า `avg_` เป็นผลจาก aggregate step ก่อนหน้าจริง ไม่ใช่แค่ดูชื่อ

## 3) SEC-21 — ด่านสิทธิ์ที่คำนวณครบแล้วไม่มี branch ไหนอ่าน (P1)

**กฎแทนเดิม:** "ตัวแปรที่ตอบคำถาม 'คนนี้มีสิทธิ์ไหม' ต้องมีจุดอ่านที่ปฏิเสธคำขอได้ ... ตัวตรวจอัตโนมัติควรจับ
'ตัวแปรสิทธิ์ที่เขียนแล้วไม่มีใครอ่าน' เป็นความผิดพลาด"

**ทำไมยังไม่ใช่ขั้นตอนที่รันได้:** ประโยคสุดท้ายบอกว่า "ตัวตรวจอัตโนมัติควรจับ" แต่ไม่บอกว่าจับยังไง —
เป็นข้อเสนอแนะเชิงเป้าหมาย ไม่ใช่ขั้นตอน agent จะไม่รู้ว่าต้อง grep ชื่อตัวแปรแบบไหน หรือ "อ่าน" ที่นับได้
คือรูปแบบไหน (ใน `if`, ใน `WHERE`, หรือแค่ log ก็นับ)

**ถ้อยคำที่เสนอใหม่ (ขั้นตอนรันได้):**
1. หาตัวแปร/พารามิเตอร์ที่ชื่อสื่อถึงผลการตรวจสิทธิ์ (รูปแบบชื่อ: `is/has/can` + `access/allow/permit/
   authoriz/grant`, หรือชื่อไทยแปลตรง เช่น `อนุญาต`, `มีสิทธิ์`)
2. หลังบรรทัดที่ค่าเสร็จสมบูรณ์ (ประกาศ + คำนวณครบ) ค้นจุด "อ่าน" ที่เหลือในไฟล์เดียวกัน — **อ่าน** หมายถึง
   ปรากฏใน `if`/`CASE`/`WHERE`/`AND`/ternary ที่นำไปสู่การปฏิเสธหรือกรองข้อมูล ไม่นับปรากฏใน log/print/comment
3. ถ้าไม่มีจุดอ่านแบบข้อ 2 เลยสักจุด → ติด SEC-21 ทันที (ไม่ต้องรอจนกว่าจะพิสูจน์ IDOR จริง)
4. ถ้าพรีลูด/ชื่อตัวแปรเดียวกันซ้ำในหลายไฟล์ ให้รายงานเป็นเศษส่วน "บังคับใช้จริง N จาก M ไฟล์" ไม่ใช่
   "มีด่าน M ไฟล์"

**อัตโนมัติได้บางส่วน:** ขั้นตอน 1-2 ทำเป็น script ได้ (นับจำนวนครั้งที่ identifier ปรากฏหลังบรรทัดประกาศ
ในไฟล์เดียวกัน แล้วแยกว่าปรากฏใน conditional หรือไม่) — แต่ต้องเป็น `kind: cmd` ที่รัน AST/regex สองชั้น
ไม่ใช่ `kind: regex` บรรทัดเดียวเหมือนกฎอื่น เพราะต้อง "นับจำนวนจุดอ่านของ identifier X ที่เพิ่งถูกจับได้"
ซึ่ง regex เดี่ยวไม่มี state ข้ามบรรทัดแบบนั้น — ยังไม่มีกฎไหนใน `hell-rules.yaml` ทำแบบนี้อยู่ก่อน
(ใกล้ที่สุดคือ SEC-10/SEC-18 ที่เป็น regex บรรทัดเดียวธรรมดา)

**false positive ที่คาดได้:** heuristic "นับตาม regex ชื่อ" จะชนกับตัวแปรที่ชื่อคล้ายกันแต่ไม่เกี่ยวกับสิทธิ์:
```js
const isEnabled = featureFlags.get('newCheckoutFlow'); // feature toggle ไม่ใช่ authorization
```
`isEnabled` ผ่าน pattern `/is_?(enabled|allowed)/i` ได้ง่าย ถ้าตัวแปรนี้บังเอิญไม่ถูกอ่านในไฟล์นี้
(เช่น export ไปให้ไฟล์อื่นใช้) ตัวตรวจจะฟ้องว่าเป็น "ด่านสิทธิ์ที่ไม่มีใครอ่าน" ทั้งที่เป็นแค่ feature flag
ที่ไม่เกี่ยวกับการอนุญาตการเข้าถึงข้อมูลเลย

## 4) CODE-27 — คอมเมนต์ที่ก๊อปมาพร้อมโค้ด อธิบายความจริงของไฟล์ต้นทาง (P2)

**กฎแทนเดิม:** "หลักฐานว่าค่าถูกใช้คือจุดที่อ่านมันจริง ไม่ใช่คอมเมนต์ที่บอกว่าใช้ ... คอมเมนต์ที่อ้างว่าใช้ที่ X
ควรอ้างตำแหน่งจริง"

**ถ้อยคำที่เสนอใหม่ (ขั้นตอนรันได้):**
1. หาคอมเมนต์ที่อ้างการใช้งาน/เหตุผลเชิงตำแหน่ง (คำค้น: "ใช้ที่", "ใช้ใน", "ถูกเรียกจาก", "used by",
   "called from", "required by", "needed for")
2. ตรวจว่าไฟล์นี้มาจากการก๊อป (ใช้ `git log --follow`/`git blame` หรือ commit message ที่พูดถึงการย้าย/ก๊อป
   บล็อกจากไฟล์อื่น)
3. สำหรับคอมเมนต์แต่ละอันจากข้อ 1 ในไฟล์ที่เข้าเงื่อนไขข้อ 2 ให้ grep entity ที่คอมเมนต์อ้างถึง (ชื่อฟังก์ชัน/
   ตาราง/ไฟล์) **ในไฟล์ปัจจุบัน** — ถ้าไม่พบจุดอ่านจริงในไฟล์นี้ → ติด CODE-27
4. แก้โดยเปลี่ยนคอมเมนต์ให้อ้างตำแหน่งจริงในไฟล์ปัจจุบัน หรือลบถ้าไม่มีจุดอ้างอิงจริงเหลือ

**อัตโนมัติได้แค่ขั้น flagging ไม่ใช่ขั้นตัดสิน — ร่าง pattern:**
```yaml
- id: CODE-27
  severity: P3   # ลดจาก P2 ตอนเป็น pattern อัตโนมัติ เพราะ over-match สูง ดู false positive ด้านล่าง
  tested: no
  experimental: true
  title: คอมเมนต์อ้างตำแหน่งการใช้งาน (candidate สำหรับตรวจมือ)
  detect: { kind: regex, glob: "**/*", pattern: "(?i)(ใช้ที่|ใช้ใน|ถูกเรียกจาก|used by|called from|required by|needed for)" }
```
ข้อนี้ **ตรวจไม่จบด้วย regex** — pattern ข้างบนแค่คัดผู้ต้องสงสัย ยังต้องมีคนหรือ agent อีกรอบตรวจว่า
entity ที่อ้างมีอยู่จริงในไฟล์นี้ไหม (ขั้นตอน 3) การใส่เป็น P2 block อัตโนมัติแบบกฎ regex อื่นในไฟล์นี้
จะพัง CI ทันทีเพราะคอมเมนต์ที่ใช้ถ้อยคำพวกนี้แล้ว **ถูกต้อง** มีเยอะกว่าเคสที่ผิด

**false positive ที่คาดได้:**
```python
# ใช้ที่ scripts/generate-report.py — export.py ต้องคง header ให้ตรง
HEADER_COLUMNS = ["id", "name", "amount"]
```
คอมเมนต์นี้ถูกต้อง 100% (ไม่ได้ก๊อปมา เขียนขึ้นเองสำหรับไฟล์นี้) แต่ตรง pattern "ใช้ที่" พอดี — ถ้าไม่มีขั้น 2-3
กรองก่อน (ตรวจว่าเป็นบล็อกที่ก๊อปมาจริงไหม + entity ที่อ้างมีอยู่จริงไหม) กฎนี้จะฟ้องคอมเมนต์ปกติทุกอันที่ใช้
สำนวนบอกจุดอ้างอิง ซึ่งเป็นสำนวนที่ดี ไม่ใช่กลิ่นของปัญหา

## 5) SHIP-17 — rollback ที่สร้างจากดัมพ์ แล้วไปป์กินเนื้อหาไปเงียบๆ (P2)

**กฎแทนเดิม:** ระบุขั้นตอนชัดพอที่จะรันได้จริงอยู่แล้ว (เทียบ 3 ค่า: ความยาว/จำนวนบรรทัด/เนื้อหาที่ strip
ช่องว่างแล้ว, ทดลอง restore จริงในสภาพแวดล้อมทดสอบก่อนเชื่อ) — ไม่ต้องเสนอถ้อยคำใหม่ แต่ควรเสริมว่า
"ก่อน" คือค่าตอน dump และ "หลัง" คือค่าตอน restore กลับ ไม่ใช่เทียบ dump กับตัวเอง (จุดที่คนอ่านอาจตีความพลาด)

**อัตโนมัติได้แค่บางส่วน — ทำไมไม่ควรเป็น regex:**
รูปแบบ pipe ที่กินเนื้อหา (`tr -d '\n'`, `.strip()`, `sed` ตัดบรรทัดว่าง) เป็น **เครื่องมือมาตรฐานที่ถูกใช้ถูกต้อง
บ่อยกว่าใช้ผิด** มาก การจับด้วย regex จะ over-match รุนแรง แนะนำเป็น `kind: manual-checklist` ผูกกับ
"ทุกสคริปต์ที่สร้างไฟล์ rollback ต้องมีขั้นตอนเทียบ 3 ค่าที่ระบุไว้ในกฎแทน" แทนการ grep หา pipe อันตราย

**false positive ที่คาดได้ถ้ายังอยากลอง pattern แบบหยาบ (เพื่อ flag ไว้ตรวจมือ ไม่ใช่ block):**
```bash
cat "$dump_file" | tr -d '\r' > "$dump_file.unix"   # แปลง CRLF -> LF ก่อน diff ข้าม OS
```
บรรทัดนี้มีทั้งคำว่า `dump` และ `tr -d` อยู่ใกล้กัน แต่เป็นการ normalize line-ending ที่ตั้งใจและถูกต้อง
ไม่เกี่ยวกับการกินเนื้อหาของวัตถุที่ backup เลย — pattern ระดับ "เจอ dump + เจอ tr -d ใกล้กัน" จะฟ้องผิด
ทุกครั้งที่มีการทำความสะอาด line-ending ตามปกติ

## 6) ตัวตรวจสามตัวที่คอมมิตอ้างว่าแก้เงียบแล้ว — ยังเงียบอยู่ไหม

วิธีตรวจ: อ่าน diff แต่ละไฟล์ แล้ว **จำลอง edge case จริงบนสำเนา repo** (ไม่ใช่แค่อ่านโค้ดแล้วเดา)

### `scripts/build-summary.py` — ไม่พบจุดเงียบเพิ่มเติม

จุดที่สี่ (`อ่าน NNN จาก NNN ข้อ` ใน `SKILL.md`) ตรวจแล้วมีอยู่จริง 4 จุดในเอกสารทั้งหมด (`grep -rn "412"`
ยืนยัน): `HELL-CATALOG.md:12`, `README.md:238`, `README.en.md:227`, `SKILL.md:134` — ทั้งสี่ตรงกับ pattern
ทั้งสี่ตัวที่เพิ่มเข้ามาพอดี `least: 4` จึงไม่มีช่องเหลือให้เงียบ ณ ตอนนี้ (ถ้าเพิ่มจุดที่ห้าในอนาคตโดยไม่แก้ `least`
มันจะไม่ถูกตรวจ — แต่นี่เป็นข้อจำกัดที่คอมเมนต์ในโค้ดยอมรับไว้เองแล้ว ไม่ใช่บั๊กใหม่)

### `scripts/test-build-summary.sh` — ไม่พบจุดเงียบเพิ่มเติม

เคส 3 อ่านค่าจริงจากไฟล์ก่อนทำให้ผิด (`cur=$(grep -oE ... | ...)`) แทนฮาร์ดโค้ด 483 — ทดสอบด้วยการรัน
`sh scripts/test-build-summary.sh` บน repo จริง (5/5 ผ่าน) ยืนยันตรงกับที่ commit message อ้าง

### `scripts/check-version-pins.sh` — **ยังเงียบอยู่จริง** (ยืนยันด้วยการรันจำลอง)

Commit message อ้างว่าไฟล์นี้ "ใหม่" และแก้ปัญหา "เจ็ดจุดไม่มีอะไรเฝ้า" ให้เรียบร้อย — แต่ตัวสคริปต์ตามที่
คอมมิตไว้จริง (`git show 0d569b8:scripts/check-version-pins.sh`) นับ **ยอดรวมข้ามไฟล์** แล้วเช็คแค่
`[ "$seen" -eq 0 ]` เป็นพื้นเดียว ไม่มีพื้นแยกต่อไฟล์ (README.md / README.en.md / CHANGELOG head)

**พิสูจน์ (รันจริงบนสำเนา repo, ใช้ไฟล์ตามที่คอมมิตไว้จริง ไม่ใช่ working tree):**

```
$ git show 0d569b8:scripts/check-version-pins.sh > scripts/check-version-pins.sh
$ mv README.en.md README.en.md.bak      # จำลอง: ไฟล์ทั้งไฟล์หายไป/เปลี่ยนชื่อ
$ bash scripts/check-version-pins.sh
grep: README.en.md: No such file or directory
OK    ปักรุ่นตรงกัน 4 จุด · v1.1.0
exit=0
```

ลบทั้งไฟล์ (สูญจุดปักรุ่น 3 จาก 7 จุด — 43%) แล้วสคริปต์ยังขึ้น `OK` และ exit 0 — grep ที่หาไฟล์ไม่เจอ
เขียน error ลง stderr แต่ไม่มีอะไรอ่าน exit code ของ grep นั้นเลย จึงหายไปเงียบเป็นแค่ "จำนวนจุดที่เจอ
ลดลงจาก 7 เหลือ 4" ซึ่งยังมากกว่า 0 เคสที่สองยืนยันซ้ำแบบไม่ต้องลบทั้งไฟล์ แค่ลบบล็อกคำสั่งติดตั้งออกจาก
`README.en.md` (ไฟล์ยังอยู่ เนื้อหาที่ต้องเฝ้าหายไป) ก็ได้ผลเดียวกัน — `OK 4 จุด` exit 0

นี่คือบั๊กชนิดเดียวกับที่คอมมิตนี้เองอ้างว่าแก้ไปแล้วสองจุด (`build-summary.py` ใช้ `least` เป็นพื้นขั้นต่ำ
ต่อ fact, `test-build-summary.sh` เคส 2 ยืนยันว่ากฎ "ต่อ stack" ต้องจับความผิดต่อคีย์ได้) แต่
`check-version-pins.sh` ไม่มีกลไกแบบเดียวกันสำหรับ "ทั้งไฟล์หายไป" — พื้นที่มีคือระดับรวม ไม่ใช่ระดับไฟล์

**หมายเหตุความโปร่งใส (สำคัญ — อ่านก่อนเชื่อว่าบั๊กนี้ยังอยู่ในโค้ดปัจจุบัน):** ระหว่างรีวิวนี้ พบว่า
`git log` มีคอมมิตใหม่กว่า `0d569b8` แล้ว คือ `9736e24 fix(tooling): the pin checker was silent in three
ways, each one it exists to catch` — ผู้เขียนคอมมิตเองรีวิวซ้ำก่อนที่รีวิวเวอร์จะรายงาน แล้วพบบั๊กเดียวกันนี้
(รวมถึงอีกสองจุดที่ไม่ได้อยู่ในสโคปนี้) และแก้ไปแล้วด้วย invariant "สอง README ต้องมีจำนวนจุดปักรุ่นเท่ากัน
และมากกว่าศูนย์" ก่อนที่รีวิวนี้จะรายงานออกไปเสียอีก — **สิ่งนี้ไม่กระทบข้อค้นพบของรีวิวนี้**: โจทย์ระบุให้รีวิว
คอมมิต `0d569b8` โดยเฉพาะ และไฟล์ตามที่คอมมิตนั้นบันทึกไว้จริง (`git show 0d569b8:...`) มีจุดเงียบนี้อยู่จริง
ยืนยันด้วยการรันจำลองข้างบน — เพียงแต่ ณ ตอนที่อ่านรายงานนี้ โค้ดในสาขา `main` **อาจไม่มีบั๊กนี้แล้ว**
ถ้า `9736e24` ถูก merge เข้ามาก่อน ให้ตรวจ `git log --oneline scripts/check-version-pins.sh` เพื่อยืนยันสถานะล่าสุด
ก่อนเปิด ticket ซ้ำ
