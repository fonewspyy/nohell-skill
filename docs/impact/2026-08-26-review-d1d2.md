## TEST-17 — เทสที่ผ่านเพราะทั้งสองฝั่งพังเหมือนกัน

**D1 — ค้นเอง ไม่ใช้ 3 ID ที่คอมมิตอ้าง (`TEST-09` `TEST-02` `MEAS-04`)**

ไล่ทั้ง 750 บรรทัดหา "ตัวเทียบที่ให้ผลบวกปลอมว่าไม่มีอะไรเปลี่ยน" เจอผู้ท้าชิงที่ใกล้กว่า 3 ตัวที่คอมมิตอ้าง:

| ID ที่เจอเอง | ทำไมดูใกล้ | ทำไมไม่ครอบ |
|---|---|---|
| `TEST-16` | ทั้งคู่คือ "เทสให้หลักฐานปลอมว่าระบบถูกต้อง" — คำเดียวกับที่ TEST-17 ใช้ ("รายงานออกไปว่า 'พิสูจน์แล้ว'") | กฎแทนของ TEST-16 คือ "ผูกเทสกับ rule id เมื่อกฎธุรกิจเปลี่ยน" — ใช้ไม่ได้กับบั๊กของ TEST-17 เพราะไม่มีกฎธุรกิจไหนเปลี่ยน ปัญหาอยู่ที่ตัวเทียบเอง ไม่ใช่เทสที่ค้างอายุ |
| `SSOT-16` | บังคับให้ทำ shadow run เทียบ C กับของเดิมบนข้อมูลจริง — เป็นบริบทเดียวกับที่ TEST-17 เกิด (เทียบก่อน-หลังการแก้ SP) | บอกว่า "ต้องเทียบ" แต่ไม่บอกว่าตัวเทียบเองต้องแยกแยะ "เหมือนกันเพราะพังเหมือนกัน" ออกจาก "เหมือนกันเพราะพฤติกรรมไม่เปลี่ยน" — ทำตาม SSOT-16 ครบ (มี shadow run จริง) บั๊กของ TEST-17 ก็ยังเกิดได้ |
| `TEST-09` (ที่คอมมิตอ้าง) | assert อ่อน | ตรง — assert เดี่ยว ไม่ใช่ตัวเทียบสองฝั่ง |

**สรุป D1: ผ่าน** ไม่มี ID เดิมข้อไหน (รวม TEST-16 ที่คอมมิตไม่ได้เช็ค) ที่ทำตามแล้วบั๊กนี้ไม่เกิด แต่ตารางในคอมมิตควรใส่ `TEST-16` แทนหรือเพิ่มจาก `TEST-09`/`TEST-02`/`MEAS-04` เพราะ TEST-16 คือคำอธิบายที่ตรงกับ "ทำไมมันร้ายแรง" มากกว่า

**D2 — ระดับ**

3 ID ที่คอมมิตอ้างเป็น D1 คือ `TEST-09` (**P3**) และ `TEST-02` (**P2**) — ทั้งคู่ต่ำกว่า P1 ที่ตั้งให้ TEST-17 สองระดับและหนึ่งระดับตามลำดับ
ถ้าตัดสินระดับจาก "ID ที่ใกล้ที่สุดตามกลไก" (assert ผิด/เทสหลอกตัวเอง) จะได้ P2-P3 ไม่ใช่ P1
แต่ถ้าตัดสินจาก **อาการ** ตามที่ `CONTRIBUTING.md` บอกให้ทำ (ไม่ใช่จากกลไก): "รายงานออกไปว่า 'พิสูจน์แล้ว' ทั้งที่ไม่ได้พิสูจน์อะไรเลย" คือหลักฐานปลอมสำหรับการตัดสินใจ deploy การเปลี่ยนแปลงต่อระบบ production —
ตรงกับ `TEST-16` (P1) ซึ่งได้ P1 ด้วยเหตุผลเดียวกัน ("เป็นหลักฐานปลอมว่า 'ระบบถูกต้อง'") ไม่ใช่เพราะมันทำข้อมูลพังโดยตรงตามนิยามในขั้นที่ 1 ของ decision tree

**คงระดับ P1** แต่แก้เหตุผลอ้างอิงในคอมมิต — อ้าง `TEST-16` ไม่ใช่ `TEST-09`/`TEST-02` เป็นหลัก

## MEAS-11 — อ่านตัวเลขโดยไม่รู้ว่าเป็นค่าเฉลี่ยของประชากรไหน

**D1 — พบทับซ้อนจริงที่คอมมิตไม่ได้เช็ค**

MEAS-11 มีสองประโยคที่แยกกันได้เป็นสองปัญหาคนละแบบ:

1. `"AVG(avg_x)" ให้ช่วงเงียบมีน้ำหนักเท่าช่วงพีค เพี้ยนได้หลายเท่าเมื่อทราฟฟิกกระจุก` ← นี่คือ **ค่าเฉลี่ยของค่าเฉลี่ย** คำต่อคำ
2. `ตัวเลขจาก cache ของแผนเดียวถูกอ่านเป็นภาพรวมของทั้ง object` ← นี่คือ scope ของประชากรที่วัดไม่ตรงกับที่อ้างถึง

ตัวที่ 1 ทับกับ **`AGG-04`** (P1 เหมือนกัน) ตรงตัว:

| ช่อง | `AGG-04` | `MEAS-11` (ประโยคแรก) |
|---|---|---|
| Hell | ค่าเฉลี่ยของค่าเฉลี่ย | (ไม่มีชื่อแยก แต่ประโยคแรกของอาการคือเรื่องเดียวกัน) |
| กฎแทน | "ใช้ผลรวมหารด้วยผลรวมของจำนวน ไม่ใช่เฉลี่ยซ้อนเฉลี่ย" | "ถ่วงน้ำหนักด้วยจำนวนครั้งเสมอ" |

ทดสอบ D1: เอากฎแทนของ `AGG-04` ("ใช้ผลรวมหารด้วยผลรวมของจำนวน") มาใช้กับกรณี `AVG(avg_x)` ที่ MEAS-11 ยกตัวอย่าง — ปัญหานั้นหายไปพอดี เพราะเป็นบั๊กเดียวกัน
คอมมิตเช็ค D1 กับ `MEAS-03` `MEAS-06` `MEAS-09` (ทั้งสามอยู่หมวด MEAS) แต่ไม่ได้เปิดหมวด `AGG` เลย ทั้งที่ชื่อหมวด "การรวมยอดบนเซ็ตที่ไม่ตรงคำถาม" บอกตรงตัวว่าเป็นเรื่องเดียวกับ "ค่าเฉลี่ย/ผลรวมที่คำนวณผิดเซ็ต"

ประโยคที่ 2 (scope ของ cache/plan) **ไม่ทับ** ใครเลย — เป็นเรื่อง "ตัวเลขตัวเดียวกันมาจากคนละ scope แล้วไม่มีป้ายบอก" ซึ่ง `MEAS-09` (ไม่มีข้อมูลกำกับ) ใกล้ที่สุดแต่ MEAS-09 พูดถึง metadata ของ*การวัด* (ใครวัด เครื่องมืออะไร) ไม่ใช่ metadata ของ*ประชากรที่ถูกวัด* (นับกี่ครั้ง ช่วงไหน) — นี่คือส่วนที่ MEAS-11 เพิ่มของจริง

**สรุป D1: ทับบางส่วน** — ไม่ใช่กรณีต้องลบทิ้งทั้งข้อ (ประโยคที่ 2 คือของใหม่จริง) แต่ประโยคแรกควรตัดออกแล้วอ้าง `AGG-04` แทน หรือรวม `AVG(avg_x)` เป็นตัวอย่างประกอบใน `AGG-04` แล้วให้ `MEAS-11` โฟกัสเฉพาะเรื่อง scope/ป้ายกำกับประชากรของค่าที่วัด

**D2 — ระดับ**

เดิมกังวลว่า MEAS-11 ควรเป็น P2 เพราะสามข้อที่คอมมิตอ้าง (`MEAS-03` `MEAS-06` `MEAS-09`) ล้วน P2 — แต่หลังพบว่าเนื้อหาจริงคาบเกี่ยวกับ `AGG-04` ซึ่งเป็น **P1** อยู่แล้วสำหรับกลไกเดียวกัน จึงไม่มีเหตุผลให้ลดระดับ **คงที่ P1**

**ช่อง "ใช้กับ" — ควรแก้**

ป้าย `ทุกที่` แต่อาการทั้งประโยคเป็นภาษาของ SQL Server DMV ล้วน (`plan cache`, `object` ในความหมายของ query plan, ตัวเลข ms จากแหล่งเดียวกันสี่แบบ — อ่านแล้วคือ `sys.dm_exec_query_stats` / `sys.dm_exec_procedure_stats`)
หลักการที่แท้จริง ("ตัวเลขทุกตัวต้องตอบได้ว่าเป็นค่าเฉลี่ยของใคร กี่ครั้ง ช่วงไหน") เป็นสากลจริง ใช้ได้กับ dashboard ของ APM ทั่วไป แต่ **อาการ** ที่เขียนไว้ไม่สื่อสิ่งนั้น — ทีม Go+PostgreSQL ที่อ่าน `ทุกที่` จะเจอตัวอย่างที่ไม่มีความหมายกับ stack ตัวเอง
เสนอ: เขียนอาการใหม่ให้มีตัวอย่างที่ไม่ผูกกับ SQL Server (เช่น latency เฉลี่ยจาก APM ที่ pre-aggregate ต่อ instance) หรือถ้าจะคงตัวอย่างเดิม ให้ย้ายป้ายเป็น `RDBMS`/`SQL Server` แทน `ทุกที่`

## SEC-21 — ด่านสิทธิ์ที่คำนวณครบแล้วไม่มี branch ไหนอ่าน

**D1 — ค้นเอง ไม่ใช้ 3 ID ที่คอมมิตอ้าง (`SEC-05` `SEC-06` `SEC-07`)**

ไล่หา "โค้ดที่คำนวณค่าไว้แต่ไม่มีใครอ่าน" ทั้งไฟล์ เจอผู้ท้าชิงเพิ่มจากที่คอมมิตเช็ค:

| ID ที่เจอเอง | ทำไมดูใกล้ | ทำไมไม่ครอบ |
|---|---|---|
| `CODE-06` (Dead code) | นิยามตรงตัว: ตัวแปรที่เขียนแล้วไม่มีจุดอ่าน = โค้ดตาย | กฎแทนคือ "ลบทิ้ง ตรวจด้วย coverage/telemetry" — ถ้าทำตามนี้กับ SEC-21 คือ **ลบตัวแปรสิทธิ์ทิ้ง** เพราะมันดู "ตาย" ซึ่งเป็นคำแนะนำที่ผิดสำหรับกรณีนี้โดยสิ้นเชิง (ควรต่อสาย ไม่ใช่ลบ) — นี่คือหลักฐานว่า SEC-21 ต้องแยกออกจาก CODE-06 ไม่ใช่แค่ไม่ทับ แต่ทับแล้วให้คำแนะนำที่อันตราย |
| `ARCH-21` (Read/Write rule ไม่สมมาตร) | ทั้งคู่คือ "ตัวตัดสินใจมีสองจุดที่ไม่ตรงกัน" | ARCH-21 คือฝั่งอ่าน (ปุ่ม/query) กับฝั่งเขียน (command) ใช้*นิยามคนละชุด* — ยังมีการบังคับใช้อยู่ทั้งสองฝั่ง แค่ไม่ตรงกัน ส่วน SEC-21 คือฝั่งเขียนคำนวณนิยามไว้แล้ว *ไม่บังคับใช้เลยสักฝั่ง* — คนละกลไก |
| `SEC-05` (ที่คอมมิตอ้าง) | ไม่มีด่านเลย | ตรง — SEC-21 มีด่าน (โค้ดที่คำนวณ) แต่ด่านไม่ถูกอ่าน ผ่านรีวิวง่ายกว่าไม่มีด่านเลยเพราะโค้ดดู "เหมือนตรวจแล้ว" |

**สรุป D1: ผ่าน** ยิ่งไปกว่านั้น `CODE-06` (dead code) ถ้าถูกนำมาใช้แทน SEC-21 จะให้คำแนะนำผิด (ลบ) แทนคำแนะนำถูก (ต่อสาย) — เป็นหลักฐานที่หนักแน่นกว่าการแค่ "ไม่ครอบ" ว่าทำไมต้องมีข้อแยก

**D2 — ระดับ:** P1 ถูกต้อง สอดคล้องกับ `SEC-05`/`SEC-06` ที่เป็น P1 ทั้งคู่ด้วยเหตุผลเดียวกัน (ไม่มีการบังคับสิทธิ์จริงที่ backend) **คงระดับ**

**หมวด — SEC หรือ ARCH?**

ตรวจ `ARCH-21` (ผู้ท้าชิงที่ใกล้ที่สุดใน ARCH) แล้วสรุปว่า **SEC ถูกแล้ว** เพราะ SEC-21 ไม่ใช่เรื่องสถาปัตยกรรม/ขอบเขตของระบบ (ARCH ทั้งหมวดคุยเรื่องการแบ่งโมดูล/service/layer) — SEC-21 คือข้อบกพร่องเฉพาะจุดในกลไกควบคุมสิทธิ์ระดับโค้ด ตรงกับนิยามหมวด SEC และอยู่ติดกับ `SEC-05`/`SEC-06`/`SEC-07` ซึ่งเป็นกลุ่มเดียวกัน (authorization enforcement)

**ช่อง "ใช้กับ":** `ทุกที่` ถูกต้อง — รูปแบบ "prelude ก๊อปข้ามไฟล์ บางไฟล์ต่อสาย บางไฟล์ไม่ต่อ" ไม่ผูกกับภาษาหรือฐานข้อมูลใด

## CODE-27 — คอมเมนต์ที่ก๊อปมาพร้อมโค้ด อธิบายความจริงของไฟล์ต้นทาง

**D1 — ค้นเอง ไม่ใช้ 3 ID ที่คอมมิตอ้าง (`CODE-19` `CODE-05` `SSOT-02`)**

พบผู้ท้าชิงที่ใกล้กว่าที่คอมมิตเช็ค คือ **`AI-07`**:

| ช่อง | `AI-07` | `CODE-27` |
|---|---|---|
| Hell | เอกสาร/คอมเมนต์ที่ไม่ตรงกับโค้ด | คอมเมนต์ที่ก๊อปมาพร้อมโค้ด |
| อาการ | agent เขียนคำอธิบายจากสิ่งที่ตั้งใจ ไม่ใช่สิ่งที่เขียน | คอมเมนต์จริงในไฟล์ต้นทาง แต่ผิดตั้งแต่วินาทีที่ถูกก๊อปมาไฟล์ใหม่ |
| กฎแทน | "ตรวจคอมเมนต์เทียบโค้ดในรีวิว หรือ generate จากโค้ดจริง" | "หลักฐานว่าค่าถูกใช้คือจุดที่อ่านมันจริง ไม่ใช่คอมเมนต์ที่บอกว่าใช้" |

ทดสอบ D1: ถ้าทำตามกฎแทนของ `AI-07` ("ตรวจคอมเมนต์เทียบโค้ดในรีวิว") กับกรณี CODE-27 จริง ๆ — รีวิวเวอร์ที่ตรวจว่าคอมเมนต์ตรงกับโค้ดหรือไม่ *จะ*จับได้ว่าคอมเมนต์อ้างจุดใช้งานที่ไม่มีอยู่ในไฟล์นี้ ดังนั้นในทางทฤษฎี AI-07 ก็ครอบกลไกนี้ได้เหมือนกัน
แต่ `AI-07` อยู่ในหมวด **"AI — โค้ดที่ agent สร้าง"** ซึ่งขอบเขตทั้งหมวดคือ "เกิดจาก agent" ตามชื่อหมวดเอง ส่วนเคสจริงของ CODE-27 (ตามคอมมิต) มาจากการเคลียร์โค้ดตายในงาน production ทั่วไป ไม่ได้ระบุว่าเป็นฝีมือ agent — ทีมที่ไม่ใช้ agent เขียนโค้ดเลยจะไม่มีวันอ่านหมวด AI จึงพลาดกฎนี้ทั้งที่ human ก๊อป-วางก็เกิดปัญหาเดียวกันได้

**สรุป D1: ผ่าน** แต่ตารางในคอมมิตควรเช็ค `AI-07` ด้วย เพราะเป็นกลไกที่ใกล้ที่สุดจริง ๆ ไม่ใช่ `CODE-19`/`CODE-05`/`SSOT-02` — เหตุผลที่แยกไม่ใช่เพราะกลไกต่างกัน (มันเหมือนกัน) แต่เพราะขอบเขตการอ่านของหมวด AI ไม่ครอบคนที่ไม่ใช้ agent ควรบันทึกเหตุผลนี้แทนของเดิม

**D2 — ระดับ**

ใช้ decision tree ตรง ๆ : ไม่ใช่ข้อมูลผิด/หาย/รั่ว/เงินเคลื่อนผิด (ขั้น 1) ไม่ใช่พังแบบดังที่กู้ได้เร็ว (ขั้น 2) → ตกไปขั้น 3 = P3 ตามตัวอักษรของ `CONTRIBUTING.md`
แต่มีบรรทัดหนึ่งในอาการที่เขียนไว้ว่า "แย่กว่านั้น เชื่อว่ามีการบังคับใช้ที่ไม่มีอยู่" — ถ้าคอมเมนต์ที่ก๊อปมาอ้างว่ามีการตรวจสอบ/บังคับสิทธิ์ที่จริงไม่มี นี่คือรูปแบบเดียวกับ `SEC-21` (ความเชื่อผิดว่ามีด่านป้องกันอยู่) ซึ่งเป็น P1 — ระดับที่เหมาะสมจึงแกว่งกว้างมากตามว่าคอมเมนต์นั้นอ้างอะไร
เทียบกับ `CODE-20` (any/dynamic ทั่วโปรเจกต์) ที่ได้ P2 ด้วยเหตุผลคล้ายกัน คือ "ซ่อนบั๊กไว้ไม่ให้เห็น" (ไม่ใช่ทำข้อมูลพังตรง ๆ หรือพังแบบดัง) — นี่คือบรรทัดฐานในหมวด CODE เองที่ยอมให้ P2 กับความเสี่ยงที่ "ซ่อนปัญหาไว้ให้สะสม" โดยไม่ต้องผ่าน decision tree ตรง ๆ

**คงระดับ P2** ตามบรรทัดฐาน `CODE-20` แต่ควรตัดวลี "เชื่อว่ามีการบังคับใช้ที่ไม่มีอยู่" ออกจากอาการ หรือแยกเป็นกรณีย่อยที่ยก P1 ถ้าคอมเมนต์อ้างเรื่องความปลอดภัย/สิทธิ์ — ตอนนี้ประโยคเดียวครอบทั้งสองความรุนแรงแล้วให้ระดับเดียว

## SHIP-17 — rollback ที่สร้างจากดัมพ์ แล้วไปป์กินเนื้อหาไปเงียบ ๆ

**D1 — ค้นเอง ไม่ใช้ 3 ID ที่คอมมิตอ้าง (`SHIP-04` `SHIP-06` `SHIP-03`)**

ผู้ท้าชิงที่ใกล้กว่าที่ยังไม่ถูกเช็ค: **`SQL-24`**

`SQL-24`: "SP ไม่อยู่ใน version control ... dump SP ทั้งหมดเข้า repo **และตั้ง drift check เทียบ prod เป็นระยะ**" — SHIP-17 คือเหตุการณ์ที่เกิด*ระหว่าง*การทำตาม SQL-24 พอดี (drift check ที่ SQL-24 สั่งให้มี ไปรายงานผลผิดเพราะไปป์ในกระบวนการดัมพ์กินอักขระ)
แต่ SQL-24 จำกัดที่ `มี SP` ส่วน SHIP-17 กว้างกว่า (ดัมพ์/backup/rollback ของสิ่งใดก็ได้ ไม่ใช่แค่ SP) — ไม่ทับ แต่ควรอ้างเป็นบริบทที่ SHIP-17 เกิดขึ้นจริง

**สรุป D1: ผ่าน** ไม่มี ID เดิมครอบ

**D2 — ระดับ: เสนอเปลี่ยน**

นี่คือข้อที่มีปัญหาจริงในตัวถ้อยคำเอง ไม่ใช่แค่ป้ายระดับ อาการเขียนปนกันสองทิศทางที่ควรได้ระดับต่างกัน:

1. **ทิศที่อาการบรรยายจริง (false positive):** ปิด restore แล้วเนื้อหาถูกต้อง แต่ตัวเทียบ drift (ที่เทียบความยาว/บรรทัดดิบ) รายงานผิดว่าไม่ตรง → เสียเวลาไล่หาสาเหตุที่ไม่มีอยู่ → ตรงกับขั้น 3 ของ decision tree (อ่านยาก แก้ยาก ดูแลยาก) = **P3** ไม่ใช่ P2 ด้วยซ้ำ
2. **ทิศที่กฎแทนกำลังป้องกันจริง (false negative):** ถ้าไปป์เดียวกันนี้กินอักขระที่มีความหมายจริงออกจากตัว "rollback" (ไม่ใช่แค่ตัวรายงาน drift) แล้วไม่มีใครรู้เพราะเชื่อว่า "รันผ่าน" คือหลักฐานว่าใช้ได้ — วันที่ต้อง restore จริงในเหตุฉุกเฉิน ตัวถอยจะคืนข้อมูลที่ขาดอักขระเงียบ ๆ ตรงกับขั้น 1 ของ decision tree (ข้อมูลที่บันทึกแล้วผิด/หายโดยระบบไม่ฟ้องเอง) = **P1**

กฎแทนที่เขียนไว้ ("ตัวถอยต้องพิสูจน์ว่าคืนได้เท่าเดิมทุกไบต์ ไม่ใช่แค่รันผ่าน") ป้องกันทิศที่ 2 ชัดเจน — นั่นคือความเสี่ยงจริงที่ข้อนี้มีไว้กัน ไม่ใช่ทิศที่ 1 ที่อาการเลือกมาเล่า
เทียบกับ `SHIP-06` (P1: "migration ที่ไม่มีทางกลับและไม่มี backup — เปลี่ยนแล้วเปลี่ยนเลย") — ตัวถอยที่ดูเหมือนใช้งานได้แต่จริง ๆ คืนข้อมูลผิดเงียบ ๆ คือ **สภาพเดียวกับไม่มีตัวถอยเลย** แค่รู้ตัวช้ากว่า (ตอนกำลังกู้วิกฤตจริง) ซึ่งอันตรายกว่า "ไม่มี backup" ตรง ๆ เสียอีก เพราะสร้างความมั่นใจปลอมไว้ก่อน

**เสนอ:** ยก SHIP-17 เป็น **P1** ให้ตรงกับ `SHIP-06` และเขียนอาการใหม่ให้ตัวอย่างหลักเป็นทิศที่ 2 (ตัวถอยจริงเสียหายเงียบแล้วไปใช้กู้วิกฤต) ส่วนกรณี false-positive-ของ-drift-check ที่ยกมาเล่าตอนนี้ ถ้าจะเก็บไว้ ให้แยกเป็นตัวอย่างประกอบ ไม่ใช่อาการหลัก เพราะสองทิศนี้ต้องการระดับต่างกันและปนกันอยู่ในประโยคเดียวตอนนี้ทำให้ตัดสินระดับไม่ได้แน่ชัด — นี่คือสิ่งที่ `CONTRIBUTING.md` ข้อ D2 เตือนไว้เอง: "อ่านตามอาการ ไม่ใช่ความรู้สึกว่าร้ายแรงแค่ไหน" — ปัญหาคือ **อาการเองก็คลุมเครือ** ต้องแก้อาการก่อนถึงจะตัดสินระดับได้จริง

**ช่อง "ใช้กับ":** `ทุกที่` ถูกต้อง — `tr -d`/`strip()` เป็นแค่ตัวอย่างประกอบ concept (ไปป์ที่ตั้งใจล้างขยะแต่กินเนื้อวัตถุ) ใช้ได้กับ backup/rollback ของอะไรก็ได้ ไม่ผูก stack

## สิ่งที่ตรวจแล้วผ่านจริง ไม่มีอะไรต้องแก้

- **จำนวนที่ประกาศ** (`488`/`31 หมวด`, ตัวเลขต่อหมวดทุกหมวด, `ทุกที่`=363, ผลรวม RDBMS=412) ตรวจนับมือกับเนื้อไฟล์จริงทุกหมวดแล้วตรงกับที่ประกาศ ไม่ใช่แค่เชื่อ `OK 488/31` ในคอมมิต
- ทั้ง 5 ข้อใหม่มี ID ต่อท้ายหมวดถูกต้อง (`CODE-27` ต่อจาก `CODE-26`, `SEC-21` ต่อจาก `SEC-20`, `SHIP-17` ต่อจาก `SHIP-16`, `TEST-17` ต่อจาก `TEST-16`, `MEAS-11` ต่อจาก `MEAS-10`) ไม่มีการแทรกกลาง
- ไม่มีข้อไหนใน 5 ข้อใหม่เป็น "คำแนะนำลอยๆ" ทุกข้อมีกฎแทนที่ตรวจได้เป็นรูปธรรม ผ่านเกณฑ์ "สิ่งที่จะถูกปฏิเสธ" ใน `CONTRIBUTING.md`
