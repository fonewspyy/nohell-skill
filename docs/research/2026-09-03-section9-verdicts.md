# §9 จุดขัดแย้ง C1–C16 — วัดข้อไหนได้ วัดแล้วได้อะไร และข้อไหนวัดไม่ได้เพราะอะไร

รายงาน `2026-09-02-accuracy-speed-eval.md` §9 ตั้งกติกาไว้ว่า **"ไม่เฉลี่ย ไม่เลือกข้างเงียบ ๆ"**
ทุกข้อในตารางนั้นคือคำถามที่หลักฐานชุดเดิมตอบไม่ได้ และถ้าต้องตัดสินใจ ต้องวัดเอง
เอกสารนี้คือการไล่วัดทั้ง 16 ข้อ พร้อมบอกตรง ๆ ว่าข้อไหนวัดไม่ได้ด้วยของที่มีและเพราะอะไร

**เครื่องมือ** `eval/reanalyze.py` — วิเคราะห์ซ้ำจากคำตอบที่ธนาคารเก็บไว้แล้ว **โดยไม่ยิงเพิ่มสักสาย**
มันไม่ตัดสินคะแนนเอง แต่ประกอบบรรทัดคำตอบสังเคราะห์แล้วส่งกลับเข้า `judge()` ตัวจริงใน `run.py`
ถ้าเขียนกติกาให้คะแนนซ้ำที่นั่น วันหนึ่งสองที่จะเดินจากกันโดยไม่มีอะไรฟ้อง (`ARCH-08`)

```bash
python eval/reanalyze.py --arm full --runs 3 --compare routed
```

## 1. C1 — ตัวเลขเดิมถูกทิศ แต่ **ยังไม่ถึงขั้นสรุปได้**

เอกสาร `2026-09-02-c1-catalog-access-experiment.md` สรุปว่า `full` ชนะ `routed` ที่ recall 10.8 จุด
และ must-ask 37.1 จุด และให้เหตุผลว่า *"10.8 จุด เป็น ~6 เท่าของ sd รอบต่อรอบของแขน full (0.017)
จึงไม่น่าเป็น noise"*

**เหตุผลนั้นใช้ตัวหารผิดตัว** sd รอบต่อรอบตอบคำถามว่า "ยิงเคสชุดเดิมซ้ำจะได้เลขต่างกันแค่ไหน"
ไม่ได้ตอบว่า "ผลต่างนี้จะยังอยู่ไหมถ้าใช้เคสอีกชุด" ซึ่งเป็นคำถามที่คนอ่านตัวเลขต้องการจริง (ดู §4)

วัดใหม่ด้วยการทดสอบที่ถูกกับรูปทรงของข้อมูล — เทียบจับคู่รายเคส รอบที่ 1 ของทั้งสองแขน:

| เกณฑ์ | ผลต่างเฉลี่ย | ช่วง 95% | เคสที่สองแขนต่างกัน | sign test |
|---|---|---|---|---|
| recall | +0.1176 | [−0.0882, +0.3235] | 5 ใบ (full ชนะ 4 แพ้ 1) | p = **0.375** |
| must_ask_hit | +0.3333 | [0.0000, +0.6667] | 3 ใบ (full ชนะ 3 แพ้ 0) | p = **0.250** |

**ทั้งสองเกณฑ์ยังไม่ถึงนัยสำคัญ** และข้อที่สองมีรายละเอียดที่ต้องเห็น:
must_ask ออกมา **3-0 ซึ่งคือผลที่สะอาดที่สุดเท่าที่เป็นไปได้** แล้วยังได้ p = 0.25
เพราะ sign test ที่มีคู่ต่างกัน 3 คู่ มีค่า p ต่ำสุดได้แค่ 0.25 เท่านั้น

> ⚠️ **ที่คู่ต่างกัน 3 คู่ ไม่ว่าผลจะสะอาดแค่ไหนก็เป็นไปไม่ได้ที่จะมีนัยสำคัญ**
> ต้องมีคู่ที่ต่างกันอย่างน้อย 5 คู่ (p ต่ำสุด = 0.0625) ถึงจะมีโอกาสแตะ 0.05
> นี่คือเหตุผลเชิงตัวเลขที่ต้องเพิ่มเคส must-ask ไม่ใช่แค่ "มีเยอะไว้ก่อนดีกว่า"

### 1.2 ตัวหารที่ถูกต้องกว่า: แขนเดียวกันคนละวัน ต่างกันเท่าไร

ยิงแขน `full` ใหม่ทั้งชุดในวันถัดมา (tag `t1`) ได้ตัวหารที่ตรงคำถามกว่า sd รอบต่อรอบ
**หลังกันเคส `b07` ออกแล้ว** (คำตอบที่ธนาคารเก็บมาไม่ใช่คำตอบ — ดู §8)

| ชุด (n=16 เคส) | recall | `must_ask_hit` (9 เคสเดิม) |
|---|---|---|
| `full` 09-02 รอบ 1 | 0.9062 | 0.7778 |
| `full` 09-02 รอบ 2 | 0.9062 | 0.8889 |
| `full` 09-02 รอบ 3 | 0.8750 | 0.7778 |
| **`full` 09-03 รอบ 4** | **0.8438** | **0.6667** |
| `routed` รอบ 1 · รอบ 2 | 0.7812 | 0.4444 |

- **recall** — `full` แกว่างเอง **6.2 จุด** ข้ามสี่รอบสองวัน ส่วนช่องว่างกับ `routed` คือ
  10.2 จุด ⇒ ช่องว่างใหญ่กว่าความแกว่างของตัวเองแค่ **1.6 เท่า** และรอบต่ำสุดของ `full`
  (0.8438) อยู่เหนือ `routed` เพียง 6.3 จุด
- **sd ที่ถูกต้อง** — 3 รอบวันเดียวได้ 0.0170 · เพิ่มรอบจากอีกวันเป็น **0.0299** (1.8 เท่า)
  ⇒ **ความแกว่างข้ามวันใหญ่กว่าในวันเดียวเกือบสองเท่า และ eval ไม่เคยวัดมันมาก่อน**
- **`must_ask_hit`** — แกว่างเอง **14.8 จุด** (0.8148 เฉลี่ยสามรอบ → 0.6667) ส่วนช่องว่าง
  กับ `routed` คือ 37 จุด ⇒ ใหญ่กว่าความแกว่าง 2.5 เท่า **ข้อนี้ยืนได้ดีกว่า recall มาก**

⇒ **ข้อสรุปที่รับน้ำหนักได้จริงคือข้อ must-ask ไม่ใช่ข้อ recall** และเป็นข้อที่สำคัญกว่าอยู่แล้ว
ตามเป้าหมายที่เจ้าของรีโปประกาศไว้ (`AI-06` — อย่าให้กฎธุรกิจที่เดาเอาถูกฝังลงโค้ด)

**สิ่งที่ไม่เปลี่ยน:** ทิศทางยังชี้ไปทางเดิมทุกเกณฑ์ และหลักฐานเชิงคุณภาพยังยืน —
สามเคสที่ `routed` ถอยจาก "ถาม" เป็น "เดา" ถูกตรวจทีละใบแล้วว่าข้อที่มันตอบ **ไม่เข้าจริง**
(`a03` TXN-17 · `a06` TIME-05 · `a08` AGG-05) นั่นเป็นหลักฐานคนละชนิดกับ p-value และไม่ถูกลบล้าง

**สิ่งที่เปลี่ยน:** ห้ามเขียนว่า "routing แย่กว่า 10.8 จุด" เป็นข้อเท็จจริง
ต้องเขียนว่า "วัดได้ 10.8 จุด ทิศทางสม่ำเสมอ แต่ยังไม่ผ่านเกณฑ์นัยสำคัญที่ n เท่านี้"

### 1.1 การจับคู่ไม่ได้ช่วยเพิ่มพลังเลย และนั่นเป็นข้อมูล

สมมติฐานตั้งต้นคือการทดลองแบบจับคู่ควรมีพลังสูงกว่า เพราะตัดความแปรปรวนระหว่างเคสออก
**วัดแล้วไม่จริงสำหรับข้อมูลชุดนี้**

```
corr(recall รายเคส ของสองแขน) = -0.039
sd(ผลต่าง) ที่วัดได้        = 0.452
sd(ผลต่าง) ถ้าสองแขนอิสระกัน = 0.443
```

สองค่าเกือบเท่ากัน ⇒ ผลรายเคสของสองแขน **แทบเป็นอิสระต่อกัน** เคสที่ `full` ทำได้ ไม่ได้บอกอะไร
เลยว่า `routed` จะทำได้ไหม การจับคู่จึงไม่ได้ลด variance และ MDE ของแบบจับคู่ก็ไม่ได้ดีกว่า

## 2. C3 — "จ่าย token เพื่อความแม่น" ไม่ฟรี และไม่ฟรีแบบวัดได้

ฝ่าย ก (#56/#94) ว่า input ที่ cache แล้วเกือบฟรี · ฝ่าย ข (#21 Anthropic) ว่า latency สเกลตาม token
ทั้ง input และ output รายงานบอกว่าประสานได้ถ้าแยก cached/uncached **แต่ไม่มีแหล่งไหนแยกให้**

ที่รีโปนี้แยกไม่ได้เหมือนกัน (ไม่มีทางบังคับ cache hit/miss ผ่าน `claude -p`) แต่ **วัดผลรวมได้**
สองแขนต่างกันแค่ปริมาณที่ต้องอ่าน: `full` อ่านแคตตาล็อกทั้งไฟล์ 198KB · `routed` อ่านเฉพาะช่วงบรรทัด

**คำตอบคือ: เครื่องวัดนี้วัดเวลาไม่ได้ และตัวเลขเวลาทุกตัวที่รีโปนี้เคยรายงานต้องถอน**

วัดจับคู่รายเคส 42 เคส ได้ `full` มัธยฐาน 55.2s vs `routed` 50.5s = **1.18 เท่า** และ
`full` ช้ากว่าใน 23/42 เคส (sign test p = 0.644) ซึ่งขัดกับ **"routing เร็วขึ้น 4.7 เท่า"**
ที่เอกสาร C1 รายงานไว้ — ตัวเลขนั้นมาจากเคสเดียว (`a09`, n=1 เทียบ n=2)

แต่ตัวเลข 1.18 เท่าก็ใช้ไม่ได้เหมือนกัน ดูเคส `a09` ใบเดียวกัน แขนเดียวกัน ข้ามเซสชัน:

| ไฟล์เวลา | `a09` | มัธยฐานทั้งชุด |
|---|---|---|
| `full` 09-02 | 172.8s, 144.6s | 158.7s (n=1 เคส) |
| **`full` 09-03** | **85.3s** | 55.2s (n=42) |
| `routed` 09-02 | 33.4s | 40.9s |
| **`routed` 09-03 ร2** | **50.3s** | 49.2s |
| `routed` 09-03 ร3 | 54.8s | 55.7s |

**แขนเดียวกัน เคสเดียวกัน ต่างกัน 1.9 เท่า** (`full` 172.8 → 85.3) และช่วงของสองแขน
**คาบเกี่ยวกัน** (`full` 85–173 · `routed` 33–55) ความต่างระหว่างเซสชันของแขนเดียวกัน
ใหญ่พอ ๆ กับความต่างที่อ้างว่าเป็นผลของแขน

สาเหตุ: `ask()` จับ **wall-clock** ของ `claude -p` ซึ่งขึ้นกับ `--jobs` ที่ใช้ในรอบนั้น
ภาระเครื่องขณะนั้น และเครือข่าย — วันนี้เครื่องรัน 36 process พร้อมกันจน RAM เหลือ 1.3GB
และ `claude` ตายด้วย `0xC0000409` หลายครั้ง ส่วนเมื่อวานเงื่อนไขเป็นอย่างอื่น

> ⚠️ **ทั้ง "4.7 เท่า" และ "1.18 เท่า" เป็นผลของเงื่อนไข ไม่ใช่ของตัวแปรต้น**
> ที่จับได้เพราะบังเอิญมีเคสเดียวกันวัดซ้ำห้าครั้งข้ามเซสชัน ถ้ามีชุดเดียวก็จะรายงาน
> 1.18 เท่าไปด้วยความมั่นใจเท่า ๆ กับที่เมื่อวานรายงาน 4.7 เท่า

**เงื่อนไขที่จะวัดเวลาได้จริง** (ยังไม่เคยทำ): เซสชันเดียว · สลับแขนสับหว่างรายเคส ·
`--jobs` เท่ากัน · เครื่องไม่มีงานอื่น · และรายงานมัธยฐานของผลต่างรายคู่ ไม่ใช่ของแต่ละแขน

## 3. C6 — N-vote ไม่คุ้ม แต่กติกา "เอาเฉพาะที่ทุกรอบเห็นตรงกัน" คุ้ม

รวมคำตอบ 3 รอบของแขน `full` (37 เคส · recall 17 เคส · must-ask 9 เคส) ด้วยสี่กติกา:

| กติกา | recall | must_ask_hit | false_alarm | acceptable | ยิงกี่ครั้ง |
|---|---|---|---|---|---|
| **single** (ที่ใช้อยู่) | 0.9020 (sd 0.0170) | **0.8148** (sd 0.0642) | 10.0 | 7.0 | 1× |
| union (≥1 รอบ) | 0.9118 | 0.7778 | 14 | 11 | 3× |
| majority (≥2 รอบ) | 0.9118 | 0.7778 | 12 | 7 | 3× |
| **unanimous** (ครบ 3 รอบ) | 0.8824 | 0.7778 | **4** | 3 | 3× |

**majority ตามโปรโตคอลของ #19 ไม่คุ้มสำหรับงานนี้** — จ่ายค่ายิง 3 เท่า เพื่อ recall +1.0 จุด
แล้ว **เสีย must_ask 3.7 จุด และเพิ่ม false alarm 2 ID/รอบ** สองอย่างหลังคือสิ่งที่เจ้าของรีโปอยากลด

เหตุผลที่ must_ask แย่ลงทุกกติกาที่รวมเสียง: `ask_ok` เป็น 1 ต่อเมื่อ **ตอบ ASK และไม่มี ID เลย**
การรวมเสียงจากหลายรอบทำให้ ID จากรอบที่เดามาปนกับ ASK จากรอบที่ถาม ผลคือได้ทั้งสองอย่าง ซึ่งนับเป็นเดา

### 3.2 C14 — หลักฐานทางอ้อมว่า "รอบสองควรตัดออก ไม่ใช่หาเพิ่ม"

แถว `unanimous` คือสิ่งที่น่าสนใจที่สุดในตาราง: **false alarm 10 → 4 (ลด 60%)** และ acceptable 7 → 3
แลกด้วย recall −2.0 จุด

รายงาน §7.6 เสนอทางประสานของ C14 ไว้ว่า *"รอบสองต้อง **ตัดออก** ไม่ใช่ **หาเพิ่ม**"*
(#35 ว่า self-critique ได้ผล · #77 CR-Bench ว่า Reflexion ดัน recall +5.75 แต่ SNR ตกจาก 5.11 → 1.95)
`unanimous` เป็นตัวกรองที่ **ตัดออกอย่างเดียว** และผลออกมาตรงกับทางประสานนั้นพอดี

> ⚠️ **นี่เป็นหลักฐานข้างเคียง ไม่ใช่การวัด C14 โดยตรง** — C14 ถามถึง *self-critique*
> (ให้โมเดลตรวจงานตัวเอง) ส่วน `unanimous` คือ *self-consistency* (ให้หลายรอบโหวตกันเอง)
> กลไกคนละตัว บังเอิญให้ผลไปทางเดียวกัน การวัด C14 จริงต้องมีแขนที่ยิงรอบสองเพื่อตัด ID ทิ้ง

## 4. C11 + C15 — คำตอบที่พลิกวิธีอ่านตัวเลขทุกตัวในรีโปนี้

### 4.1 sd ที่ `run.py` พิมพ์ ตอบคำถามคนละข้อกับที่คนอ่านคิด

| แขน | sd รอบต่อรอบ (ที่พิมพ์อยู่) | se เคสต่อเคส (clustered) | อัตราส่วน |
|---|---|---|---|
| `full` (3 รอบ) | 0.0170 | **0.0641** | **3.8 เท่า** |
| `routed` (2 รอบ) | **0.0000** | **0.0864** | ∞ |

#74 ในรายงานเดาไว้ว่า clustered SE ใหญ่กว่าได้ถึง 3 เท่า — **วัดจริงได้ 3.8 เท่า และแขนหนึ่งได้ ∞**

`routed` สองรอบให้ recall เท่ากันเป๊ะ (0.7941 ทั้งคู่) และ must_ask เท่ากันเป๊ะ ⇒ sd = 0
ถ้าอ่าน sd อย่างเดียวจะสรุปว่า "แม่นยำสมบูรณ์ ไม่มีความไม่แน่นอนเลย" **ซึ่งผิดสองชั้น**

**ชั้นที่หนึ่ง** โมเดลไม่ได้นิ่ง — เทียบคำตอบรายเคสของสองรอบ:

```
เคสที่มี 2 รอบ                    37
คำตอบ (ชุด ID + ASK) เหมือนกันเป๊ะ  24 / 37     ⇒ เปลี่ยนไป 13 เคส (35%)
ข้อความดิบเหมือนกันทุกตัวอักษร      21 / 37
```

13 เคสเปลี่ยนคำตอบ แต่เปลี่ยนแบบหักล้างกันพอดี (บางเคสดีขึ้น บางเคสแย่ลง) ค่าเฉลี่ยจึงนิ่งสนิท
**`sd = 0` ไม่ได้แปลว่าโมเดลนิ่ง มันแปลว่าค่าเฉลี่ยกลบความไม่นิ่งไปหมด**

**ชั้นที่สอง** ช่วงความเชื่อมั่นที่แท้จริงกว้างมาก:

| แขน | recall ที่รายงาน | ช่วง 95% แบบ bootstrap รายเคส | ตัวเลขที่ซื่อสัตย์ |
|---|---|---|---|
| `full` | 0.9118 | [0.7647, 1.0000] | **0.91 ± 0.12** |
| `routed` | 0.7941 | [0.6176, 0.9412] | **0.79 ± 0.16** |
| `full` must_ask_hit | 0.7778 | [0.4444, 1.0000] | **0.78 ± 0.28** |

⇒ **ห้ามรายงาน recall เป็นทศนิยม 4 ตำแหน่งอีก** ตัวเลขหลัง `0.9` ไม่มีความหมาย
และ `must_ask_hit` ที่ ±0.28 แปลว่าตอนนี้เรายังแยก "ถามถูก 45%" จาก "ถามถูก 100%" ไม่ออก

### 4.2 C11 — จำนวนเคสที่ชุดนี้ต้องมี (คำนวณจากความแปรปรวนของตัวเอง ไม่ใช่ลอกใคร)

ฝ่าย ก (#71) ว่า ~1,000 · ฝ่าย ข (#48 Anthropic) ว่า 20–50 คือจุดเริ่มที่ดี
รายงานบอกว่าประสานได้ (30 เคสจับ effect ใหญ่ได้ จับเล็กไม่ได้) **แต่ nohell อยู่ในระบอบ effect เล็กแล้ว**

คำนวณจาก sd รายเคสของแขน `full` (power 80%, α = .05):

| จะจับผลต่าง recall | ต้องมีเคสที่มี `must_find` ราว |
|---|---|
| 15 จุด | 24 |
| 10 จุด | 55 |
| 5 จุด | 219 |

**ตอนนี้มี 17 เคส ⇒ ผลต่างที่เล็กที่สุดที่ชุดนี้จับได้คือราว 17.9 จุด**
(สำหรับแขน `routed` ที่ sd สูงกว่า ตัวเลขเดียวกันคือ 24.2 จุด)

⇒ **ทั้งสองฝ่ายถูก และรีโปนี้อยู่ฝั่งที่เจ็บ** — 20–50 เคสพอสำหรับ "ของใหม่ดีกว่าของเดิมชัด ๆ"
แต่การแก้ skill ที่ตั้งใจจะดันคุณภาพขึ้นทีละไม่กี่จุด **วัดด้วยชุดนี้ไม่ออก** ไม่ว่าจะยิงกี่รอบ
เพราะการเพิ่มรอบไม่ได้ลด se เคสต่อเคสเลยแม้แต่น้อย มันลดแค่ sd รอบต่อรอบซึ่งเล็กอยู่แล้ว

> **นี่คือสิ่งที่ต้องรู้ก่อนแก้ skill ครั้งต่อไป** ถ้าเป้าหมายคือ "ดัน recall อีก 3 จุด"
> เครื่องวัดปัจจุบันบอกไม่ได้ว่าทำสำเร็จไหม ต้องเพิ่มเคสก่อน ไม่ใช่เพิ่มรอบ

## 5. ข้อที่ **วัดไม่ได้** ด้วยของที่มี — และเพราะอะไร

ทุกข้อในหัวข้อนี้ **ไม่ได้แปลว่าไม่สำคัญ** แต่แปลว่าถ้าวัดด้วยของที่มีตอนนี้จะได้ตัวเลข
ที่หน้าตาเหมือนผลวัดแต่ไม่ได้วัดสิ่งที่ถาม ซึ่งเป็นความผิดพลาดที่รีโปนี้เจอมาแล้วหลายรอบ

| # | เหตุผลที่วัดไม่ได้ / ยังไม่วัด |
|---|---|
| **C2** prompt caching | `claude -p` ไม่มีสวิตช์บังคับ cache hit หรือ miss และไม่รายงานว่ารอบนี้ hit หรือไม่ ⇒ **คุมตัวแปรต้นไม่ได้เลย** ถ้าวัดเวลาเฉย ๆ แล้วเรียกว่า "ผลของ caching" คือการติดป้ายให้ noise |
| **C4** fan-out | คำถามคือ "review หนึ่งชิ้นควรแตกเป็นหลาย subagent ไหม" ส่วน `--jobs` ของ eval คือการยิงหลาย**เคส**พร้อมกัน ซึ่งเป็น throughput ของเครื่องวัด **ไม่ใช่สถาปัตยกรรมของ skill** วัดตัวหลังแล้วตอบตัวแรกคือคนละคำถาม |
| **C5** เรียงลำดับ | วัดได้จริง (สลับลำดับหมวดในแคตตาล็อกแล้วยิงซ้ำ) แต่ต้องยิงเต็มชุดต่อหนึ่งลำดับ และรายงานเองก็บอกว่าอาจไม่ใช่ข้อขัดแย้งจริง (positional bias vs attention capacity เป็นคนละกลไก) ⇒ **ต้นทุนสูง คุณค่าต่ำ จัดคิวท้ายสุด** |
| **C7** confidence | ต้องมีแขนที่สั่งให้โมเดลติดค่าความมั่นใจมากับทุก ID แล้ววัด calibration ⇒ ต้องแก้ทั้ง `WELLFORMED_RE` และ `parse_answer` ซึ่งกระทบตัวเลขย้อนหลังทั้งหมด |
| **C8** reasoning | `claude -p` ไม่ได้เปิดทางให้สั่ง extended thinking แบบคุมได้จากตรงนี้ ⇒ คุมตัวแปรต้นไม่ได้ |
| **C10** CoT | ขัดกับกติกาการตอบของ eval โดยตรง (บรรทัดเดียว ห้ามอธิบาย) การเปิด CoT ต้องออกแบบ `parse_answer` ใหม่ทั้งชุด — และ §7 ของรายงานเตือนไว้แล้วว่า **b05 เคยถูกขูด ID จากร้อยแก้วมานับเป็น false alarm** |
| **C12/C13** judge | **ไม่เกี่ยวกับรีโปนี้** `run.py` ตัดสินด้วย exact match ของ ID ไม่มี LLM judge อยู่ในวงจรเลย ทั้งสองข้อจึงไม่มีผลจนกว่าจะเปลี่ยนวิธีตัดสิน |
| **C16** hierarchical route | **ไม่ใช่ข้อขัดแย้งสำหรับรีโปนี้** — ตรวจโครงไฟล์แล้ว: `skills/nohell/` มี **5 ไฟล์** ทั้งหมด และ `SKILL.md` (148 บรรทัด) อ้างถึงแค่ 4 ไฟล์แบบ**ชั้นเดียว** เงื่อนไขที่ทำให้ #83/#84 ขัดกับ #88 คือ reference ที่ซ้อนชั้นจนโดน `head -100` ตัด — โครงนี้ไม่มีการซ้อนชั้นเลย "31 หมวด" เป็นหัวข้อ*ภายในไฟล์เดียว* ไม่ใช่ไฟล์แยก ส่วนทางเลือกที่มีจริง (อ่านทั้งไฟล์ vs อ่านเฉพาะช่วงบรรทัด) คือ C1 ซึ่งวัดไปแล้ว |

## 6. C9 — แขนพร้อมแล้ว รอผล

`PROMPTS['full_ask']` ใน `eval/run.py` ต่างจาก `full` **แค่ประโยคเดียวท้ายกติกาการตอบ**
(สั่งว่ากฎธุรกิจที่โจทย์ไม่ระบุห้ามเดาแทน ให้ตอบ ASK แม้เห็นข้อที่น่าจะเข้า)

**เกณฑ์ตัดสินของการทดลองนี้ไม่ใช่ `must_ask_hit` ตัวเดียว** — การดัน ask-rate ทำได้ง่ายมาก
ด้วยการสั่งให้ถามบ่อยขึ้น แล้วมันจะไปโผล่เป็น `ask_on_bug` แทน (ถามในเคสที่มีคำตอบชัด
= ผลักภาระกลับไปหาคนโดยไม่จำเป็น ซึ่งเป็นสิ่งที่เจ้าของรีโปประกาศว่าอยากลด)

ต้องอ่านสามตัวพร้อมกัน: **`must_ask_hit` ขึ้น · `ask_on_bug` ต้องไม่ขึ้น · `recall` ต้องไม่ตก**
ตอนนี้ `ask_on_bug` = 0 ทั้งสองแขน จึงมีที่ให้แย่ลงได้เต็มที่ และนั่นคือสิ่งที่ต้องเฝ้า

**วัดแล้ว 2026-09-03** · 46 เคส 1 รอบ · เทียบกับแขน `full` ที่วัด **วันเดียวกัน** (tag `t1`)
จึงไม่มีตัวกวนข้ามวันแบบที่ทำให้ตัวเลข C1 อ่านยาก

### ผล — สั่งให้ถามได้ผล และไม่ได้จ่ายด้วยสิ่งที่กลัว

กัน **6 เคสที่ปนเปื้อน** ออกจากทั้งสองแขนก่อน (คำตอบเป็นคำขอสิทธิ์ ไม่ใช่คำตอบ — ดู §8.1)
เหลือ **38 เคสที่เทียบได้** ทั้งสองแขนใช้ชุดเดียวกันเป๊ะ

| เกณฑ์ | `full` | `full_ask` | Δ |
|---|---|---|---|
| **recall** (n=14) | 0.8214 | **0.8214** | **0 — ไม่เสียเลย** |
| **must_ask_hit** (n=15) | 0.6000 | **0.8000** | **+20 จุด** |
| **false_alarm** | 17 | **8** | **−53%** |
| **ask_on_bug** | 0 | **0** | **0 — ผลข้างเคียงที่กลัวไม่เกิด** |
| acceptable | 5 | 6 | +1 |

**เกณฑ์ที่ตั้งไว้ก่อนวัดผ่านครบทั้งสามข้อ**: `must_ask_hit` ขึ้น · `ask_on_bug` ไม่ขึ้น ·
`recall` ไม่ตก — และ false alarm ลดลงเกินครึ่ง ซึ่งไม่ได้อยู่ในเกณฑ์ตั้งต้นด้วยซ้ำ

### เคสที่เปลี่ยน — และมันกระจุกอยู่ที่เดียว

**สามเคสที่เปลี่ยนจากเดาเป็นถาม ล้วนเป็นตระกูลปัดเศษเงิน:**

| เคส | `full` ตอบ | `full_ask` ตอบ |
|---|---|---|
| `a01` ปัดเศษเงิน (บั๊กจริง) | `TYPE-04` | **`ASK`** |
| `a09` ปัดเศษเงิน (เคสควบคุม) | `TIME-03` `TYPE-04` | **`ASK`** |
| `p01` ฝาแฝดร้อยแก้วของ a01 | `TIME-02` `TYPE-04` | **`ASK`** |

นี่คือตระกูลที่บันทึกไว้ตั้งแต่ต้นว่า **ผลิต false alarm ครึ่งหนึ่งของทั้งชุด**
ประโยคเดียวที่เติมเข้าไปแก้ได้ตรงจุดนั้นพอดี

**ที่เหลือคือ false alarm ที่หายไปจากเคสสะอาดและฝาแฝด** (`c06` `c08` `p03` `p04` `b11`)
สวนทางด้วย 2 เคส (`b12` `c04` เพิ่มขึ้นอย่างละ 1)

### ความเชื่อมั่น — ทิศเดียวกันทุกเกณฑ์ แต่ยังไม่มีเกณฑ์ไหนถึงนัยสำคัญ

| เกณฑ์ | เคสที่ต่างกัน | sign test |
|---|---|---|
| `must_ask_hit` | 3 ใบ (`full_ask` ชนะ 3 · แพ้ 0) | **p = 0.250** ← เพดานของ 3 คู่ |
| false_alarm | 10 ใบ (ลด 8 · เพิ่ม 2) | **p = 0.109** ← ใกล้ที่สุดในชุดนี้ |
| recall | 0 ใบ | ไม่มีข้อมูลให้ทดสอบ |

⇒ **ไม่มีเกณฑ์ไหนผ่าน 0.05 แต่ก็ไม่มีเกณฑ์ไหนที่ขยับสวนทาง** และ `recall` ที่เท่ากันเป๊ะ
เป็นหลักฐานชนิดที่แข็งกว่า p-value: **ไม่มีเคสบั๊กใบไหนเลยที่แย่ลง**

## 7. สิ่งที่เอกสารนี้ทำให้ต้องเปลี่ยนในทางปฏิบัติ

1. **`run.py` พิมพ์ sd ที่ตอบคำถามผิดข้อ** — ควรพิมพ์ se เคสต่อเคสคู่ไปด้วย หรืออย่างน้อย
   ติดคำเตือนว่า sd ตัวนี้ไม่ใช่ความไม่แน่นอนของตัวเลข (ยังไม่แก้ในรอบนี้ — กระทบ baseline)
2. **เลิกรายงาน recall 4 ตำแหน่ง** ความละเอียดจริงคือ ±0.12
3. **การแก้ skill ที่หวังผลต่ำกว่า ~18 จุด วัดไม่ออกด้วยชุดปัจจุบัน** ต้องเพิ่มเคสก่อน ไม่ใช่เพิ่มรอบ
4. **must-ask ต้องมีเคสที่ทำให้สองแขนต่างกันอย่างน้อย 5 ใบ** ถึงจะมีโอกาสแตะนัยสำคัญ
5. **`unanimous` เป็นตัวกรอง false alarm ที่วัดผลได้แล้ว** (−60%) ถ้าจะใช้จริงต้องยอมจ่าย 3 เท่า
   และยอมเสีย recall 2 จุด — ยังไม่เสนอให้เปลี่ยน default เพราะ must_ask แย่ลง 3.7 จุดด้วย

### 8.1 คำตอบที่ไม่ใช่คำตอบ ถูกเก็บลงธนาคารแล้วให้คะแนนเป็น recall 0

> ผมต้องการสิทธิ์อ่านไฟล์ `C:\Users\Wassaphas\.claude-pools\account_c\skills\nohell\HELL-CATALOG.md`
> แต่ระบบยังไม่อนุมัติให้ — รบกวนช่วยอนุมัติ permission prompt ที่ขึ้นมาด้วยครับ

**การรันนั้นไม่เคยอ่านแคตตาล็อกเลย** แต่ `judge()` ให้คะแนน recall 0 ตามปกติ
และมันคือ 1 ใน 4 เคสที่ทำให้แขน `full` ดูถอยลงข้ามวัน — คิดเป็น 5.9 จุดจากทั้งหมด 11.8 จุด

  รวมข้าง ๆ ตัวอื่น ไม่มีอะไรบังคับให้คนอ่านไปดูว่ามันคือเคสไหน

  ⇒ ตรวจแล้วว่าสำเนาแคตตาล็อกในทุก pool **byte-identical กับ repo** (sha256 ตรงกันทั้ง 7 ที่)
  จึงไม่ใช่กรณี "วัดคนละแคตตาล็อก" แต่**ต้องตรวจซ้ำทุกครั้ง** เพราะไม่มีอะไรบังคับให้ตรงกัน

### 8.2 `--merge` เขียนทับ ไม่ใช่เขียนต่อท้าย — และด่านที่เขียนมากันมันก็พลาดคลาสเดียวกัน

`--merge r2` เขียนไฟล์หลักด้วยผลของ tag ที่ระบุ**เท่านั้น** คำตอบรอบก่อนหายเงียบ
ด่านแรกที่เขียนกันไว้เทียบ **จำนวน** คำตอบ ซึ่ง `r2` มี 1 ต่อเคสเท่ากับของเดิมพอดี
⇒ **ผ่านฉลุย เขียนทับรอบ 1 ทิ้ง พิมพ์ว่า "รวมแล้ว 44 เคส" และคืน exit 0**
แก้เป็นเทียบ **ตัวคำตอบ** ด้วย `Counter` แล้วทดสอบด้วยคำสั่งที่*คาดว่าจะถูกปฏิเสธ*

> ถ้ารันแต่คำสั่งที่ถูกต้อง (`--merge c,r2`) ด่านที่พังจะผ่านทั้งคู่และไม่มีวันถูกจับได้

### 8.3 เพดานของเครื่องไม่ใช่ "จำนวน agent" แต่เป็น RAM

ดิสแพตช์ 3 งาน × `--jobs 3` = 3 agent + 9 `claude -p` ลูก รวมกับ session อื่น
⇒ **36 node process · RAM ว่าง 1.3GB จาก 15.7GB** แล้วล้มด้วยข้อความที่ไม่มีคำว่าหน่วยความจำเลย

| `bash: fork: Resource temporarily unavailable` | `0xC000012D` | STATUS_COMMITMENT_LIMIT |

และ orchestrator จัดชั้นตัวแรกเป็น `transient` แล้ว **retry** ⇒ ภาระเพิ่มขึ้นตอนที่เครื่องกำลังจะหมด
