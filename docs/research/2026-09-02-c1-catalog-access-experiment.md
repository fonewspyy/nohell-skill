## วิธีวัด

สองแขนต่างกัน **แค่ตัวแปรเดียว: วิธีเข้าถึงแคตตาล็อก** โจทย์ · snippet · กติกาการตอบ ·
เฉลยสามชั้น · และ parser เหมือนกันเป๊ะทั้งคู่ (`eval/run.py --arm {full,routed}`)

| แขน | prompt สั่งให้ทำอะไร |
|---|---|
| `full` | อ่าน `skills/nohell/HELL-CATALOG.md` ทั้งไฟล์ (490 ข้อ / 198KB) |
| `routed` | อ่านรหัสหมวด 31 หมวดจาก `SKILL.md` เลือกหมวดที่เกี่ยว แล้วอ่าน **เฉพาะช่วงบรรทัดของหมวดนั้น** · ห้ามอ่านทั้งไฟล์ |

**เงื่อนไขการวัด** (ต้องระบุ ไม่งั้นตัวเลขอ้างไม่ได้)

- 37 เคสใน `eval/cases/` · `full` 3 รอบ · `routed` 1 รอบ
- `--jobs 2` สำหรับ `routed` (4 พร้อมกันทำให้เครื่องพัง `paging file is too small`)
- `routed` รันผ่าน claude-orchestrator บน pool `account_c`
  (ยืนยันด้วย `CLAUDE_CONFIG_DIR=C:/Users/Wassaphas/.claude-pools/account_c`)
  หั่นเป็น 10 คำสั่ง foreground ละ 4 เคส เพราะ Bash tool มี timeout สูงสุด 10 นาที
- ให้คะแนนด้วยเฉลยและ parser ชุดเดียวกันหลังเก็บครบ ⇒ ไม่มีแขนไหนถูกวัดด้วยไม้บรรทัดต่างกัน

**manipulation check** — ไม่มีทางบังคับให้ agent อ่านเฉพาะหมวด มีแค่คำสั่งใน prompt
เวลาที่วัดได้จึงทำหน้าที่เป็นตัวตรวจด้วย: ถ้ามันแอบอ่านทั้งไฟล์ 198KB ตามเดิม
เป็นไปไม่ได้ที่จะเร็วขึ้นหลายเท่า ⇒ ความต่างของเวลายืนยันว่าแขน `routed` อ่านน้อยลงจริง

## สามเคสที่ถอยจาก "ถาม" เป็น "เดา"

ทั้งสามเคยตอบ `ASK` **นิ่ง 3/3 รอบ** ในแขน `full`

| เคส | `routed` ตอบ | ข้อนั้นเข้าจริงไหม |
|---|---|---|
| `a03` สต็อกติดลบ | `TXN-17` | **ไม่** — `UPDATE` เดียวเป็น atomic ในตัวเอง ไม่มีขั้นเช็คแยกก่อนเขียน |
| `a06` ตัดรอบเดือน | `TIME-05` | **ไม่** — snippet ใช้ `@fromUtc`/`@toUtc` ระบุเขตเวลาชัด ตรงข้ามกับอาการ |
| `a08` ตัดชำระ | `AGG-05` | **ไม่** — `AGG-05` คือ `TOP 1` ที่ `ORDER BY` ตัดสินไม่ขาด · snippet ไม่มี `TOP` |

ทุกตัวเป็นข้อที่ **เกี่ยวข้องแต่ไม่ใช่คำตอบ** ⇒ กลไกที่อธิบายได้: เมื่อเห็นเฉพาะหมวดที่ตัวเอง
เลือก มันเจอข้อที่ *ดูใกล้เคียง* แล้วฟันธง แทนที่จะรู้ว่าโจทย์ขาดกฎธุรกิจที่เดาแทนไม่ได้

**นี่คือความผิดพลาดเดียวกับที่คนเขียนเฉลยของ `b02` ทำ** — หาข้อที่ตรงไม่ได้ ก็หยิบ `SQL-10`
ที่หน้าตาใกล้ที่สุดมาใส่ (ดู `eval/keys/merged.json` field `note` ของ `b02`)
**การจำกัดขอบเขตที่มองเห็นไม่ได้ทำให้ตัดสินแม่นขึ้น มันทำให้ตัดสินเร็วขึ้นบนข้อมูลที่น้อยลง**

## แต่ routing ไม่ได้แย่ทุกทาง — มันเจอสิ่งที่ full พลาด

`c03-idempotent-upsert` เคยถูกติดป้ายเป็น **เคสสะอาด** มาตลอด แขน `routed` รายงาน `TXN-19`
และตรวจแล้ว **เข้าจริง**: snippet คือ `MERGE ... WHEN NOT MATCHED THEN INSERT` ที่ไม่มี
`WITH (HOLDLOCK)` ตรงนิยามคำต่อคำ

วงจรปิดครบรอบในวันเดียว

```
g4 (audit เฉลย)  สังเกตบน c03 ว่า "แคตตาล็อกไม่มี ID สำหรับ MERGE race และ TXN-17
                 ตามตัวอักษรถือว่า MERGE ทำถูกแล้ว"
      ↓
d3 (ด่าน D1/D2)  เสนอ TXN-19 P1 · เทียบ 3 ID ใกล้สุด ตอบ "เกิด" ครบ
      ↓
เพิ่มเข้าแคตตาล็อก (488 → 490)
      ↓
แขน routed       หา TXN-19 เจอบน c03 · แขน full ไม่เจอ
```

กลไกที่อธิบายได้: **อ่านเฉพาะหมวด `TXN` ทำให้ข้อใหม่เด่นขึ้น แทนที่จะจมอยู่ในกอง 490 ข้อ**
⇒ routing แลก *ความกว้าง* เป็น *ความลึกในหมวดที่เลือก*

ผลข้างเคียงที่ยอมรับไว้: เติม `TXN-19` เข้า `must_find` ของ `c03` ตามหลักฐาน แล้ว
**recall ของแขน `full` ตกจาก 0.958 เป็น 0.902** เพราะแขนที่เคยดูดีกว่าก็ถูกลงโทษ
ด้วยไม้บรรทัดเดียวกัน — ไม่ปรับเฉลยเพื่อรักษาตัวเลข

## ข้อสรุป และข้อจำกัด

**สำหรับ use case นี้ ฝ่าย ก ชนะบนความแม่น ฝ่าย ข ชนะบนความเร็ว**
routing เร็วขึ้น ~4.7 เท่า แล้วจ่ายด้วย recall 11 จุด และ ask-rate 37 จุด

เป้าหมายที่เจ้าของรีโปประกาศไว้คือ **คุณภาพของงานและเวลาของคน ไม่ใช่ต้นทุน token**
การถามคือสิ่งที่กันไม่ให้กฎธุรกิจที่เดาเอาถูกฝังลงโค้ดถาวร (`AI-06`) ⇒ **การแลก ask-rate
เกือบครึ่งเพื่อเวลา 2 นาทีต่อเคสเป็นการแลกผิดด้าน**

ทางที่ผลนี้เปิดไว้แต่ยังไม่ได้วัด: **ใช้ผสม** — `routed` สำหรับงานที่รู้หมวดแน่ชัดอยู่แล้ว
(review diff ที่แตะแต่ SQL) และ `full` สำหรับงานที่โจทย์กำกวมหรือยังไม่รู้ว่าจะเจออะไร

### ข้อจำกัดที่ต้องอ่านคู่กับตัวเลขทุกครั้ง

1. **`routed` มี 1 รอบ เทียบกับ `full` 3 รอบ** — แต่ recall ต่างกัน 10.8 จุด ซึ่งเป็น
   ~6 เท่าของ sd รอบต่อรอบของแขน `full` (0.017) และสามเคสที่ถอยเคยนิ่ง 3/3
   จึงไม่น่าเป็น noise ของรอบเดียว · **ยังไม่ได้ทำ power analysis** ตามที่ §7.2 ของรายงานแนะนำ
2. **เวลาเทียบจับคู่ได้แค่ `a09` (n=1)** — เลข "4.7 เท่า" มาจากคู่เดียว ถ้าต้องการเลขเวลา
   ที่เชื่อได้ต้องรันแขน `full` ใหม่ให้มีข้อมูลเวลาครบทุกเคส (อีก 37 calls)
3. **`must_ask_hit` มี n=9** ดีขึ้นจาก n=2 เดิมมาก แต่ยังเล็ก และ 6 ใน 9 เคสเป็น
   **เคสสังเคราะห์** ไม่ใช่บั๊ก production จริง (ดู field `source` ของแต่ละเคส)
4. **manipulation check เป็นทางอ้อม** — ยืนยันจากเวลา ไม่ได้ยืนยันจาก log ว่าอ่านไฟล์ช่วงไหนจริง
5. **วัดครั้งเดียวในวันเดียว บนเครื่องเดียว** — ไม่รู้ว่าผลนี้คงที่ข้ามวันหรือข้ามรุ่นโมเดลไหม

### ถ้าจะทำให้แน่นขึ้น ลำดับที่คุ้มที่สุด

1. รันแขน `full` ให้มีข้อมูลเวลาครบ 37 เคส ⇒ ได้เลขเวลาที่เทียบจับคู่ได้จริงทุกเคส (37 calls)
2. เติมแขน `routed` เป็น 3 รอบ ⇒ ได้ sd ของแขนนั้นเพื่อเทียบกับ sd ของ `full` (74 calls)
3. เพิ่มเคส must-ask ที่มาจาก **บั๊ก production จริง** และใช้ `lang: text` บรรยายเป็นร้อยแก้ว
   แบบ `b06` — เซสชันที่สร้างเคสเหล่านี้เขียน snippet ที่คิดว่าสะอาดแล้วมีบั๊กสามครั้ง
   ⇒ โค้ดในเคส must-ask ดึงความสนใจไปจากคำถามเชิงนโยบาย
