# eval — วัดว่าแคตตาล็อกยังใช้งานได้จริงแค่ไหน

เฟสนี้มาก่อนการเพิ่มเนื้อหาใด ๆ เพราะถ้าไม่มีเลขตั้งต้น การแก้ skill ทุกครั้งหลังจากนี้
จะอ้างว่า "ดีขึ้น" ได้โดยไม่มีใครค้านได้

```sh
python eval/run.py                 # 3 รอบ แล้วรายงาน variance
python eval/run.py --runs 1        # รอบเดียว ตอนกำลังแก้เคส
python eval/run.py --baseline      # เขียน eval/baseline.json
```

**ไม่ต้องใช้ API key** — provider คือ `claude -p` (Claude Code headless) ที่ล็อกอินอยู่แล้ว
ไฟล์นี้ไม่อ่านและไม่เก็บ credential ใด ๆ

⚠️ **หนึ่งเคส = หนึ่ง session** 24 เคส × 3 รอบ = **72 session ต่อการรันหนึ่งครั้ง**
รันเต็มชุดสองครั้งในวันเดียวชนเพดาน ตอนพัฒนาให้ใช้ `--runs 1`

ถ้ามีเคสยิงไม่ออกแม้แต่เคสเดียว ตัวรันจะ **หยุดทันที ไม่เขียน baseline และคืน exit 2** —
เพราะเคสที่ยิงไม่ออกได้คำตอบว่าง ซึ่งถูกนับเป็น recall 0 แล้วเฉลี่ยออกมาเป็นตัวเลข
ที่หน้าตาเหมือนผลวัด (วัดมาแล้ว: 21/24 เคสล้ม แต่รายงานพิมพ์ "recall 8.3%")

## สิ่งที่วัด

| ตัวเลข | ความหมาย | ตกแล้วแปลว่า |
|---|---|---|
| `recall` | เคสบั๊ก — เจอ ID ที่ควรเจอกี่ % | แคตตาล็อกหาไม่เจอแล้ว **ตัวเลขหลักที่ห้ามตกหลังแก้ skill** |
| `false_alarm_ids` | จำนวน **ID** ที่รายงานเกินมาทั้งชุด (ไม่ใช่จำนวนเคส) | เริ่มส่งเสียงรบกวน คนจะเลิกอ่าน |
| `must_ask_hit` | เคสที่คำตอบถูกคือหยุดถาม — ตอบ `ASK` กี่ % | เริ่มเดากฎธุรกิจแทนที่จะถาม |

ตัดสินด้วย **exact match ของ ID** ไม่ใช้ LLM judge (D4) — judge ที่เป็นโมเดลคือตัวแปร
อีกตัวที่คุมไม่ได้ แล้วเลข regression จะเชื่อไม่ได้

รัน 3 รอบเพราะคำตอบของโมเดลไม่นิ่ง `stdev` ในรายงานคือสิ่งที่บอกว่าเลข mean เชื่อได้แค่ไหน
ถ้า `stdev` ของ recall สูงกว่าส่วนต่างที่กำลังจะเคลม แปลว่ายังเคลมไม่ได้

## เพิ่มเคสใหม่

หนึ่งเคส = หนึ่งไฟล์ใน `eval/cases/*.json`

```json
{
  "id": "b13-ชื่อสั้น",
  "source": "บั๊ก production จริง (repo A) — ตัดชื่อระบบ/ตาราง/คนออกแล้ว",
  "lang": "sql",
  "task": "รายงาน ID ในแคตตาล็อกที่โค้ดนี้ละเมิด",
  "snippet": "...",
  "expected_ids": ["SQL-15"],
  "must_ask": false,
  "why": "เหตุผลที่แมปเป็น ID นี้ อ้างช่องอาการหรือกฎแทนของข้อนั้น"
}
```

กติกา

1. **snippet ต้องมาจากบั๊กจริง** ตัดชื่อบริษัท ชื่อระบบ ชื่อตารางจริง ชื่อคน ออกให้หมด
   เคสที่แต่งขึ้นเองวัดได้แค่ว่าโมเดลเห็นด้วยกับคนแต่ง ไม่ได้วัดว่าแคตตาล็อกจับบั๊กจริงได้
2. **`why` ต้องอ้างแคตตาล็อกได้** ไม่ใช่ความเห็น — ถ้าเขียน `why` ไม่ได้ แปลว่ายังแมปไม่ลง
3. **ID ต้องมีอยู่จริง** `validate-catalog.sh` ข้อ 7 จะจับให้เองถ้าอ้าง ID ที่ไม่มี
4. **เพิ่มเคสบั๊กแล้วต้องเพิ่มเคสสะอาดด้วย** ไม่งั้น recall ขึ้นได้ด้วยการทำให้ตัวเองขี้ระแวง
5. เคสที่คำตอบถูกคือ *หยุดถาม* ให้ตั้ง `must_ask: true` และ `expected_ids: []`
6. **เก็บ snippet ไว้ใน `.json` เท่านั้น อย่าแยกเป็นไฟล์ `.sql`/`.ts`** — เคสคือโค้ดที่จงใจผิด
   ถ้าวางเป็นไฟล์ตามนามสกุลจริง `nohell-check` จะจับมันในซีไอของ repo นี้เอง แล้วต้องไปใส่
   `.nohellignore` ตามทีหลัง ซึ่งเปิดช่องให้คนใช้ ignore เลี่ยงงานจริงในอนาคต
   (ตอนนี้ `--full` ได้ block 0 เพราะเคสอยู่ใน `.json` ที่ไม่มีกฎตัวไหนเล็ง)

## วิเคราะห์ซ้ำจากคำตอบที่เก็บไว้ — ไม่ยิงเพิ่มสักสาย

```sh
python eval/reanalyze.py --arm full --runs 3 --compare routed
```

`run.py` ยิงแล้วรายงาน · `reanalyze.py` **อ่านคำตอบที่ธนาคารเก็บไว้แล้วตอบคำถามที่
ตัวรายงานปกติตอบไม่ได้** — โดยไม่ใช้โควตาเลย: sign test, ช่วงเชื่อมั่นแบบ cluster bootstrap,
power analysis, การเทียบเวลาจับคู่รายเคส และการเทียบเคสฝาแฝด

⚠️ **`sd` ที่ `run.py` พิมพ์ไม่ใช่ความไม่แน่นอนของตัวเลข** มันตอบว่า "ยิงเคสชุดเดิมซ้ำ
จะได้เลขต่างกันแค่ไหน" ไม่ได้ตอบว่า "ถ้าใช้เคสอีกชุดจะต่างกันแค่ไหน" วัดแล้วว่า se
เคสต่อเคสใหญ่กว่า sd นั้น **3.8 เท่า** และแขน `routed` เคยได้ `sd 0.0000` ทั้งที่โมเดล
เปลี่ยนคำตอบไป 13 จาก 37 เคส — ค่าเฉลี่ยกลบความไม่นิ่งไปหมด
⇒ ก่อนเชื่อผลต่างใด ๆ ให้รัน `reanalyze.py` ดู sign test และช่วงเชื่อมั่นก่อน
รายละเอียดใน [`docs/research/2026-09-03-section9-verdicts.md`](../docs/research/2026-09-03-section9-verdicts.md)

## ชุดปัจจุบัน

**44 เคส** · 24 ใบมาจากบั๊ก production จริงของ repo A (ตัดชื่อระบบ/ตาราง/คนออกแล้ว)

| ชนิด | จำนวน | ที่มา |
|---|---|---|
| เคสบั๊ก (มี `must_find`) | 17 | บั๊ก production ที่บันทึกไว้ แมปเข้าแคตตาล็อกด้วยเกณฑ์ D1 |
| เคสสะอาด | 11 | เขียนตาม *กฎแทน* ของข้อที่เคสบั๊กละเมิด — ต้องได้ `NONE` |
| เคสต้องหยุดถาม — โค้ด | 9 | `a01`/`a02` จาก production จริง · `a03`–`a09` สังเคราะห์ |
| เคสต้องหยุดถาม — ร้อยแก้ว | 7 | `p01`/`p03`–`p08` ฝาแฝดของเคสโค้ด ใช้ `lang: text` |

⚠️ **ตัวเลขในตารางนี้เคยค้างอยู่สองรุ่น** (เขียนว่า 12/10/2 = 24 ทั้งที่มี 44)
นับใหม่ด้วยคำสั่งนี้ทุกครั้งที่เพิ่มเคส ไม่ใช่แก้มือ:

```sh
python -c "import sys;sys.path.insert(0,'eval');from run import load_cases,load_keys;\
c,k=load_cases(),load_keys();print(len(c),'เคส ·','บั๊ก',sum(1 for x in c if k[x['id']].get('must_find')),\
'· must-ask',sum(1 for x in c if x['must_ask']))"
```

**ฝาแฝดร้อยแก้วมีไว้ทำอะไร** — `task` เหมือนต้นฉบับทุกตัวอักษร เปลี่ยนแค่ snippet
จากโค้ดเป็นคำบรรยาย เพื่อทดสอบว่าโค้ดในเคส must-ask ดึงความสนใจไปจากคำถามเชิงนโยบายไหม
