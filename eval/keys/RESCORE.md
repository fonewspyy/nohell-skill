`run.py` (`\b([A-Z]{2,6}-\d{2})\b`) ไม่มีการเรียก `claude -p` หรือแก้ `run.py`/`cases/`/`g1..g5.json`/`skills/**`

## ส่วนที่ 2 — คะแนนใหม่ 3 รอบ × 3 นโยบาย

แก้บั๊ก A (must_ask คืน false_alarm=0 เสมอ) — เคส a01 ตอบ ID 4-5 ตัวทุกรอบแทนที่จะ ASK ในการคำนวณนี้
ID เหล่านั้นถูกนับเป็นความผิดในทุกนโยบายที่นับ "ไม่อยู่ใน expected/wrong" แล้ว

| นโยบาย | รอบ 1 | รอบ 2 | รอบ 3 | เฉลี่ย | เทียบ baseline เดิม |
|---|---|---|---|---|---|
| P0 false alarm (ของเดิม, แก้บั๊ก A) | 15 | 20 | 20 | **18.33** | 13.67 (ของเดิมนับ a01=0 เสมอ — ผิด) |
| P0 recall | 0.867 | 0.867 | 0.800 | 0.8445 | 0.8445 (เท่าเดิม — บั๊ก A ไม่กระทบ recall) |
| P1-lenient false alarm (wrong รอบแรกเท่านั้น) | 3 | 2 | 2 | **2.33** | — |
| P1-strict false alarm (wrong รอบแรก + d2) | 8 | 9 | 8 | **8.33** | ตัวที่ควรเทียบกับ 13.7 — ดูเหตุผลด้านล่าง |
| P1 recall (เทียบกับ must_find ที่แก้แล้ว) | 0.967 | 0.967 | 0.933 | **0.9556** | 0.8445 เดิม |
| P2 penalty ถ่วงตามระดับ (P1×3 · P2×2 · P3×1, ยิ่งน้อยยิ่งดี) | 24 | 28 | 28 | 26.67 | ไม่มีของเดิมให้เทียบ (ตัวชี้วัดใหม่) |

`ask_on_bug_case = 2` — b02-or-chain รอบ 2 และ 3 ตอบ ASK แทนที่จะฟันธง ได้ recall 0 ที่ไม่ถูกลงโทษเป็น
false alarm ในทั้ง P0/P1 (นิยาม false alarm ทุกตัวนับจาก ID ที่ตอบออกมา — ตอบ ASK ไม่มี ID จึงไม่โดนหัก)
ตัวเลขนี้แยกไว้ต่างหากตามที่โจทย์ขอ ไม่ปนกับ false alarm — และเป็นเหตุผลส่วนหนึ่งที่ recall เฉลี่ยยังไม่ถึง 100%
แม้ P1 will ให้เครดิตเต็มกับสิ่งที่เฉลยเดิมพลาดแล้วก็ตาม (b02 เองก็ไม่มี must_find อีกต่อไปหลัง key_verdict=wrong
จึงไม่กระทบ recall — 2 ครั้งที่ตอบ ASK อยู่ในเคสที่ไม่มี ground truth ให้เทียบแล้ว)

**ทำไมต้องใช้ P1-strict ไม่ใช่ P1-lenient เทียบกับ 13.7**: P1-lenient (2.33) นับเฉพาะ ID ที่ผู้ตรวจ
รอบแรกเห็นแล้วตัดสินว่า wrong — แต่ผู้ตรวจรอบแรกไม่เห็นคำตอบจริง จึงพลาด 8 ID ที่โมเดลตอบจริงไปทั้งหมด
(ตารางด้านบน) ถ้าใช้ 2.33 จะเป็นการอวดตัวเลขที่ดีเกินจริงจากช่องโหว่การตรวจ ไม่ใช่จากคุณภาพเครื่องมือจริง
P1-strict (8.33) ปิดช่องนั้นด้วยการตัดสิน 8 ID ที่เหลือเองแล้วรวมกลับเข้า wrong tier

## ส่วนที่ 3 — acceptable คือภาระหรือมูลค่า? ตัวเลขไม่ใช่ความเห็น

- เฉลี่ย **0.97 ID/เคส** อยู่ในชั้น acceptable (29 ID จาก 30 เคส) — 14/30 เคสมี acceptable อย่างน้อย 1 ตัว
  คนตรวจต้องกวาดตาอ่านเพิ่มไม่ถึง 1 บรรทัดต่อเคสโดยเฉลี่ย ถ้านับเป็นภาระ ภาระนี้เล็ก
- ในบรรดา acceptable ทั้งหมด **37.9% เป็น P1** (ข้อมูลผิด/ล่ม/รั่ว — ระดับรุนแรงสุด), 34.5% P2, 27.6% P3
  ถ้านับเป็นมูลค่า เกือบ 4 ใน 10 ของสิ่งที่ "ทิ้งไปได้" จริงๆ คือของระดับ P1 — ทิ้งไปแล้วเจ็บ
- ถ้าใช้ P1-strict policy ทั้งชุด false alarm เฉลี่ยเหลือ **8.33 ID/รอบ** เทียบกับ 13.7 เดิม
  ลดลง 39% — ลดจริงแต่ไม่ใช่การลดแบบพลิกหน้ามือเป็นหลังมือ (P1-lenient ที่ลดเหลือ 2.33 คือ 83% เป็น
  ตัวเลขที่ดูดีเกินจริงเพราะรั่วจากช่องว่างการตรวจ ไม่ควรใช้)

**สมมติฐานตั้งต้น ("เฉลยไม่ครบทำให้ false alarm สูงเกินจริง") เป็นจริงบางส่วน ไม่เต็มร้อย**: ส่วนหนึ่งของ
13.7 เดิมมาจากบั๊ก A ที่ไม่เกี่ยวกับความไม่ครบของเฉลยเลย (ถ้าแก้แค่บั๊ก A อย่างเดียวโดยไม่แก้เฉลย ตัวเลขคือ
18.33 — **แย่กว่าเดิม** ไม่ใช่ดีกว่า) เมื่อแก้เฉลยด้วย (P1-strict) ตัวเลขค่อยลดลงมาที่ 8.33 ซึ่งดีกว่า 13.7 จริง
แต่ยังห่างจากศูนย์มาก และห่างจากตัวเลข 2.33 ที่ดูน่าตื่นเต้นตอนแรกอยู่พอสมควร — ผู้ตัดสินใจต้องเลือกเองว่า
"acceptable 37.9% เป็น P1" ควรนับเป็นเครดิตของเครื่องมือ (เจอของจริงที่เฉลยไม่ทัน) หรือความเสี่ยง (คนอ่าน
ต้องกวาดตาแยกแยะเองว่าอันไหนของจริง) — ตัวเลขทั้งสองด้านอยู่ในตารางข้างบนแล้ว
