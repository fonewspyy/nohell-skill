# archaeology — ก่อนแก้ ต้องรู้ก่อนว่าตอนนี้จริงๆ มันเป็นยังไง

โค้ดที่อ่านอยู่บอกได้แค่ว่า **repo คิดว่าระบบเป็นแบบนี้** ไม่ได้บอกว่า production เป็นแบบนั้นจริง โดยเฉพาะระบบที่เคยมี hotfix แก้ตรงบนเครื่อง มี SP ที่ไม่เคยเข้า git และมีของที่ก๊อปแล้วเปลี่ยนชื่อ

งานของ skill นี้คือ **หยุดการเดา** ไม่ใช่หาความสวยงาม

---

## กฎเหล็ก: ติดระดับหลักฐานทุกครั้งที่พูดถึงพฤติกรรมระบบ (AI-19)

```
PROD      พฤติกรรม/ข้อมูลจริงในระบบที่ใช้งานอยู่          น่าเชื่อที่สุด
DB        schema / SP / ข้อมูล บนฐานข้อมูลจริง
TEST      มีเทสที่ยืนยันและเทสนั้นรันผ่านจริง
HISTORY   git log, ประวัติการแก้, คอมมิตที่เกี่ยวข้อง
SOURCE    ซอร์สโค้ดใน repo เท่านั้น
ASSUMED   เดาจากชื่อ จากรูปแบบ จากประสบการณ์             ห้ามส่งงานโดยมีข้อนี้ค้างในเรื่องสำคัญ
```

**ห้ามใช้ประโยคว่า "ระบบทำงานแบบนี้" กับหลักฐานที่ต่ำกว่า `DB`** ระดับ `SOURCE` ให้พูดว่า "โค้ดใน repo เขียนไว้ว่า..." เท่านั้น

เหตุผลที่ต้องเข้มขนาดนี้: repo กับ production เดินจากกันได้เสมอ — SP ที่แก้บน SSMS แล้วไม่เคย commit (SQL-24), hotfix ที่ไม่เคย merge กลับ (SHIP-10), feature flag ที่ปิดโค้ดก้อนนั้นอยู่ และโค้ดที่ยังอยู่แต่ไม่มีใครเรียกแล้ว

**วิธีอัปเกรดระดับหลักฐานอย่างเร็ว:** ตรวจว่า definition ใน DB ตรงกับไฟล์ใน repo หรือไม่ (`sys.sql_modules` เทียบกับไฟล์), ดูวันที่แก้ล่าสุดของ object เทียบกับวันที่คอมมิต, และดูว่ามีการเรียกจริงหรือไม่จาก call graph

## ขั้นตอน: สืบเรื่องเดียวให้จบ

### 1. ตั้งคำถามให้แคบพอที่จะตอบได้

"ระบบคิดภาษายังไง" ตอบไม่ได้ — "เอกสารขายที่ออกวันที่ 15 ก.ค. ใช้อัตราภาษีจากที่ไหน และถ้าอัตราเปลี่ยนวันนี้ ใบเก่าจะเปลี่ยนตามไหม" ตอบได้

### 2. หาเจ้าของความจริง แล้วหาสำเนาทั้งหมด

ขั้นนี้คือหัวใจ และเป็นขั้นที่พลาดบ่อยที่สุด

### 3. ทำบัญชีผู้เรียกให้ครบก่อนแตะ (SSOT-04)

- ฝั่ง DB: `sp_call_graph` ใน `detect-sqlserver.sql`
- ฝั่งแอป: ค้นชื่อ object ทั้งใน source, ใน dynamic SQL (สตริงที่ประกอบชื่อ SP), ใน config, ใน job scheduler, ใน report definition
- ฝั่งภายนอก: Flutter, Excel ที่ต่อตรง, ระบบ SAP, integration ที่เรียกผ่าน linked server
- **ที่ที่มักลืม:** job ที่ตั้งไว้บนเครื่องใครสักคน และรายงานที่คนใช้ก๊อปสูตรไปไว้ใน Excel ของตัวเอง

ถ้าค้นด้วยชื่ออย่างเดียวแล้วเจอน้อยผิดปกติ ให้สงสัยไว้ก่อนว่ามีการเรียกแบบ dynamic

### 4. ยืนยันด้วยพฤติกรรมจริง ไม่ใช่ด้วยการอ่าน

- รันสูตรของแต่ละสำเนากับข้อมูลจริงย้อนหลัง แล้วเทียบผลทีละแถว
- ถ้าผลตรงกันทั้งหมด → เป็นผู้สมัคร SSOT ที่ผ่านด่าน C1
- ถ้าผลต่าง → **หยุด** นี่คือคำถามธุรกิจ ไม่ใช่คำถามเทคนิค ห้ามเลือกเองว่าอันไหนถูก

## Rule-drift archaeology — ค้นด้วยรูปร่าง ไม่ใช่ชื่อ (LEG-16)

ตอนก๊อปโค้ด คนเปลี่ยนชื่อเสมอ แต่**ไม่ค่อยเปลี่ยนรูปร่างของกฎ** ฉะนั้นค้นด้วยชื่อฟังก์ชันจะพลาดเกือบทุกครั้ง ให้ค้นด้วยลายนิ้วมือเหล่านี้แทน:

| ลายนิ้วมือ | ตัวอย่างสิ่งที่ค้น | ทำไมได้ผล |
|---|---|---|
| ค่าคงที่และเกณฑ์ | `0.07`, `1000`, `30`, `1.07`, จำนวนวันเครดิต | ตัวเลขทางธุรกิจแทบไม่ถูกเปลี่ยนตอนก๊อป |
| ชุดสถานะที่ปรากฏร่วมกัน | `'01','02','99'` หรือ `IN (1,3,5)` ชุดเดิม | ชุดค่าเป็นลายเซ็นของกฎ |
| โครง CASE/IF เดียวกัน | ลำดับเงื่อนไขและจำนวนสาขาที่เหมือนกัน | คนก๊อปไม่จัดลำดับใหม่ |
| ขอบวันที่ | `DATEADD`, `EOMONTH`, `>= @from AND < @to` แบบเดียวกัน | ตรรกะขอบเวลาถูกก๊อปทั้งก้อน |
| สูตรคำนวณ | ลำดับการคูณ/หาร/ปัดเศษที่เหมือนกัน | ลำดับการดำเนินการคือลายเซ็น |
| ชุดตารางที่ถูกแตะพร้อมกัน | `duplicate_sp_dependencies` ใน `detect-sqlserver.sql` | สำเนาแตะข้อมูลชุดเดียวกันเสมอ |
| คู่ไฟล์ที่แก้พร้อมกันเป็นประจำ | `cochange.csv` จาก `/nohell-dig` | ถ้าต้องแก้สองที่ทุกครั้ง แปลว่ามันคือกฎเดียวกัน |
| ข้อความที่ผู้ใช้เห็น | ข้อความ error/ป้ายภาษาไทยที่ซ้ำกัน | ข้อความมักถูกก๊อปมาทั้งประโยค |

**Semantic drift** คือกรณีที่เจ็บที่สุด: สำเนาเคยเหมือนกัน แล้วมีคนแก้ข้างเดียวเมื่อสองปีก่อน ตอนนี้ต่างกันเล็กน้อยและ **ทั้งคู่ถูกใช้อยู่จริง** จับได้ด้วยการเทียบผลบนข้อมูลจริงเท่านั้น — อ่านโค้ดเทียบกันด้วยตาไม่พอ เพราะความต่างมักซ่อนอยู่ในเงื่อนไขเดียว

เจอเมื่อไหร่ให้บันทึกทันทีว่า **ผลต่างเกิดกับข้อมูลกี่แถว ในช่วงไหน** ตัวเลขนี้คือสิ่งที่ทำให้คนตัดสินใจได้ว่าจะแก้ย้อนหลังหรือปล่อย

## ผลลัพธ์ที่ต้องส่ง

เขียนลง `docs/archaeology/<เรื่อง>.md` — สั้นได้ แต่ต้องมีครบ:

```
คำถาม:        <คำถามที่แคบพอจะตอบได้>
คำตอบ:        <ประโยคเดียว> [ระดับหลักฐาน]
เจ้าของ:       <object ที่ควรเป็นแหล่งเดียว>
สำเนาที่พบ:    <รายการ + ต่างกันตรงไหน + กระทบกี่แถว>
ผู้เรียก:      <รายการ + ที่ยังไม่ได้ตรวจคืออะไร>
ยังไม่รู้:     <สิ่งที่ยังตอบไม่ได้ และต้องถามใคร>
ตรวจแล้วไม่ใช่: <ข้อสงสัยที่ปฏิเสธไป + กลไกที่ทำให้มันไม่เกิด>
ถัดไป:        <วง C ที่ควรเปิด หรือคำถามที่ต้องถามคน>
```

**ห้ามเติมช่องให้ครบด้วยการเดา** ช่อง "ยังไม่รู้" ที่ซื่อสัตย์ มีค่ากว่าคำตอบที่แต่งขึ้น เพราะคำตอบที่แต่งขึ้นจะถูกเอาไปใช้ตัดสินใจจริง

## เก็บข้อที่ตรวจแล้ว "ไม่จริง" ไว้ด้วย ไม่ใช่เก็บแต่ข้อที่จริง

รายงานการสืบส่วนใหญ่เก็บเฉพาะสิ่งที่พบ แล้วทิ้งสิ่งที่ตรวจแล้วพบว่าไม่ใช่ ทั้งที่อย่างหลัง
ป้องกันการเสียเวลาซ้ำได้ตรงกว่า เพราะข้อที่ *ดูเหมือนจะใช่แต่ไม่ใช่* คือข้อที่คนถัดไปจะเดินไปชนอีก

ทุกครั้งที่ปฏิเสธข้อสงสัยหนึ่ง ให้บันทึกสามอย่าง

```
ข้อสงสัย:   <สิ่งที่คิดว่าเป็นปัญหา เขียนแบบที่ทำให้คนอื่นก็คิดแบบนั้นได้>
ตรวจยังไง:  <คำสั่ง/ไฟล์/ข้อมูลที่ใช้ตรวจ พร้อมระดับหลักฐาน>
ทำไมไม่ใช่: <กลไกที่ทำให้มันไม่เกิด ไม่ใช่แค่ "ลองแล้วไม่เจอ">
```

**ช่อง "ทำไมไม่ใช่" คือช่องที่มีค่าที่สุด** — "ลองแล้วไม่เจอ" แปลว่ายังไม่รู้ว่าทำไม
และพรุ่งนี้เงื่อนไขเปลี่ยนนิดเดียวมันก็กลับมาได้ ส่วน "ไม่เกิดเพราะ X บังคับไว้" คือคำตอบที่ยังใช้ได้อีกปีหน้า
และบอกด้วยว่าถ้า X ถูกลบเมื่อไหร่ ข้อนี้จะกลับมาทันที

เก็บไว้ที่เดียวกับผลการสืบ (`docs/archaeology/`) ในหัวข้อแยก ไม่ต้องแยกไฟล์
ถ้าภายหลังพบว่าที่ปฏิเสธไปนั้นผิด ให้แก้ที่บรรทัดเดิมพร้อมวันที่และหลักฐานใหม่ ห้ามลบทิ้ง —
**ประวัติการเข้าใจผิดคือข้อมูล** ไม่ใช่ความน่าอาย

### เมื่อคนตรวจแก้คนหา ให้บันทึกว่าแก้ตรงไหน

ถ้ามีสองคน (หรือ agent สองตัว) คนหนึ่งหา อีกคนตรวจ แล้วคนตรวจพบว่าข้อสรุปถูกแต่**หลักฐานที่อ้างมาผิด**
ต้องเขียนไว้ว่าข้อนั้นยืนอยู่บนหลักฐานคนละชุดกับที่เสนอมาตอนแรก ไม่ใช่กลืนเข้าไปเงียบๆ

เพราะสิ่งที่จะถูกเอาไปอ้างต่อในการประชุมคือ *หลักฐาน* ไม่ใช่ข้อสรุป — ถ้าหลักฐานผิดแต่ข้อสรุปถูก
คนที่เอาไปอ้างจะถูกจับได้ แล้วข้อสรุปที่ถูกจะถูกปัดตกไปด้วย
