# conventions — รูปแบบที่ต้องเหมือนกัน

## กฎข้อแรก: แยกให้ออกว่าอะไรเป็นงานของเครื่อง

รูปแบบแบ่งเป็นสองกอง และปนกันไม่ได้

| กองของเครื่อง — **ห้ามอยู่ในไฟล์นี้** | กองที่ต้องเขียนไว้ — อยู่ในไฟล์นี้ |
|---|---|
| เว้นวรรค tab ความยาวบรรทัด | ชื่อสื่อความหมายว่าอะไร |
| ตำแหน่งวงเล็บ เครื่องหมายคำพูด | คำไหนแปลว่าอะไรในธุรกิจนี้ |
| ลำดับ import การเรียง key | โครงของ SP ที่ต้องมีทุกตัว |
| ตัวพิมพ์ใหญ่ของคีย์เวิร์ด SQL | หน่วยและสกุลเงินในชื่อ |
| จุดหลังบรรทัด เซมิโคลอน | ขอบเขตของคำ (Order ของใคร) |

ถ้าเรื่องไหน formatter/linter บังคับได้ **ให้ไปตั้งค่าที่นั่น ห้ามเอามาเขียนเป็นกฎให้คนหรือ agent จำ** — กฎที่ต้องอาศัยความจำคือกฎที่จะถูกละเมิด และการเอามาใส่ในไฟล์นี้แค่กิน context โดยไม่ได้อะไร (ดู CODE-17, TEAM-07, X3)

## 1. คำศัพท์ธุรกิจ — สำคัญที่สุดในไฟล์นี้

ระบบนี้พูดสองภาษา คนคุยกันเป็นไทย โค้ดเขียนเป็นอังกฤษ **จุดแปลคือจุดที่ของซ้ำเกิด** เพราะคนสามคน (หรือ agent สาม session) แปลคำเดียวกันได้สามแบบ แล้วกลายเป็นสามตาราง

เก็บไว้ที่ `docs/glossary.md` และให้เป็นแหล่งเดียว:

```
| คำที่ใช้พูด | ชื่อในโค้ด | หมายถึงอะไรแน่ ๆ | ห้ามใช้คำพวกนี้แทน |
|---|---|---|---|
| ใบรับเข้า | GoodsReceipt | เอกสารยืนยันว่าของเข้าคลังจริงแล้ว | Receive, GR, InboundDoc, RcvDoc |
| ใบเบิก | IssueRequest | คำขอเบิก ยังไม่ได้ตัดสต็อก | Withdraw, Pick, Request |
| ตัดสต็อก | StockDeduction | การลดจำนวนคงเหลือจริง | Cut, Minus, Reduce |
```

**กฎ**
- หนึ่งความหมาย = หนึ่งคำ ตลอดทั้งระบบ ตั้งแต่ชื่อตาราง ชื่อ SP ชื่อ field ใน API ยันข้อความบนหน้าจอ
- คำเดียวกันที่หมายคนละอย่างในคนละบริบท **ต้องตั้งชื่อให้ต่างกัน** — `SalesOrder` กับ `PurchaseOrder` ห้ามเรียกทั้งคู่ว่า `Order` (ARCH-12)
- เจอคำใหม่ระหว่างทำงาน ให้เติมลง glossary ในคอมมิตเดียวกัน ไม่ใช่ทำทีหลัง
- **ก่อนตั้งชื่ออะไรใหม่ ต้องเปิด glossary ก่อนเสมอ** ถ้าคำนั้นมีอยู่แล้วให้ใช้ของเดิม
- ห้ามใช้ตัวย่อที่ไม่ได้อยู่ใน glossary แม้จะดูชัดเจนแค่ไหน

## 2. SQL Server

### การตั้งชื่อ

| สิ่งของ | รูปแบบ | ตัวอย่าง | ห้าม |
|---|---|---|---|
| ตาราง | เอกพจน์ PascalCase ตามคำใน glossary | `GoodsReceipt`, `GoodsReceiptItem` | `tbl_gr`, `GRs`, `GoodsReceipts` |
| คอลัมน์ | PascalCase สื่อความหมายเต็ม | `ReceivedQuantity` | `Qty1`, `Field3`, `Flag` |
| คีย์นอก | `<ชื่อตารางที่ชี้ไป>Id` | `WarehouseId` | `WH`, `RefId`, `Code2` |
| stored procedure | `<โดเมน>_<กริยา><กรรม>` | `Inventory_CreateGoodsReceipt` | `sp_Save`, `usp_Data1`, `..._New_Final` |
| SP อ่านข้อมูล | ขึ้นต้นด้วย `Get`/`List`/`Search` | `Inventory_ListPendingReceipt` | ชื่อที่ไม่บอกว่าอ่านหรือเขียน |
| ดัชนี | `IX_<ตาราง>_<คอลัมน์>` | `IX_GoodsReceipt_DocDate` | ชื่อที่ generate มาแบบสุ่ม |
| unique | `UQ_<ตาราง>_<คอลัมน์>` | `UQ_GoodsReceipt_DocNo` | |
| คีย์นอก (constraint) | `FK_<ตารางลูก>_<ตารางแม่>` | `FK_GoodsReceiptItem_GoodsReceipt` | |

**ชื่อ SP ต้องบอกว่าอ่านหรือเขียน** — คนที่อ่านชื่อแล้วเดาไม่ออกว่ามันแก้ข้อมูลไหม จะไม่กล้าเรียกมัน หรือแย่กว่านั้นคือกล้าเกินไป

**ห้ามขึ้นต้นด้วย `sp_`** เด็ดขาด (SQL-27)

### พารามิเตอร์

- ชื่อตรงกับคอลัมน์ที่มันไปลง: `@WarehouseId` ไม่ใช่ `@p1`, `@w`
- **ชนิดต้องตรงกับคอลัมน์เป๊ะ** รวมความยาวและ `n` นำหน้า — ไม่งั้นเกิด implicit conversion แล้ว index หาย (SQL-11)
- พารามิเตอร์ที่บอกว่าใครทำ ต้องมีทุก SP ที่เขียนข้อมูล: `@ActionBy`
- **ห้ามมีพารามิเตอร์ที่เปลี่ยนความหมายของทั้ง SP** เช่น `@Mode`, `@ActionType` — ถ้ารู้สึกว่าต้องมี แปลว่าควรแยกเป็นคนละ SP (SQL-01, SSOT-03)

### ตัวแปรและตารางชั่วคราว

| ใช้ | เมื่อ | ชื่อ |
|---|---|---|
| `@ตัวแปร` | ค่าเดี่ยว | `@TotalAmount` ไม่ใช่ `@t`, `@x` |
| `@ตารางตัวแปร` | แถวน้อยมาก และรู้จำนวนแน่ | `@SelectedItem` |
| `#ตารางชั่วคราว` | ชุดใหญ่ ต้องการสถิติและ index | `#PendingItem` |

เลือกผิดระหว่างสองอันหลังทำให้แผน query พังโดยไม่มีใครรู้ (SQL-18) — ถ้าเลือกอันที่ไม่ตรงกับกฎนี้ ต้องเขียนเหตุผลไว้ตรงนั้น

### สถานะ

- เก็บเป็นรหัสที่อ่านออก ไม่ใช่ตัวเลขลอย: `'PENDING'`, `'CONFIRMED'` ไม่ใช่ `1`, `2`, `99`
- มีตาราง lookup เป็นเจ้าของค่า และฝั่งแอปต้อง generate ค่าคงที่จากที่นั่น (DATA-23)
- หนึ่งคอลัมน์เก็บหนึ่งมิติ อย่าปนสถานะกับเหตุผลกับประเภท (DATA-14)

### รับพารามิเตอร์แบบไหน: `@ParamName` แยกตัว vs `@iJson` vs TVP

คำถามจริงไม่ใช่ "อันไหนดีกว่า" แต่คือ **สัญญาของ SP นี้อยู่ที่ไหน**

พารามิเตอร์แยกตัวทำให้ลายเซ็นของ SP *คือ* สัญญา — engine ตรวจชนิดให้ฟรี ผู้เรียกส่งชื่อผิดคือ error ทันที และ `sys.parameters` บอกได้ว่ารับอะไรบ้างโดยไม่ต้องเปิดโค้ด
JSON ทำให้สัญญานั้น**หายไป** เหลืออยู่แค่ในคอมเมนต์ ซึ่งไม่มีอะไรบังคับให้ตรงกับโค้ด

| ใช้ | เมื่อ | ระวัง |
|---|---|---|
| `@ParamName` แยกตัว | ฟิลด์คงที่ ไม่เกินราวสิบตัว ไม่มีรายการลูก | เพิ่มฟิลด์ = เปลี่ยนลายเซ็น = ผู้เรียกเดิมต้องแก้ |
| TVP (table-valued parameter) | มีรายการลูก และผู้เรียกเป็น backend ที่ส่ง TVP ได้ | ต้องประกาศ table type และแก้ยากกว่า |
| `@iJson` | payload มาจาก API/Flutter เป็น JSON อยู่แล้ว หรือโครงซ้อน หรือ optional เยอะ | สัญญาหาย ต้องเอากลับคืนด้วยมือ ดูเทมเพลต |

**เกณฑ์ตัดสินง่าย ๆ:** ถ้าเลือก JSON เพราะ *ผู้เรียกส่ง JSON อยู่แล้ว* คือเหตุผลที่ดี ถ้าเลือกเพราะ *ขี้เกียจประกาศพารามิเตอร์* หรือ *เผื่อว่าจะเพิ่มฟิลด์ทีหลัง* คือเหตุผลที่แย่ และจะกลายเป็นหนี้ภายในสามเดือน

**สามข้อที่ห้ามลืมถ้าใช้ JSON**

1. **ห้ามมีฟิลด์ที่เปลี่ยนพฤติกรรมของ SP** — `"action": "create|cancel"` คือ `@ActionType` ที่ย้ายไปซ่อนใน payload ที่ที่ไม่มี linter มองเห็น นี่คือ God SP ที่งอกใหม่ (SQL-29, SSOT-03)
2. **`OPENJSON` ต้องมี `WITH` เสมอ** ชนิดตรงกับคอลัมน์ปลายทางเป๊ะ ไม่งั้นทุกค่าเป็น `nvarchar(4000)` แล้ว join ทีเกิด implicit conversion → index scan (SQL-30, SQL-11)
3. **ต้องปฏิเสธคีย์ที่ไม่รู้จัก** เพราะคีย์เป็น case-sensitive เสมอ ผู้เรียกพิมพ์ `warehouseID` แทน `warehouseId` แล้วค่าจะเป็น NULL เงียบ ๆ พารามิเตอร์แยกตัวได้การป้องกันข้อนี้ฟรี JSON ไม่ได้

ดูของจริงที่ `templates/stored-procedure-json.sql`

### โครง SP มาตรฐาน

ทุก SP ที่เขียนข้อมูลต้องมีโครงตาม `templates/stored-procedure.sql` (พารามิเตอร์แยกตัว) หรือ `templates/stored-procedure-json.sql` (รับ JSON) — ไม่ใช่ข้อแนะนำ

สิ่งที่ขาดไม่ได้: บล็อกอธิบายสัญญาที่หัวไฟล์ · `SET NOCOUNT ON` · `SET XACT_ABORT ON` · ตรวจ input ก่อนเริ่ม transaction · `TRY/CATCH` ที่ rollback แล้ว `THROW` ต่อ · result set ที่ประกาศไว้ชัดว่ามีกี่ชุดหน้าตายังไง · ไม่มี `PRINT` ไม่มี `SELECT *` ไม่มีโค้ด debug

## 3. โค้ดฝั่งแอป

### ไฟล์และโฟลเดอร์

จัดตาม **โดเมน** ไม่ใช่ตามชนิดทางเทคนิค

```
✓ inventory/goods-receipt/{route,service,schema,test}
✗ controllers/ services/ types/ utils/     ← แก้ฟีเจอร์เดียวต้องเปิดสี่โฟลเดอร์
```

### การตั้งชื่อที่มีผลจริง

| กฎ | ทำไม | ตัวอย่าง |
|---|---|---|
| ใส่หน่วยและสกุลเงินในชื่อ | ที่มาของบั๊กเงินและน้ำหนักเกือบทั้งหมด | `amountTHB`, `weightKg`, `durationMs` ไม่ใช่ `amount`, `weight` |
| `Id` ต่อท้าย = ตัว id ไม่ใช่ตัว object | กันการส่งผิดชนิดที่ compiler จับไม่ได้ถ้าเป็น string ทั้งคู่ | `warehouseId` vs `warehouse` |
| boolean ขึ้นต้น `is`/`has`/`can` | อ่านแล้วรู้ทันทีว่าเป็นคำถามใช่/ไม่ | `isConfirmed`, `canCancel` |
| ชื่อฟังก์ชันต้องบอกผลข้างเคียงทั้งหมด | ชื่อที่โกหกคือบั๊กที่รอเกิด | `getUser` ห้ามเขียน log หรือแก้สถานะ (CODE-08) |
| ชื่อบอกขอบเขต ไม่ใช่แค่ชนิด | คำเดียวกันคนละบริบทคือที่มาของ SSOT พัง | `SalesOrderRow` ไม่ใช่ `Row` |
| ห้าม `data`, `info`, `temp`, `handle`, `manager`, `helper` | ไม่มีคำไหนบอกอะไรเลย | ตั้งชื่อตามสิ่งที่มันเป็นจริง |
| ชื่อต้องอยู่ใน glossary | ป้องกันคำพ้องที่กลายเป็นของซ้ำ | ดูข้อ 1 |

**ความยาวของชื่อควรแปรตามขอบเขตของมัน** ตัวแปรที่มีชีวิตสามบรรทัดใช้ชื่อสั้นได้ ตัวที่ export ออกไปทั้งระบบต้องยาวและชัด

### ชนิดข้อมูล

- ค่าที่มีความหมายทางธุรกิจต้องมี type ของตัวเอง ไม่ปล่อยเป็น `string` ลอย ๆ (CODE-26)
- schema ที่ขอบเป็นแหล่งความจริงของ type — ประกาศครั้งเดียวแล้ว derive ทั้งสองฝั่ง อย่าเขียน interface ซ้ำมือ
- `any` ต้องมีคอมเมนต์เหตุผล ไม่งั้น linter บล็อก (CODE-20)

### ข้อความถึงผู้ใช้

- อยู่ในไฟล์แปลเสมอ แม้ตอนนี้จะมีภาษาเดียว (TIME-12)
- คู่กับรหัสคงที่ที่ฝั่ง client แยกแยะได้ ไม่ใช่ให้ไป match ข้อความไทย (API-05)

## 4. คอมมิตและ PR

รูปแบบ: `<ชนิด>(<ขอบเขต>): <ทำอะไร>` — `feat(receipt): รองรับรับเข้าบางส่วน`

**สิ่งที่สำคัญกว่ารูปแบบ**
- คอมมิตที่เปลี่ยนโครงสร้าง กับคอมมิตที่เปลี่ยนพฤติกรรม **ต้องแยกกัน** (LEG-06) — ปนกันแล้วหาสาเหตุไม่เจอตอนพัง
- คอมมิตที่แก้บั๊กแล้วมีไฟล์เทสถูกแตะด้วย ต้องอธิบายในข้อความว่าทำไม (F2, AI-13)
- ข้อความบอก **ทำไม** ไม่ใช่ **อะไร** — diff บอกอะไรอยู่แล้ว
- คอมมิตที่ปิดวง C ต้องอ้าง id จาก `CONSOLIDATIONS.yaml`

## 5. สิ่งที่ต้องตั้งค่าให้เครื่องทำ ไม่ใช่จำเอง

ตั้งครั้งเดียวแล้วเลิกคิดถึงมันตลอดไป:

- formatter ที่รันตอน save และตอน commit hook
- linter ที่บล็อก `any`, `console.log`, catch ว่าง, `as any`
- ตัวจัดรูปแบบ T-SQL ที่ตกลงรูปแบบเดียวทั้ง repo
- ตัวตรวจว่าชื่อ SP ตรงรูปแบบ (regex เดียวใน CI)
- ตัวตรวจว่าไฟล์ migration ตั้งชื่อและเรียงถูก
- `.editorconfig` เพื่อให้ทุกเครื่องมือเห็นตรงกัน

**ถ้ายังต้องรีวิวเรื่องพวกนี้ด้วยตา แปลว่ายังตั้งค่าไม่เสร็จ** — และเวลารีวิวที่หมดไปกับเรื่องพวกนี้คือเวลาที่ไม่ได้ใช้ดู logic
