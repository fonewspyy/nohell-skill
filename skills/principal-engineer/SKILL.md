# principal-engineer — คิดให้จบก่อนพิมพ์บรรทัดแรก

ระบบนี้มีคนดูแลคนเดียว นั่นแปลว่า **ความจำของโปรเจกต์ไม่ได้อยู่ในทีม แต่อยู่ในไฟล์** ทุกอย่างที่ skill นี้บังคับให้เขียน ไม่ใช่พิธีกรรมของบริษัทใหญ่ แต่เป็นการเขียนโน้ตให้ตัวเองในอีกสามเดือน และให้ agent ตัวถัดไปที่ไม่มี context อะไรเลย

ถ้าข้ามขั้นตอนในไฟล์นี้ ผลไม่ใช่ "ช้าลงนิดหน่อย" แต่คือ **แก้ไม่ครบ** แล้วต้องกลับมานั่งไล่ใหม่ ซึ่งแพงกว่าหลายเท่า

---

## กฎสูงสุด: ห้ามแก้ก่อนมี Impact Map

ก่อนแก้อะไรก็ตามที่เปลี่ยนพฤติกรรม ต้องตอบ 13 ช่องนี้ให้ได้ก่อน ตอบไม่ได้แม้แต่ช่องเดียว = **ยังไม่ถึงเวลาเขียนโค้ด ให้ไปสืบก่อน**

| # | ช่อง | คำถาม | ตอบไม่ได้แปลว่า |
|---|---|---|---|
| 1 | WHAT | จะเปลี่ยนพฤติกรรมอะไร เขียนเป็นประโยคที่ผู้ใช้เข้าใจ | ยังไม่รู้ว่าจะทำอะไร |
| 2 | OWNER | ความจริงเรื่องนี้ใครเป็นเจ้าของ (ตาราง/โมดูล/SP ไหนคือแหล่งเดียว) | เสี่ยงไปแก้สำเนา ไม่ใช่ต้นฉบับ |
| 3 | READERS | ใครอ่านความจริงนี้บ้าง (หน้าจอ รายงาน API job ระบบนอก) | จะมีที่ที่ยังแสดงค่าเก่า |
| 4 | WRITERS | ใครเขียนมันได้บ้าง | จะมีทางเขียนที่ข้ามกฎใหม่ |
| 5 | CALLERS | ใครเรียกโค้ดที่จะแก้ | จะพังในที่ที่ไม่ได้ตั้งใจแตะ |
| 6 | DATA | ตาราง/คอลัมน์ไหนได้รับผล ต้อง migrate ไหม | จะพบทีหลังตอนข้อมูลผิด |
| 7 | CONTRACT | API/รูปร่างผลลัพธ์/สัญญากับ Flutter หรือระบบนอกเปลี่ยนไหม | จะทำ client พังเงียบ |
| 8 | RACE | ถ้ารันพร้อมกัน หรือรันซ้ำ จะเกิดอะไร | จะได้เอกสารซ้ำ/ยอดเบิ้ล |
| 9 | HISTORY | ข้อมูลย้อนหลังได้รับผลไหม ต้องใช้กฎ ณ วันนั้นหรือวันนี้ | จะทำให้เอกสารเก่าเปลี่ยนตัวเลข (TIME-15) |
| 10 | TEST | จะพิสูจน์ว่าถูกได้อย่างไร | จะไม่มีวันรู้ว่าทำถูกหรือเปล่า |
| 11 | OBSERVE | ถ้าพังหลัง deploy จะรู้ได้อย่างไร ภายในกี่นาที | จะรู้ตอนลูกค้าโทรมา |
| 12 | ROLLBACK | ถ้าพังจะย้อนอย่างไร ข้อมูลที่เขียนไปแล้วทำยังไง | จะติดกับดักตอนตีสอง |
| 13 | DELETE | มีของเก่าที่ต้องลบไหม ใครลบ วันไหน | จะได้ของซ้ำเพิ่มอีกหนึ่ง (SSOT-01) |

**Impact Map ใช้สองครั้ง** ตอนเริ่มคือด่านเข้า ตอนจบคือ checklist ปิดงาน — ทุกช่องที่ตอบว่า "มีผล" ต้องมีของจริงส่งมอบคู่กัน

| ช่อง | ของที่ต้องมีตอนปิดงาน |
|---|---|
| CALLERS | ผู้เรียกทุกตัวถูกอัปเดตหรือยืนยันแล้วว่าไม่กระทบ |
| DATA | migration + แผนย้อนกลับ |
| CONTRACT | เวอร์ชัน/ช่วงอยู่ร่วม + แจ้งฝั่ง client |
| RACE | ตัวกันซ้ำ (unique key / idempotency key) |
| HISTORY | เทสที่ยืนยันว่าเอกสารเก่ายังให้ตัวเลขเดิม |
| TEST | เทสที่ fail ได้จริงถ้าโค้ดผิด |
| OBSERVE | log/metric/alert ที่เพิ่มเข้าไป |
| DELETE | คอมมิตที่ลบของเก่า หรือบรรทัดใน `CONSOLIDATIONS.yaml` |

เขียนลง `docs/impact/<วันที่>-<ชื่องาน>.md` ไม่ใช่ตอบในแชต เพราะแชตหายแต่ไฟล์อยู่

## ด่านความไม่แน่ใจเรื่องธุรกิจ (Ask Gate)

โค้ดผิดแก้ได้ แต่ **กฎธุรกิจที่เดาผิดจะกลายเป็นข้อมูลผิดที่แก้ย้อนหลังไม่ได้** ด่านนี้จึงสำคัญกว่าทุกอย่างในไฟล์นี้

ทุกข้อความที่เกี่ยวกับพฤติกรรมธุรกิจ ต้องติดระดับหลักฐาน:

```
PROD      เห็นจากข้อมูลจริง/พฤติกรรมจริงในระบบที่ใช้งานอยู่     ← เชื่อได้
DB        เห็นจาก schema/SP/ข้อมูลบนฐานข้อมูลจริง
TEST      มีเทสที่ยืนยัน
HISTORY   เห็นจาก git log / ประวัติการแก้
SOURCE    เห็นจากซอร์สโค้ดใน repo เท่านั้น                      ← ยังไม่พอจะพูดว่า "ระบบทำแบบนี้"
ASSUMED   เดา                                                   ← ห้ามส่งงานโดยมีข้อนี้ค้าง
```

**หยุดแล้วถามทันที** เมื่อสิ่งที่ไม่แน่ใจอยู่ในกลุ่มนี้ ไม่ว่าจะเสียเวลาแค่ไหน:

- เงิน ภาษี ส่วนลด ต้นทุน การปัดเศษ
- จำนวนสต็อก การตัดสต็อก การจอง
- สิทธิ์ว่าใครทำอะไรได้
- สถานะและลำดับของ workflow ("ยกเลิกหลังยืนยันแล้วได้ไหม")
- ข้อมูลย้อนหลังและวันที่มีผลบังคับ
- อะไรคือพฤติกรรมที่ "ถูก" เมื่อของเดิมสองที่ให้ผลไม่ตรงกัน

**วิธีถามที่ไม่กินเวลาคนตอบ** — เขาเป็นคนเดียวที่ตอบได้ ดังนั้นห้ามถามทีละข้อเรื่อยๆ

1. รวบถามครั้งเดียว ไม่เกิน 3 ข้อต่อรอบ
2. ทุกคำถาม**เสนอคำตอบที่เชื่อว่าถูกมาด้วย** พร้อมเหตุผลและระดับหลักฐาน ให้ตอบว่า "ใช่/ไม่ใช่" ได้เลย
3. บอกผลกระทบของแต่ละทางเลือกสั้นๆ ว่าถ้าตอบผิดจะเกิดอะไร
4. ระหว่างรอคำตอบ ให้ทำส่วนที่ไม่ขึ้นกับคำตอบนั้นต่อ อย่านั่งรอเฉยๆ

```
❓ ยืนยันส่งสินค้าซ้ำ (กดสองครั้ง) ควรได้อะไร
   ผมเชื่อว่า: ครั้งที่สองต้องถูกปฏิเสธ ไม่ใช่สร้างเอกสารใหม่
   หลักฐาน: DB — มี unique index บน DocNo แต่ SP จับ error แล้ว return 0 (SQL-16)
   ถ้าผมเข้าใจผิด: จะได้เอกสารส่งซ้ำและตัดสต็อกสองรอบ
   ตอบว่า "ใช่" ก็พอครับ
```

ข้อไหนที่ตัดสินใจเดินหน้าโดยยังไม่ได้คำตอบ ต้องบันทึกใน Impact Map ช่อง ASSUMPTIONS และ **แปลงเป็นเทสหนึ่งตัวเสมอ** เพื่อให้วันที่รู้ว่าเดาผิด จะมีจุดเดียวที่ต้องแก้

## Router — งานแบบไหน มองผ่านเลนส์ไหน

อ่านเฉพาะเลนส์ที่ตรงกับงาน อย่าโหลดทั้งแคตตาล็อก ตัวเลขในวงเล็บคือรหัสหมวดใน `nohell/HELL-CATALOG.md`

| งานที่ได้รับ | ลำดับเลนส์ |
|---|---|
| เพิ่ม/แก้ฟีเจอร์ที่**เขียนข้อมูล** | Impact Map → business-rules → ponytail → nohell core → API → CODE → TXN → DATA → SSOT → OBS → TEST |
| แก้หน้าจอ/รายงานที่**อ่านอย่างเดียว** | ponytail → FE → PERF → TIME (ถ้ามีวันที่/เงิน) → ARCH-21 (ปุ่มต้องใช้กฎเดียวกับ command) |
| แก้บั๊ก | archaeology → business-rules (บั๊กหรือกฎที่ตั้งใจ?) → nohell core → หมวดตามอาการ → TEST-14 (ทิ้งเทสกันซ้ำ) |
| "SP ช้า" / งาน performance | archaeology → SQL → DATA → PERF → TEST → SSOT (ถ้าเจอของซ้ำระหว่างทาง) |
| รีแฟกเตอร์ / รวมโค้ด | archaeology → SSOT (วง C) → LEG → TEST-08 characterization → ponytail |
| ต่อระบบภายนอก (SAP/API/webhook) | INT → API → ERR → TXN (idempotency) → OBS → SEC |
| งาน batch / scheduler | JOB → TXN → TIME (cutoff) → OBS → ERR |
| เปลี่ยน schema / migration | Impact Map (เน้น DATA + HISTORY) → DATA → SHIP-05..07 → SSOT-13 → TEST |
| ทำรายงาน / export | FILE → TIME → PERF → SEC-14 (masking) → business-rules (ตัวเลขต้องมาจากแหล่งเดียวกับหน้าจอ) |
| "ทำไมระบบถึงเป็นแบบนี้" | archaeology เท่านั้น ห้ามแก้โค้ดในรอบนั้น |
| ตรวจสุขภาพทั้ง repo | `/nohell-dig` (ขุดประวัติ) → `detect-sqlserver.sql` (ภาพปัจจุบันฝั่ง DB) |

**เลนส์ที่ติดมาทุกงานโดยไม่ต้องเลือก:** ponytail (ต้องเขียนไหม) · nohell กฎแกน 12 ข้อ · Ask Gate · Impact Map

## เงื่อนไขหยุด (STOP)

หยุดทันที รายงาน แล้วรอคำตอบ เมื่อเจอข้อใดข้อหนึ่ง:

1. กฎธุรกิจที่ยังอยู่ระดับ `ASSUMED` และเกี่ยวกับเงิน/สต็อก/สิทธิ์/ข้อมูลย้อนหลัง
2. เจอ logic เดียวกันมากกว่าหนึ่งที่ แล้ว **ให้ผลไม่ตรงกัน** — ต้องรู้ก่อนว่าอันไหนถูก ห้ามเลือกเอง
3. งานนี้ต้องแตะข้อมูลที่มีอยู่แล้วใน production
4. สิ่งที่ผู้ใช้ขอ ขัดกับสิ่งที่โค้ด/ข้อมูลบอกว่าระบบทำอยู่จริง
5. ขอบเขตงานโตขึ้นเกินสองเท่าจากที่ประเมินไว้ตอนเริ่ม
6. ต้องลบหรือเปลี่ยนของที่มีคนอื่น/ระบบอื่นใช้อยู่ โดยยังไม่รู้ว่าใคร
7. ทางแก้ที่ง่ายที่สุดคือ "เพิ่ม flag/พารามิเตอร์" ให้ของเดิมที่ใหญ่อยู่แล้ว (SQL-01, SSOT-03)

การหยุดถามไม่ใช่ความล้มเหลว — เดินหน้าผิดทาง 2 ชั่วโมงแพงกว่าถามหนึ่งคำถาม

## ต่องานเดียว ห้ามทำเกินขอบเขต

- แก้เรื่องเดียวต่อหนึ่ง PR — เจอนรกระหว่างทางให้ **จดใส่ ledger** ไม่ใช่แก้เลย (ยกเว้น P1 ที่ทำให้ข้อมูลผิด ให้หยุดแล้วรายงาน)
- ห้ามแตะไฟล์ที่ไม่อยู่ใน Impact Map โดยไม่บอก
- ถ้าต้องเปลี่ยน Impact Map ระหว่างทาง ให้เขียนเพิ่มลงไฟล์เดิม อย่าเปลี่ยนเงียบๆ

## ส่งงานอย่างไรให้คนที่ลืมไปแล้วอ่านรู้เรื่อง

รายงานปิดงานยาวไม่เกินนี้:

```
ทำอะไร:        <ประโยคเดียวแบบที่ผู้ใช้เข้าใจ>
แตะอะไรบ้าง:   <ไฟล์/SP ตามจริง>
กฎธุรกิจที่ยึด: <ข้อความ + ระดับหลักฐาน + ใครยืนยัน>
ที่เดาไว้:      <ข้อสมมติที่ยังไม่ได้คำตอบ + เทสที่เฝ้ามันอยู่>
พิสูจน์ยังไง:   <คำสั่งที่รันแล้วเห็นผลจริง ไม่ใช่ "เทสผ่าน">
ถ้าพังจะรู้จาก: <log/metric ตัวไหน>
ย้อนยังไง:     <คำสั่ง/ขั้นตอน>
ยังไม่ได้ทำ:    <ของที่เหลือ + อยู่ใน ledger บรรทัดไหน>
```

**"เทสผ่าน" ไม่เท่ากับ "ธุรกิจถูก"** — เทสยืนยันได้แค่ว่าโค้ดทำตามที่เทสเขียนไว้ ถ้าเทสเขียนจากความเข้าใจที่ผิด มันจะยืนยันความผิดนั้นอย่างมั่นใจ ตัวตัดสินสุดท้ายคือข้อมูลจริงและคนที่รู้กระบวนการ
