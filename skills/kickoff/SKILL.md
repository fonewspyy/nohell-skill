# kickoff — agent เป็นคนพาเดิน ไม่ใช่คนรอสั่ง

โปรเจกต์ใหม่พังเพราะสิ่งที่ **ไม่มีใครพูดถึง** ไม่ใช่เพราะสิ่งที่ตกลงกันแล้ว
คนที่ทำงานคนเดียวมีจุดบอดตรงนี้มากที่สุด เพราะไม่มีใครถามคำถามที่เขาลืมถามตัวเอง

**หน้าที่ของ agent ในโหมดนี้: เป็นคนที่ถามคำถามที่เขาลืม** ไม่ใช่รอให้เขานึกออกเอง

---

## กฎของโหมดนี้

1. **อย่ารอคำสั่ง** ผู้ใช้บอกแค่ "อยากทำ X" ก็เริ่มพาเดินได้เลย ไม่ต้องถามว่า "อยากให้ช่วยอะไร"
2. **อย่าเขียนโค้ดในสองเฟสแรก** เฟส 0-1 เป็นการหาความจริงล้วนๆ
3. **ถามเป็นชุด ไม่ถามทีละข้อ** สูงสุด 7 ข้อต่อรอบ และทุกข้อ**ต้องเสนอคำตอบที่เชื่อว่าถูกมาด้วย** ให้ตอบ "ใช่/ไม่" ได้
4. **บอกเสมอว่าตอนนี้อยู่เฟสไหน เหลืออีกกี่เฟส** คนที่ทำงานคนเดียวจะรู้สึกว่าคุมสถานการณ์ได้
5. **ทุกเฟสจบด้วยไฟล์** ไม่ใช่จบด้วยข้อความในแชต แชตหาย ไฟล์อยู่
6. **หยุดเมื่อคำตอบสำคัญยังไม่มา** ห้ามเดาเรื่องเงิน สต็อก สิทธิ์ หรือข้อมูลย้อนหลัง

**ทำไมต้องถามก่อน:** งานวิจัย ClarifyGPT วัดได้ว่าการให้โมเดลถามคำถามชี้แจงก่อนเขียนโค้ด ยก pass@1 ของ GPT-4 บน MBPP-sanitized จาก 70.96% เป็น 80.80% การถามไม่ใช่การถ่วงเวลา มันคือส่วนหนึ่งของงาน

## เฟส 0 — เข้าใจว่าจะสร้างอะไร (ห้ามเขียนโค้ด)

เปิดด้วยประโยคเดียวสรุปว่าเข้าใจอะไร แล้วยิงคำถามชุดแรก

**คำถามที่ต้องได้คำตอบ เรียงตามความสำคัญ**

| # | คำถาม | ทำไมถามก่อน |
|---|---|---|
| 1 | ใครใช้ ใช้ตอนไหน อยู่ในสภาพแวดล้อมแบบไหน | คนคุมสต็อกยืนถือเครื่องสแกนในคลัง กับคนนั่งออฟฟิศ ออกแบบคนละแบบสิ้นเชิง |
| 2 | ถ้าไม่มีระบบนี้ วันนี้เขาทำยังไง | ของเดิมคือ spec ที่แม่นที่สุด และมักเป็น Excel ที่คุณต้องแทน |
| 3 | อะไรคือ "สำเร็จ" ที่วัดได้ | ถ้าตอบไม่ได้ แปลว่ายังไม่รู้ว่าจะสร้างอะไร |
| 4 | ข้อมูลอะไรที่ผิดไม่ได้เด็ดขาด | ตรงนี้กำหนดว่าต้องลงทุน constraint/เทสตรงไหน |
| 5 | ระบบนี้ต้องคุยกับระบบไหนบ้าง | integration ที่โผล่ทีหลังคือสิ่งที่ทำให้ต้องรื้อ |
| 6 | อะไรที่ **ไม่** ต้องทำในรอบนี้ | ขอบเขตที่ไม่ได้เขียนไว้จะโตเอง |
| 7 | ถ้าระบบล่มหนึ่งวัน เกิดอะไรขึ้นกับธุรกิจ | กำหนดว่าต้องลงทุนกับ resilience แค่ไหน |

**รูปแบบการถามที่ไม่กินเวลาคนตอบ**

```
❓ ข้อ 3: อะไรคือ "สำเร็จ" ของระบบนี้
   ผมเดาว่า: ลดเวลาปิดยอดสิ้นวันจาก 2 ชม. เหลือ 15 นาที
   เพราะ: คุณพูดถึงการนั่งกระทบยอด Excel ตอนเย็นสองรอบ
   ถ้าผมเดาผิด: ผมจะออกแบบหน้าจอผิดกลุ่มผู้ใช้ทั้งหมด
   ตอบว่า "ใช่" ก็พอครับ
```

**ระหว่างรอคำตอบ ให้ทำต่อ** — สำรวจของเดิม อ่านโครงสร้างข้อมูล ร่างคำถามชุดถัดไป ห้ามนั่งรอเฉยๆ

**ส่งมอบเฟส 0:** `docs/kickoff/00-understanding.md` — สิ่งที่เข้าใจ, สิ่งที่ยังไม่รู้, ข้อสมมติที่จะเดินต่อ

## เฟส 1 — หากฎธุรกิจให้เจอก่อนออกแบบ

เฟสนี้คือเฟสที่คนข้ามบ่อยที่สุด และเป็นเฟสที่ทำให้ต้องรื้อทีหลัง

ไล่ตาม [business-rules](../business-rules/SKILL.md) — สิ่งที่ต้องได้:

- **รายการ fact** ที่ระบบนี้เป็นเจ้าของ และ fact ที่ไปยืมคนอื่นมา
- **ตารางสถานะ** ของเอกสาร/รายการหลัก (จาก → เหตุการณ์ → ไป → ใครทำได้ → ผลข้างเคียง → ย้อนได้ไหม)
- **กฎที่ผูกกับเวลา** อะไรบ้างที่เปลี่ยนตามวันที่ และเอกสารเก่าต้องใช้ค่าเดิม
- **กฎที่ผูกกับสิทธิ์** ใครทำอะไรได้ และตัดสินที่ไหน
- **เคสที่ธุรกิจปฏิเสธ** (เครดิตเกิน ของไม่พอ เอกสารซ้ำ) พร้อมว่าผู้ใช้ควรทำอะไรต่อ

ถ้าเป็นระบบที่มีของเดิมอยู่ ให้ทำ [archaeology](../archaeology/SKILL.md) ตรงนี้ และติดระดับหลักฐานทุกข้อ

**ส่งมอบ:** `docs/kickoff/01-business-rules.md` + ตารางสถานะ

## เฟส 2 — เสนอทางเลือก ไม่ใช่เสนอคำตอบเดียว

ตรงนี้ agent เป็นฝ่ายเสนอ ผู้ใช้เป็นฝ่ายเลือก

เสนอ **2-3 ทาง** ทุกครั้ง แต่ละทางบอก: ได้อะไร เสียอะไร พังตรงไหนก่อน และเหมาะเมื่อไหร่ พร้อม**ระบุว่าแนะนำอันไหนและเพราะอะไร** — เสนอเฉยๆ โดยไม่แนะนำคือการโยนภาระกลับ

หัวข้อที่ต้องเสนอทางเลือกเสมอ:
- เก็บข้อมูลยังไง (โครงตาราง แหล่งความจริง)
- แยกเป็นกี่ส่วน และอะไรคุยกับอะไร
- อะไร sync อะไร async
- ทำเองหรือใช้ของที่มี
- จะทำอะไรก่อนใน 2 สัปดาห์แรก

**ทุกข้อที่ตัดสินใจแล้วและย้อนยาก → เขียน ADR หนึ่งหน้าใน `docs/adr/`** (ตัดสินใจอะไร ทางเลือกที่ตัดทิ้ง เหตุผล และเงื่อนไขที่จะกลับมาทบทวน)

**ส่งมอบ:** `docs/kickoff/02-options.md` + ADR ของสิ่งที่เลือกแล้ว

## เฟส 3 — Walking skeleton ก่อนเสมอ

**ห้ามสร้างเป็นชั้นๆ (DB ก่อน แล้ว API แล้ว UI)** เพราะจะรู้ว่าประกอบไม่ได้ตอนท้าย

สร้างเส้นบางที่สุดที่วิ่งได้ตั้งแต่ต้นจนจบก่อน: หน้าจอ → API → ธุรกิจ → ฐานข้อมูล → กลับมาแสดงผล แม้จะทำได้แค่เคสเดียวก็ตาม

พร้อมกับ skeleton ต้องมีของพวกนี้ตั้งแต่วันแรก ไม่ใช่ค่อยเติม:
- migration ที่รันซ้ำได้
- log ที่มี correlation id
- เทสหนึ่งตัวที่ fail ได้จริงถ้าโค้ดผิด
- คำสั่งเดียวที่ทำให้คนใหม่รันระบบขึ้นได้
- วิธี deploy และวิธีย้อนกลับ

**เกณฑ์ผ่านเฟสนี้:** ทำงานจริงได้หนึ่งเคส และมีคนอื่นรันตามได้จากเอกสาร

## เฟส 4 — วางโครง repo ให้ agent ไม่หลุด

สิ่งที่ต้องมีตั้งแต่วันแรก:

```
AGENTS.md                    ← กติกาสำหรับ agent (สั้น คม)
CONSOLIDATIONS.yaml          ← ทะเบียนวง C (เริ่มว่างก็ได้)
docs/
  kickoff/                   ← ผลของเฟส 0-2
  adr/                       ← การตัดสินใจที่ย้อนยาก
  impact/                    ← Impact Map ต่องาน
```

**AGENTS.md ต้องใส่**: คำสั่ง build/test/lint ที่รันได้จริง · โครงโฟลเดอร์ · กฎห้าม (เช่น ห้ามแก้ไฟล์เทสในคอมมิตที่แก้บั๊กโดยไม่ระบุเหตุผล) · business rule สำคัญที่ไม่มีในโค้ด · วิธีพิสูจน์ว่างานเสร็จ

**AGENTS.md ห้ามใส่**: ทุกอย่างในโลก ไฟล์ที่ยาวเกินทำให้ agent สนใจงานจริงน้อยลง รายละเอียดเฉพาะทางให้ย้ายไป skill ที่โหลดเมื่อต้องใช้

## เฟส 5 — ส่งมอบและตั้งจังหวะ

- แผน 2 สัปดาห์แรกที่มีของส่งมอบจริงทุกสัปดาห์
- รายการสิ่งที่ยังไม่รู้ + จะรู้ได้เมื่อไหร่
- ตัวเลขตั้งต้นของ fitness function (จำนวนไฟล์/SP/บรรทัด) ไว้เทียบว่าแย่ลงไหม

## เมื่อผู้ใช้ข้ามขั้น

เขาจะพูดว่า "เอาเลย ไม่ต้องถามเยอะ" — ซึ่งเข้าใจได้ เพราะเขารีบและทำงานคนเดียว

**อย่าเถียง ให้ทำแบบนี้แทน:**

1. ทำตามที่เขาขอ
2. บอกสั้นๆ ว่ากำลังเดาอะไรอยู่ และถ้าเดาผิดจะต้องรื้ออะไร
3. บันทึกข้อสมมติลงไฟล์ และทำให้แต่ละข้อมีเทสเฝ้า

```
เริ่มให้เลยครับ ระหว่างทางผมเดาสามข้อนี้ไว้ก่อน:
 · หนึ่งเอกสารมีได้หลายรายการ (ถ้าผิด ต้องรื้อโครงตาราง)
 · ยกเลิกหลังยืนยันแล้วไม่ได้ (ถ้าผิด ต้องเพิ่มเอกสารกลับรายการ)
 · ราคาใช้ ณ วันที่เอกสาร ไม่ใช่วันนี้ (ถ้าผิด ตัวเลขย้อนหลังจะเพี้ยน)
บอกได้ทุกเมื่อถ้าข้อไหนผิด
```

ข้อที่สามคือข้อที่ถ้าเดาผิดแล้วแก้ย้อนหลังไม่ได้ — ถ้าเรื่องประเภทนี้ยังไม่ชัด **ให้หยุดถามจริงๆ** ไม่ใช่เดาต่อ
