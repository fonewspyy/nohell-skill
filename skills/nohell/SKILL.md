# nohell — อย่าสร้างนรกใส่คนที่มาทีหลัง

ponytail ถามว่า *ต้องเขียนไหม*
nohell ถามว่า *ถ้าเขียน มันจะกลายเป็นนรกไหม*

ทั้งคู่ไม่ทับกัน: ponytail ลดปริมาณ, nohell ลดต้นทุนการอยู่กับมันอีก 5 ปี

## บันไดตัดสิน (รันหลัง ponytail ladder, ก่อนลงมือเขียน)

```
1. logic นี้มีอยู่แล้วที่อื่นไหม?      → มี: เรียกใช้ / รวมเป็นที่เดียว  (DUP)
2. ถ้าพัง จะรู้ได้ยังไง?              → ไม่รู้: ใส่ log/metric/alert ก่อน  (OBS)
3. ถ้ารันซ้ำ 2 รอบ ผลเหมือนเดิมไหม?   → ไม่: ทำให้ idempotent  (TXN/JOB)
4. คนอื่นอ่าน 6 เดือนหลัง จะเดาถูกไหม? → ไม่: ตั้งชื่อใหม่ / เขียน ADR  (CODE/LEGACY)
5. ข้อมูลผิดเงียบๆ ได้ไหม?            → ได้: ใส่ constraint/validation ที่ขอบ  (DATA/API)
6. ใครเป็นเจ้าของก้อนนี้?             → ไม่มี: อย่าเพิ่งสร้าง  (TEAM)
7. ลบทิ้งวันไหน ใครลบ?               → ไม่มีคำตอบ: ใส่ deprecation plan  (LEGACY)
```

ผ่านครบ 7 ข้อ ค่อยเขียน ตกข้อไหน แก้ข้อนั้นก่อน ไม่ใช่เขียนต่อแล้วค่อยว่ากัน

## วงจร C — หัวใจของ SSOT

รวมโค้ดไม่ใช่การ **สร้าง** แต่คือการ **ลบ** ตัวส่งมอบของงาน consolidation คือ A กับ B ที่หายไป ไม่ใช่ C ที่โผล่มา

สร้าง C แล้วไม่ลบ A/B = เดิมมีสองที่ ตอนนี้มีสามที่ แล้วอันที่สามมักเป็นอันที่ไม่มีใครใช้จริง นี่คือวิธีที่ระบบโตขึ้นเรื่อยๆ ทั้งที่ทุกคนตั้งใจจะทำให้มันเล็กลง

```
C0  รู้ว่า A กับ B ทำเรื่องเดียวกัน                     ← ยังไม่เริ่ม
C1  พิสูจน์แล้วว่า A ≡ B จริง (ไม่ใช่แค่หน้าตาเหมือน)   ← ด่านกันไม่ให้สร้าง God SP ตัวใหม่
C2  C มีอยู่ + A,B ยังทำงานเดิม                        ← อันตรายที่สุด: มี 3 ที่ ต้องจับเวลา
C3  A,B เหลือเป็นเปลือกที่เรียก C (ไม่มี logic เหลือ)
C4  ผู้เรียกทั้งหมดย้ายไป C แล้ว (ตัวนับผู้เรียก A,B = 0)
C5  ลบ A และ B                                        ← ตรงนี้เท่านั้นที่เรียกว่าเสร็จ
C6  ปิดประตู: มีกฎตรวจไม่ให้มีคนเขียน A ตัวใหม่
```

**กติกาที่บังคับได้**

- ห้าม merge PR ที่พา C เข้าสถานะ C2 โดยไม่มีบรรทัดใน `CONSOLIDATIONS.yaml` ที่ระบุ A, B, เจ้าของ, และวันลบ
- วง C ที่เลยวันลบ = P1 ต้องเลือกอย่างใดอย่างหนึ่ง: ลบให้จบ หรือ **ยกเลิกแล้วลบ C ทิ้ง** ห้ามปล่อยค้าง
- งาน consolidation ต้องจบด้วยจำนวนบรรทัด/จำนวน SP **สุทธิติดลบ** ถ้าบวกต้องอธิบายว่าทำไม
- ห้ามผ่านด่าน C1 ด้วยความรู้สึก ต้องมีหลักฐาน: เทียบผลบนข้อมูลจริง (shadow run), decision table, หรือ characterization test
- ถ้า A ≢ B ให้ **แยกให้ขาด** อย่ารวมด้วย flag — `@ActionType` คือหน้าตาของการรวมสิ่งที่ไม่ควรรวม
- SSOT ของ logic ไม่นับ ถ้าข้อมูลยังอยู่สองที่ แผนรวมตารางต้องมาคู่กัน

**ตัวเลขที่ต้องดู ไม่ใช่ความรู้สึก:** จำนวนวง C ที่เปิดอยู่ · อายุของวงที่เก่าที่สุด · จำนวนผู้เรียกที่เหลือของแต่ละ A,B

## กฎแกน 12 ข้อ (always-on, ห้ามละเมิดโดยไม่มี ADR)

1. **Single source of truth = สร้าง C แล้ว *ลบ* A และ B** — rule หนึ่งเรื่องอยู่ได้ที่เดียว และงานยังไม่จบจนกว่าของเดิมจะหายไป ดูหมวด SSOT
2. **ห้ามสร้างของใหม่ทับของเดิม** — ก่อนสร้าง SP/service/helper ใหม่ ต้องค้นของเดิมก่อนเสมอ แล้วบอกว่าทำไมของเดิมใช้ไม่ได้
3. **ขอบเขตต้องตรวจ** — input จากภายนอกทุกทาง (HTTP, file, queue, SP param) validate ที่ขอบก่อนเข้าระบบเสมอ
4. **ห้ามกลืน error** — catch ต้องจบด้วย จัดการ / แปลง / โยนต่อ อย่างใดอย่างหนึ่ง ห้าม `catch {}` ห้าม `return null` เงียบๆ
5. **ทำซ้ำได้เสมอ** — ทุก write path ต้อง idempotent หรือมี key กันซ้ำ
6. **ห้ามพังเงียบ** — พังแล้วต้องมี log + correlation id + สัญญาณให้คนรู้ ข้อมูลผิดเงียบแย่กว่าระบบล่ม
7. **ห้าม magic** — ห้าม hard-code เลข/สถานะ/path/ID ที่มีความหมายทางธุรกิจ ต้องมีชื่อและที่อยู่
8. **schema คือสัญญา** — ห้ามเปลี่ยน column/field/response shape แบบ breaking โดยไม่มี version + backward-compatible window
9. **แก้ prod ต้องผ่าน repo** — DDL, SP, config ทุกอย่างมี source of truth ใน git ห้ามแก้ผ่าน SSMS/RDP แล้วจบ
10. **แตะ legacy ต้องมีตาข่าย** — ก่อนรีแฟกเตอร์โค้ดเก่า ต้องมี characterization test หรือ production data oracle ก่อน
11. **ทุกก้อนมีเจ้าของ** — โค้ดที่ไม่มีชื่อคนดูแล = โค้ดที่กำลังจะเป็นนรก
12. **หนี้ต้องขึ้นทะเบียน** — ทางลัดทำได้ แต่ต้องทิ้ง `// nohell-debt: <เหตุผล> <วันหมดอายุ>` ไว้เสมอ

## วิธีใช้

| งาน | ทำอะไร |
| --- | --- |
| กำลังเขียนโค้ดใหม่ | ใช้บันได 7 ขั้น + กฎแกน 12 ข้อ ไม่ต้องโหลดแคตตาล็อก |
| รีวิว diff | โหลด `HELL-CATALOG.md` เฉพาะหมวดที่ diff แตะ **แล้วกรองด้วยช่อง `ใช้กับ` ให้เหลือเฉพาะ stack ของโปรเจกต์** รายงานเป็น `ID — ไฟล์:บรรทัด — กฎที่ละเมิด — แก้ยังไง` |
| audit ทั้ง repo | ไล่ `hell-rules.yaml` ทีละข้อ (ข้อที่ตรวจอัตโนมัติได้) แล้วค่อยไล่ manual เฉพาะ P1 |
| audit ฐานข้อมูล | รัน `detect-sqlserver.sql` แล้ว map ผลกลับเป็น ID |
| CI gate | `hell-rules.yaml` → เลือก severity ที่จะ block (แนะนำ: P1 = block, P2 = warn) |

## กติกาการรายงาน

- อ้าง ID เสมอ (`SQL-02`) ห้ามบ่นลอยๆ
- หนึ่งข้อ = หนึ่งบรรทัด: `ID | ไฟล์:บรรทัด | สิ่งที่เห็น | แก้เป็น`
- ห้ามเสนอ rewrite ทั้งไฟล์เมื่อแก้ 3 บรรทัดจบ (ponytail rule ยังใช้อยู่)
- ถ้าละเมิดโดยตั้งใจ ต้องออก ADR ไม่ใช่เถียงใน PR
- ห้ามรายงานข้อที่ไม่ได้อยู่ใน diff/scope ที่ขอ ยกเว้น P1 ที่เจอระหว่างทาง

## โครงสร้างไฟล์

```
nohell/
├── SKILL.md              ← ไฟล์นี้ (โหลดตลอด, ~3–4k tokens)
├── HELL-CATALOG.md       ← 490 ข้อ 31 หมวด (โหลดตามหมวดเวลา audit)
├── hell-rules.yaml       ← ชุดที่ตรวจอัตโนมัติได้ + คำสั่งตรวจ
├── detect-sqlserver.sql  ← สคริปต์สแกน SQL Server (God SP, dup logic, schema smell)
└── CONSOLIDATIONS.example.yaml ← เทมเพลตทะเบียนวง C (คัดลอกไปไว้ที่ราก repo เป้าหมาย)
```

## อ่านเฉพาะที่เกี่ยวกับ stack ตัวเอง

ทุกข้อมีช่อง **ใช้กับ** บอกเงื่อนไขที่ทำให้มันเกี่ยวกับคุณ ก่อน audit ให้ตอบสองคำถามนี้ก่อน
แล้วกรองแคตตาล็อกทิ้งตั้งแต่ต้น อย่าไล่อ่านข้อที่ใช้กับ stack ตัวเองไม่ได้

```
ฐานข้อมูลอะไร        ไม่มี / RDBMS ใดก็ได้ / SQL Server
ตรรกะอยู่ที่ไหน       ในแอป / ใน stored procedure
หน้าบ้านเป็นเว็บไหม   ใช่ / ไม่ใช่
ภาษาอะไร            TS-JS / .NET / อื่น
มีแอปมือถือไหม       มี / ไม่มี
มีโมเดล ML ไหม       มี / ไม่มี
เก็บข้อมูลส่วนบุคคลไหม เก็บ / ไม่เก็บ
```

| ใช้กับ | จำนวน | อ่านเมื่อ |
| --- | --- | --- |
| `ทุกที่` | 363 | เสมอ ไม่ว่า stack ไหน |
| `RDBMS` | 50 | มีฐานข้อมูลเชิงสัมพันธ์ |
| `SQL Server` | 14 | ใช้ T-SQL |
| `มี SP` | 7 | ตรรกะอยู่ใน stored procedure |
| `เว็บ` | 17 | หน้าบ้านเป็นเว็บ |
| `TS/JS` | 2 | เขียน TypeScript หรือ JavaScript |
| `.NET` | 1 | เขียน C# หรือ .NET |
| `mobile` | 13 | มีแอปมือถือที่ต้องทำงานตอนไม่มีเน็ต |
| `ML` | 13 | มีโมเดลที่ตัดสินใจแทนคนในระบบจริง |
| `PII` | 10 | ระบบเก็บข้อมูลส่วนบุคคลของคนจริง |

ร้าน Go + PostgreSQL ที่ไม่มี SP อ่าน 413 จาก 490 ข้อ · ร้าน .NET + SQL Server ที่ทำงานผ่าน SP อ่านครบเกือบทั้งหมด

## รหัสหมวด

`ARCH` สถาปัตยกรรม · `SQL` stored procedure/T-SQL · `DATA` schema · `TXN` transaction/concurrency ·
`API` สัญญา API · `CODE` โครงสร้างโค้ด · `CACHE` state/cache · `ERR` error handling ·
`OBS` log/observability · `SEC` security · `CFG` config/secret · `SHIP` build/deploy/migration ·
`TEST` การทดสอบ · `PERF` performance · `INT` integration/messaging · `JOB` batch/scheduler ·
`TIME` วันเวลา/เงิน/ภาษา · `FILE` ไฟล์/รายงาน · `SSOT` การรวมและการลบของเดิม · `LEG` legacy/refactor · `TEAM` คน/กระบวนการ ·
`AI` โค้ดที่ agent สร้าง · `FE` frontend · `TYPE` ชนิดข้อมูล/การแปลงโดยปริยาย · `AGG` การรวมยอด · `MEAS` การวัดที่เชื่อไม่ได้ ·
`REG` ทะเบียนที่ต้องอัปเดตพร้อมกัน · `TOOL` ค่าเริ่มต้นของเครื่องมือ ·
`MOBILE` แอปมือถือที่ทำงานตอนไม่มีเน็ต · `ML` โมเดลที่ผิดโดยไม่มีใครเห็น ·
`PDPA` ข้อมูลส่วนบุคคลที่ถือไว้โดยไม่มีสิทธิ์

ระดับ: **P1** = ทำให้ข้อมูลผิด/ระบบล่ม/ข้อมูลรั่ว · **P2** = ทำให้แก้ไม่ไหวในระยะยาว · **P3** = ทำให้ชีวิตแย่ลง
