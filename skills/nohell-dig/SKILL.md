# nohell-dig — โบราณคดีของ repo

คุณคือนักสืบ ไม่ใช่ช่างซ่อม งานนี้ **ห้ามแก้โค้ดแม้แต่บรรทัดเดียว**

เป้าหมาย: หาว่าตลอด **8 เดือนที่ผ่านมา** อะไรที่ทำให้เสียเวลาซ้ำแล้วซ้ำอีก โดยดูจากสิ่งที่ *เกิดขึ้นจริง* ในประวัติ ไม่ใช่จากสิ่งที่โค้ดปัจจุบันดูไม่สวย

หลักการเดียวที่ต้องจำ: **โค้ดปัจจุบันบอกว่าตอนนี้เป็นยังไง แต่ประวัติบอกว่าอะไรทำให้เจ็บ** ไฟล์ที่หน้าตาแย่ที่สุดมักไม่ใช่ไฟล์ที่กัดคุณบ่อยที่สุด ให้เชื่อข้อมูล ไม่ใช่ความรู้สึก

---

## กฎเหล็ก

1. **อ่านอย่างเดียว** ห้าม edit ห้าม commit ห้ามรัน migration ห้ามแตะฐานข้อมูลที่เขียนได้
2. **ทุกข้อสรุปต้องมีหลักฐาน** — commit hash, ไฟล์:บรรทัด, หรือตัวเลขจากคำสั่งที่รันจริง ข้อไหนไม่มีหลักฐานให้เขียนว่า "ไม่พบหลักฐาน" ห้ามเติมให้ครบ ห้ามเดา
3. **ข้อมูลก่อน อ่านทีหลัง** เฟส 1-2 ใช้ `git`/สคริปต์เท่านั้น ห้ามเปิดไฟล์ซอร์สเลย จนกว่าจะรู้ว่าไฟล์ไหนคุ้มที่จะเปิด
4. **อย่าเปิดไฟล์ทั้งไฟล์** เมื่อถึงเฟส 3 ให้อ่าน **diff ของคอมมิตที่แก้บั๊ก** เป็นหลัก เพราะ diff บอกว่า *พังยังไง* ส่วนตัวไฟล์บอกแค่ว่าตอนนี้เป็นยังไง
5. **เขียนผลลงไฟล์ทุกจบเฟส** ที่ `.nohell/` ถ้า context ถูกบีบ ให้กลับมาอ่านไฟล์ตัวเองต่อ ห้ามเริ่มใหม่
6. **ห้ามเสนอ rewrite** ทุกข้อเสนอต้องเป็นการเปลี่ยนที่ทำได้ใน PR เดียว
7. **แยกคนกับ agent** ถ้าประวัติมีคอมมิตที่ AI สร้าง ให้แยกสถิติสองชุด เพราะรูปแบบความพังต่างกัน
8. **จำนวนไม่ใช่เป้า** รายงานที่มี 8 เรื่องที่มีหลักฐานแน่น ดีกว่า 40 เรื่องที่เดาครึ่งหนึ่ง

## เฟส 0 — ถามหนึ่งคำถาม แล้วเริ่มเลย

ถามผู้ใช้ข้อเดียวนี้ แล้ว **ไม่ต้องรอคำตอบ** เริ่มเฟส 1 ทันที:

> "ก่อนผมขุด ช่วยพิมพ์จากความทรงจำ 5 เรื่องที่คุณคิดว่ากินเวลาคุณมากที่สุดใน 8 เดือนนี้ ไม่ต้องเรียงลำดับ — ผมจะเอาไปเทียบกับสิ่งที่ข้อมูลบอกตอนจบ"

ช่องว่างระหว่าง "สิ่งที่จำได้" กับ "สิ่งที่ข้อมูลบอก" คือผลลัพธ์ที่มีค่าที่สุดของงานนี้ เรื่องที่กัดบ่อยแต่เล็กจนไม่ติดความทรงจำ มักเป็นเรื่องที่คุ้มแก้ที่สุด

## เฟส 1 — เก็บข้อมูลดิบ (git เท่านั้น)

```bash
mkdir -p .nohell/raw .nohell/out
SINCE="8 months ago"

git log --since="$SINCE" --numstat --date=short \
    --pretty=format:'::%H|%ad|%an|%s' > .nohell/raw/numstat.txt

git log --since="$SINCE" --oneline --grep='^Revert' > .nohell/raw/reverts.txt

git log --since="$SINCE" --date=format:'%u %H' \
    --pretty=format:'%h|%ad|%an|%s' > .nohell/raw/when.txt

git log --since="$SINCE" --pretty=format:'%s' | sort | uniq -c | sort -rn \
    > .nohell/raw/subjects.txt
```

จากนั้นเขียนสคริปต์วิเคราะห์ `.nohell/mine.py` ที่อ่าน `numstat.txt` แล้วออกตารางเหล่านี้ลง `.nohell/out/` (เขียนเองได้ตามสะดวก ขอแค่ผลลัพธ์ครบ):

| ตาราง | คืออะไร | บอกอะไร |
|---|---|---|
| `churn.csv` | ไฟล์ + จำนวนคอมมิต + บรรทัดเพิ่ม/ลบ | ที่ที่งานกระจุก |
| `fix-density.csv` | สัดส่วนคอมมิตที่เป็นการแก้ ต่อคอมมิตทั้งหมด ต่อไฟล์ | ที่ที่พังบ่อย — **ตัวชี้ที่สำคัญที่สุด** |
| `refix.csv` | ไฟล์ที่ถูกแก้ซ้ำภายใน 14 วันหลังแก้ครั้งก่อน | แก้ไม่ตรงต้นเหตุ (ERR/AI-12) |
| `cochange.csv` | คู่ไฟล์ที่เปลี่ยนพร้อมกัน ≥ 5 ครั้ง และอยู่คนละโฟลเดอร์ | coupling ที่ซ่อนอยู่ / logic ซ้ำ (ARCH-14, SQL-02, SSOT) |
| `ownership.csv` | ผู้แก้ล่าสุด + จำนวนคนที่เคยแตะ + วันที่แตะล่าสุด | bus factor / ของกำพร้า (TEAM-01, LEG-10) |
| `sprawl.csv` | จำนวนไฟล์ `.sql` และบรรทัดรวม แยกตามเดือน | เส้นโค้งการบวม (LEG-15) |
| `firefight.csv` | คอมมิตที่เป็นการแก้ นอกเวลาทำการ / ศุกร์เย็น / เสาร์อาทิตย์ | ของที่พังตอนไม่มีคนเฝ้า (SHIP-12) |

คำที่ใช้จับคอมมิตประเภทแก้ (ทั้งไทยและอังกฤษ):
`fix|bug|hotfix|patch|revert|urgent|temp|workaround|แก้|พัง|ด่วน|ผิด|ตกหล่น|ไม่ขึ้น|ค้าง`

**เพิ่มเติมที่มักได้ผลดี**

```bash
# คอมเมนต์ที่บอกว่าเคยเจ็บมาก่อน
grep -rn -i -E "ห้ามแก้|ห้ามลบ|อย่าแตะ|workaround|hack|temp fix|ชั่วคราว|TODO|FIXME" \
    --include="*.sql" --include="*.ts" --include="*.tsx" --include="*.cs" . \
    > .nohell/raw/scars.txt

# อายุของแผลเป็นแต่ละอัน (ใครใส่ไว้ เมื่อไหร่)
git log -S "ห้ามแก้" --oneline --since="$SINCE"
```

จบเฟส เขียน `.nohell/out/phase1.md` สรุปตัวเลขระดับบน: จำนวนคอมมิต, สัดส่วนคอมมิตที่เป็นการแก้, จำนวน revert, จำนวนไฟล์ที่แตะ

## เฟส 2 — จัดอันดับจุดร้อน แล้วหยุดรายงาน

ให้คะแนนแต่ละไฟล์:

```
hotspot = (จำนวนคอมมิตที่เป็นการแก้)
        × (1 + จำนวนครั้งที่ถูกแก้ซ้ำใน 14 วัน)
        × (น้ำหนักความใหม่: 90 วันล่าสุด = 2.0, 91-180 = 1.3, เก่ากว่านั้น = 1.0)
```

ไฟล์ที่ churn สูงแต่ fix ต่ำ **ไม่ใช่** จุดร้อน — นั่นคือไฟล์ที่ทำงานอยู่ตามปกติ อย่าไปยุ่งกับมัน

**หยุดตรงนี้** แล้วรายงานให้ผู้ใช้ดู: 20 อันดับแรก + 10 คู่ co-change ที่แรงที่สุด + 5 บรรทัดจาก `subjects.txt` ที่ซ้ำมากที่สุด แล้วถามว่า "จะให้ขุดลึกทั้ง 20 หรือตัดเหลือกี่ตัว" เพราะเฟส 3 แพงกว่าเฟส 1-2 หลายเท่า

## เฟส 3 — ขุดลึกเฉพาะจุดร้อนที่ได้รับอนุมัติ

ต่อหนึ่งไฟล์ ทำตามนี้:

```bash
git log --since="$SINCE" --follow -p --pretty=format:'::%H|%ad|%an|%s' -- <ไฟล์> \
  | head -c 200000
```

อ่าน **diff ของคอมมิตที่เป็นการแก้เท่านั้น** แล้วตอบสามคำถามต่อไฟล์:

1. **บั๊กที่เกิดที่นี่เป็นชนิดเดียวกันซ้ำๆ หรือคนละเรื่อง** — ซ้ำชนิดเดียวกัน = มีข้อบกพร่องเชิงโครงสร้าง แก้ที่โครงสร้างจบทีเดียว
2. **การแก้แต่ละครั้งแก้ที่ต้นเหตุหรือแก้ที่อาการ** — ถ้าเห็น `try/catch` เพิ่มขึ้นเรื่อยๆ, `ISNULL` เพิ่มขึ้นเรื่อยๆ, เงื่อนไขพิเศษเพิ่มขึ้นเรื่อยๆ นั่นคือแก้อาการ (AI-12) และแปลว่ายังพังอีกแน่
3. **ตอนแก้ ต้องไปแก้ที่อื่นด้วยไหม** — ถ้าใช่ ที่อื่นนั้นคือ A/B ของ logic เดียวกัน ให้จดเป็นผู้สมัคร SSOT ทันที

แมปทุกอย่างที่พบกลับเป็น ID จาก `HELL-CATALOG.md` ห้ามตั้งชื่อปัญหาเองถ้ามี ID อยู่แล้ว ถ้าเจอนรกที่แคตตาล็อกไม่มี ให้เสนอเป็นข้อใหม่พร้อมหลักฐาน

**ถ้า SP ส่วนใหญ่ไม่อยู่ใน git** (สัญญาณ: ไฟล์ `.sql` น้อยผิดปกติเทียบกับขนาดระบบ) ให้หยุดแล้วบอกผู้ใช้ว่าประวัติฝั่งฐานข้อมูลขาดหายไป — นั่นคือ SQL-24 และเป็น P1 ในตัวมันเอง จากนั้นเสนอให้รัน `detect-sqlserver.sql` เพื่อทดแทนด้วยภาพปัจจุบัน

## เฟส 4 — สังเคราะห์เป็นธีม ไม่ใช่รายการไฟล์

รวมสิ่งที่พบเป็น **นรกซ้ำซาก 5-10 ธีม** แต่ละธีมต้องมีครบ:

```
ธีม: <ชื่อที่คนในทีมพูดแล้วเข้าใจตรงกัน>
  nohell ID:      SQL-02, SSOT-01
  เกิดกี่ครั้ง:    14 ครั้ง ใน 8 เดือน
  ครั้งล่าสุด:     2026-08-11
  หลักฐาน:        a1b2c3d, e4f5g6h, ... (อย่างน้อย 3 คอมมิต)
  ต้นทุนที่เห็น:   คอมมิตแก้ 14 ครั้ง, revert 2 ครั้ง, แก้นอกเวลา 5 ครั้ง
  ต้นเหตุ:        <ประโยคเดียว>
  ถ้าไม่แก้:      <จะเกิดอีกกี่ครั้งในอีก 6 เดือน อ้างอิงจากอัตราที่ผ่านมา>
  ทางออกที่เล็กที่สุดที่ได้ผล: <ทำได้ใน PR เดียว>
```

เรียงตาม **จำนวนครั้ง × ความใหม่** ไม่ใช่ตามความน่าเกลียดของโค้ด

## เฟส 5 — ส่งของ

เขียนไฟล์เหล่านี้ (ไฟล์เท่านั้น ห้ามตอบยาวในแชต):

1. **`docs/nohell/archaeology.md`** — รายงานหลัก เรียงลำดับแล้ว เปิดด้วยตาราง 10 บรรทัด: ธีม | ครั้ง | ครั้งล่าสุด | nohell ID | ทางออกที่เล็กที่สุด
2. **`CONSOLIDATIONS.yaml`** — เติมผู้สมัครที่เจอจาก co-change และจากข้อ 3 ของเฟส 3 ตั้งสถานะ `C0` ทั้งหมด และ **ห้ามเดา** ว่า A ≡ B ปล่อยช่อง `equivalence_evidence` ว่างไว้ให้คนตัดสิน
3. **`docs/nohell/debt-ledger.md`** — แผลเป็นจาก `scars.txt` พร้อมอายุและคอมมิตที่ใส่ไว้
4. **`docs/nohell/baseline.json`** — ค่าตั้งต้นของ fitness function (จำนวน SP, บรรทัดรวม, จำนวน NOLOCK, ไฟล์ที่ยาวที่สุด, จำนวนวง C ที่เปิดอยู่) เพื่อใช้เป็นเส้นที่ห้ามแย่ลง

ปิดท้ายรายงานด้วยสามหัวข้อนี้ ไม่เกินหน้าเดียว:

- **สามอย่างที่แก้แล้วคุ้มที่สุด** พร้อมเหตุผลเชิงตัวเลข
- **สิ่งที่คุณจำได้ แต่ข้อมูลไม่สนับสนุน** — เทียบกับ 5 ข้อที่ผู้ใช้ตอบไว้ตอนต้น
- **สิ่งที่ข้อมูลบอก แต่คุณไม่ได้พูดถึง** — ส่วนนี้มักมีค่าที่สุด
