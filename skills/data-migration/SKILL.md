# data-migration — ย้ายข้อมูลโดยที่ทุกขั้นถอยกลับได้

โค้ดถอยได้ด้วย `git revert` **ข้อมูลถอยไม่ได้** ทุกขั้นในไฟล์นี้จึงออกแบบให้ *ระบบเก่ายังทำงานได้*
ตลอดทาง ไม่ใช่ให้ *migration สำเร็จเร็ว*

`archaeology` ตอบว่า "ตอนนี้จริง ๆ มันเป็นยังไง" — ไฟล์นี้ตอบว่า "จะเปลี่ยนมันโดยไม่พังยังไง"

---

## กฎเหล็ก: ห้ามมีขั้นตอนที่ระบบเก่าใช้งานไม่ได้

ถ้าแผนมีช่วงเวลาที่ "โค้ดเก่ารันไม่ได้แล้ว แต่โค้ดใหม่ยังไม่ขึ้น" นั่นคือ downtime ที่ซ่อนอยู่
และเป็นจุดที่ rollback แพงที่สุด — `SHIP-07` (เปลี่ยน schema กับโค้ดคนละรอบ) เกิดตรงนี้

**เกณฑ์ตรวจ:** หยุดที่ขั้นไหนก็ได้แล้วระบบยังเดินอยู่ ถ้าตอบไม่ได้ แผนยังไม่พร้อม

---

## ขั้นตอน — หกขั้น หยุดได้ทุกขั้น

### 1. Expand — เพิ่มของใหม่ ห้ามลบของเก่า

เพิ่มคอลัมน์/ตาราง/index ใหม่ **nullable หรือมี default** เท่านั้น โค้ดเก่าที่ไม่รู้จักของใหม่
ต้องยังเขียนได้เหมือนเดิม

- `ALTER TABLE ... ADD` ที่ไม่มี default บนตารางใหญ่ล็อกตารางทั้งใบ — บน SQL Server ให้เพิ่ม
  แบบ nullable ก่อนแล้ว backfill ทีหลัง ส่วน index ให้สร้างด้วย `ONLINE = ON`
- บน MySQL ตารางใหญ่ใช้ `pt-online-schema-change` (trigger + shadow table, **`--resume` ได้**)
  หรือ `gh-ost` (อ่าน binlog ไม่ใช้ trigger เบากว่าตอนโหลดสูง แต่ **ตายแล้วเริ่มใหม่หมด**
  และ **ไม่รองรับ foreign key**) เลือกตามว่ามี FK ไหมและยอมเริ่มใหม่ได้ไหม
- ทุกสคริปต์ต้อง **รันซ้ำได้** (`SHIP-05`) — ครอบด้วย `IF COL_LENGTH(...) IS NULL` หรือเทียบเท่า
  เพราะ migration ที่รันครึ่งทางแล้วค้าง จะต้องถูกรันซ้ำแน่นอน

### 2. Dual-write — เขียนสองที่ อ่านที่เก่า

โค้ดใหม่เขียนทั้งของเก่าและของใหม่ **แต่ยังอ่านของเก่า** ช่วงนี้คือช่วงที่ถอยได้ถูกที่สุด:
ปิด flag แล้วกลับไปสภาพเดิมทันที

⚠️ **นี่คือขั้นที่อันตรายที่สุด ไม่ใช่ขั้น cutover** เพราะมีข้อมูลจริงสองที่พร้อมกัน
ตรงกับ `SSOT-01` สถานะ C2 — ต้องมีบรรทัดใน `CONSOLIDATIONS.yaml` พร้อมเจ้าของและวันลบ

- เขียนสองที่ใน transaction เดียว ถ้าแยก transaction ต้องตอบได้ว่าถ้าอันที่สองล้ม จะเกิดอะไร
- ห้าม "เขียนของใหม่แบบ best-effort แล้วกลืน error" — นั่นทำให้ของใหม่ขาดหายแบบเงียบ
  แล้วขั้นที่ 3 จะรายงานว่าตรงกันทั้งที่ไม่ตรง

### 3. Backfill — เป็นก้อน มีจุด resume มีเพดานผลกระทบ

- **แบ่งก้อนตามคีย์ ไม่ใช่ตาม `OFFSET`** — `OFFSET` บนตารางใหญ่สแกนซ้ำทุกรอบ
- เก็บ "ทำถึงไหนแล้ว" ลงตาราง ไม่ใช่ในตัวแปรของสคริปต์ — งานที่รัน 6 ชั่วโมงจะถูกฆ่ากลางทาง
- แต่ละก้อนต้อง **idempotent** (`TXN-06`) รันทับก้อนเดิมแล้วผลต้องเหมือนเดิม
- มีเพดาน: หยุดเองเมื่อ lock wait หรือ replication lag เกินค่าที่ตั้งไว้ — backfill ที่ทำให้
  ระบบหลักช้า จะถูกสั่งหยุดกลางทางโดยคนที่ไม่รู้ว่ามันหยุดที่ไหน

### 4. Shadow-read — เทียบผลก่อนเชื่อ ไม่ใช่เชื่อแล้วค่อยเทียบ

อ่านทั้งสองทางในคำขอเดียวกัน **คืนค่าของเก่าให้ผู้ใช้** แล้วบันทึกว่าต่างกันกี่ครั้ง ต่างที่ไหน

ตรวจสามชั้น เพราะแต่ละชั้นจับของที่ชั้นอื่นมองไม่เห็น

| ชั้น | จับอะไรได้ | จับอะไรไม่ได้ |
|---|---|---|
| `COUNT(*)` เท่ากัน | แถวหาย/เกิน | ค่าในแถวผิด |
| checksum ต่อคอลัมน์ | ค่าเพี้ยน ชนิดข้อมูลเปลี่ยน | แถวที่ *ควรมี* แต่ไม่มีทั้งสองฝั่ง |
| เทียบผลของคิวรีที่ผู้ใช้ใช้จริง | ความต่างที่เกิดจาก join/filter ไม่ใช่จากข้อมูล | กรณีที่ไม่มีใครยิงในช่วงเทียบ |

- เทียบบน **ปริมาณและช่วงข้อมูลของ production** ไม่ใช่บน dev (`MEAS-03`) — dev พันแถว
  prod ยี่สิบล้าน แล้วสรุปว่าตรงกัน คือยังไม่ได้เทียบ
- ต่างกัน 0.1% ไม่ใช่ "ผ่าน" ต้องอธิบายได้ทุกเคสว่าต่างเพราะอะไร ไม่งั้นคือยังไม่รู้สาเหตุ

### 5. Cutover — สลับทางอ่าน ทีละส่วน ไม่ใช่ทั้งระบบ

- สลับด้วย flag ที่ **ปิดกลับได้ในนาทีเดียว** ไม่ใช่ด้วยการ deploy
- สลับทีละกลุ่มผู้ใช้/ทีละหน้าจอ แล้วดูตัวเลขก่อนขยาย
- ต้องตอบได้ก่อนสลับว่า **ถ้าปิด flag กลับ ข้อมูลที่เขียนไปช่วงนั้นยังอยู่ไหม** —
  ถ้า dual-write ในขั้นที่ 2 ยังทำงาน คำตอบคือ "อยู่" ถ้าปิดไปแล้ว คำตอบคือ "หาย"

### 6. Contract — ปิดทางเขียนเก่า แล้วลบ

ตามลำดับนี้เท่านั้น: หยุด dual-write → เฝ้าดูว่าไม่มีใครอ่านของเก่าแล้วจริง → ตัดสิทธิ์เขียน
ของเก่า → **แล้วค่อยลบ**

- ตัวส่งมอบของงานนี้คือ **ของเก่าหายไป** ไม่ใช่ของใหม่โผล่มา (`SSOT-01`)
- ถ้าลบตารางเก่าไม่ได้เพราะยังมีคนอ่าน แปลว่าขั้นที่ 5 ยังไม่จบ ไม่ใช่ว่าขั้นที่ 6 ทำไม่ได้
- **รวม logic แล้วแต่ข้อมูลยังอยู่สองที่ = ยังไม่จบ** (`SSOT-13`) — เป็นกรณีที่คนคิดว่าจบแล้ว
  บ่อยที่สุด และเป็นที่มาของ `DATA-12` (ข้อมูลหลักเรื่องเดียวกันอยู่หลายที่)

## เกณฑ์ยกเลิกกลางทาง — เขียนก่อนเริ่ม ไม่ใช่ตอนเจอปัญหา

ต้องตกลงไว้ล่วงหน้าว่าเจออะไรถึงจะ **ถอย** ไม่ใช่ **ดันต่อ**

| เจอ | ทำ |
|---|---|
| shadow-read ต่างกันโดยอธิบายไม่ได้ | ถอยไปขั้นที่ 4 ห้าม cutover |
| backfill ทำให้ระบบหลักช้าเกินเพดาน | หยุด แล้วลดขนาดก้อน ไม่ใช่ปิดการเฝ้า |
| เลยวันลบที่เขียนใน `CONSOLIDATIONS.yaml` | เลือกอย่างใดอย่างหนึ่ง — ลบให้จบ หรือยกเลิกแล้วลบของใหม่ทิ้ง **ห้ามปล่อยค้าง** |
| ไม่มีใครตอบได้ว่าคอลัมน์เก่าคอลัมน์ใหม่ต่างกันตรงไหน | หยุด กลับไปทำ `archaeology` ก่อน |

การถอยที่แพงที่สุดคือการถอยหลังลบของเก่าแล้ว — จึงเป็นเหตุผลที่ขั้นที่ 6 อยู่ท้ายสุด
และมี `SHIP-06` (migration ที่ไม่มีทางกลับ) เฝ้าอยู่

## ผลลัพธ์ที่ต้องส่ง

1. **แผนหกขั้น** ระบุว่าแต่ละขั้นหยุดได้และหยุดแล้วระบบยังเดิน
2. **บรรทัดใน `CONSOLIDATIONS.yaml`** ตั้งแต่เข้าขั้นที่ 2 — ระบุของเก่า ของใหม่ เจ้าของ วันลบ
3. **ตัวเลข shadow-read** count/checksum/คิวรีจริง บนปริมาณ production พร้อมคำอธิบายทุกความต่าง
4. **สคริปต์ที่รันซ้ำได้** ทั้ง forward และ rollback แยกไฟล์
5. **บัญชีผู้เรียกของเก่า** ที่นับได้ว่าเหลือศูนย์ก่อนลบ (`SSOT-04`)
