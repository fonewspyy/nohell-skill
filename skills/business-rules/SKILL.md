# business-rules — ความจริงเรื่องนี้ ใครเป็นเจ้าของ

โค้ดผิด แก้แล้วจบ **กฎธุรกิจที่เข้าใจผิด กลายเป็นข้อมูลผิดที่ค้างในฐานข้อมูลตลอดไป** และมักถูกพบตอนปิดงบ ไม่ใช่ตอน deploy

หมวดนี้จึงมาก่อนเรื่องโครงสร้างโค้ดเสมอ

---

## 1. ทุกกฎต้องมีเจ้าของหนึ่งเดียว

ก่อนแก้กฎใดๆ ตอบให้ได้ว่า **นิยามของกฎนี้อยู่ที่ไหน** — ไม่ใช่ "อยู่ที่ไหนบ้าง"

```
fact:      "ราคาขายสุทธิของรายการสินค้า"
owner:     dbo.Sales_CalculatePrice          ← ที่เดียวที่มีสิทธิ์ตัดสิน
readers:   หน้าจอขาย, ใบเสนอราคา, รายงานยอดขาย, API ให้ Flutter
writers:   SP ข้างต้นเท่านั้น
evidence:  DB — ตรวจ call graph แล้วเมื่อ 2026-08-22
```

ถ้ายังไม่มีเจ้าของ = ยังไม่ถึงเวลาแก้ ให้ทำ [archaeology](../archaeology/SKILL.md) ก่อน แล้วเปิดวง C ใน `CONSOLIDATIONS.yaml`

## 2. Effective date — กฎมีอายุ ไม่ใช่มีแค่ "ตอนนี้" (TIME-15)

**อาการ:** พิมพ์ใบกำกับของเดือนที่แล้วซ้ำ แล้วตัวเลขไม่เท่าเดิม เพราะโค้ดไปหยิบแถวที่ `IsActive = 1` ณ วันนี้

**กฎ:** ทุกอย่างที่เป็น "ค่าที่เปลี่ยนได้ตามเวลา" ต้องเก็บเป็นช่วงเวลา และเลือกด้วย **วันที่ของรายการ** ไม่ใช่ `GETDATE()`

สิ่งที่เข้าข่ายเกือบเสมอ: ราคา ต้นทุน อัตราภาษี ส่วนลด เงื่อนไขเครดิต ค่าขนส่ง สิทธิ์ผู้ใช้ โครงสร้างค่าคอมมิชชัน สูตรคำนวณ mapping รหัสกับระบบนอก

```sql
-- ผิด: ได้ค่าปัจจุบันเสมอ ทำให้เอกสารเก่าเปลี่ยนตัวเลขเมื่อคำนวณใหม่
SELECT rate FROM TaxRate WHERE IsActive = 1;

-- ถูก: ค่าที่มีผล ณ วันที่ของเอกสาร
SELECT rate FROM TaxRate
WHERE valid_from <= @DocDate AND (valid_to IS NULL OR @DocDate < valid_to);
```

**คำถามที่ต้องถามทุกครั้งที่เจอตาราง lookup:** ถ้าพรุ่งนี้ค่านี้เปลี่ยน เอกสารของเมื่อวานควรเปลี่ยนตามไหม — ถ้าคำตอบคือไม่ แปลว่าตารางนี้ต้องมีช่วงเวลา

**คำถามคู่กัน:** ที่ต้องใช้คือ *วันที่ของเอกสาร* หรือ *วันที่เกิดรายการ* หรือ *วันที่มีผลทางบัญชี* สามอันนี้ไม่เหมือนกัน และมักเป็นต้นเหตุที่รายงานสองใบไม่ตรงกัน

**สแนปช็อตกับการอ้างอิงสด:** ถ้าค่าที่ใช้แล้วต้องคงที่ตลอดไป (เช่นราคาที่ตกลงกับลูกค้า) ให้ **เก็บค่าที่ใช้จริงลงในเอกสาร** ไม่ใช่ join กลับไปที่ master ทุกครั้ง — แต่ต้องเก็บทั้งค่าและ id ของกฎที่ใช้ เพื่อให้ตามที่มาได้

## 3. ฝั่งอ่านกับฝั่งเขียนต้องเป็นกฎเดียวกัน (ARCH-21)

**อาการสองแบบที่มาจากสาเหตุเดียว:** ปุ่มกดได้แล้วขึ้น error / ปุ่มเทาทั้งที่ควรกดได้

เกิดจาก `CanConfirm()` ที่ฝั่งอ่าน กับเงื่อนไขจริงในฝั่ง command ถูกเขียนคนละที่ แล้วเดินจากกันทีละนิด

```
ตัวตัดสินหนึ่งเดียว:  CanConfirmShipment(doc) → { allowed, reason }
   ฝั่งเขียน:        command เรียกก่อนทำงานเสมอ ปฏิเสธด้วย reason เดียวกัน
   ฝั่งอ่าน:         ปุ่ม/เมนู เรียกตัวเดียวกัน เอา reason ไปแสดงเป็น tooltip
   ฝั่ง query:       รายการ "รอยืนยัน" ต้อง derive จากเงื่อนไขชุดเดียวกัน
                     ห้ามเขียน WHERE ซ้ำในรายงาน
```

**เกณฑ์ตรวจ:** ถ้าเปลี่ยนเงื่อนไขที่เดียวแล้วปุ่ม รายการ และ command เปลี่ยนตามพร้อมกัน = ถูก ถ้าต้องไปแก้สามที่ = ยังไม่ผ่าน และนี่คือผู้สมัคร SSOT ทันที

ข้อนี้ใช้กับ "จำนวนที่แสดง" ด้วย: ตัวเลขคงเหลือบนหน้าจอ กับตัวเลขที่ระบบใช้ตัดสินว่าเบิกได้ ต้องมาจากนิยามเดียวกัน

## 4. Workflow ต้องเป็นสถานะที่ประกาศไว้ ไม่ใช่ if กระจาย

เขียนตารางสถานะออกมาก่อนเขียนโค้ด:

| จาก | เหตุการณ์ | ไป | ใครทำได้ | ผลข้างเคียง | ย้อนได้ไหม |
|---|---|---|---|---|---|
| draft | confirm | confirmed | หัวหน้าคลัง | จองสต็อก | ได้ ภายในวันเดียวกัน |
| confirmed | ship | shipped | พนักงานคลัง | ตัดสต็อกจริง | ไม่ได้ ต้องออกเอกสารกลับรายการ |

คำถามที่ต้องถามคนที่รู้กระบวนการ และมักไม่มีใครเขียนไว้:
- ยกเลิกหลังจากสถานะนี้ได้ไหม แล้วสต็อก/บัญชีที่เกิดไปแล้วทำอย่างไร
- ข้ามขั้นได้ไหม ใครข้ามได้
- ถ้าเอกสารค้างอยู่สถานะกลางนานเกินไป ระบบควรทำอะไร
- สองคนทำพร้อมกันคนละขั้น ใครชนะ

**ห้ามให้สถานะเป็นแค่ตัวเลขในคอลัมน์เดียวที่ปนความหมายหลายมิติ** (DATA-14) และห้ามให้การเปลี่ยนสถานะเกิดในหลาย SP โดยไม่มีตัวคุมกลาง

## 5. เงิน การปัดเศษ และการคำนวณซ้ำ

- ปัดเศษเป็น **นิยามทางธุรกิจ** ไม่ใช่รายละเอียดทางเทคนิค ต้องรู้ว่าปัดที่ระดับบรรทัด หรือระดับเอกสาร และปัดกี่ตำแหน่ง — ปัดคนละจุดได้ผลต่างกัน และผลต่างนี้จะไปโผล่ที่รายงานสรุป
- การคำนวณต้อง **ทำซ้ำแล้วได้เท่าเดิม** จากข้อมูลเดียวกัน ถ้าคำนวณใหม่แล้วต่าง แปลว่ามีอะไรบางอย่างอ่านค่าปัจจุบันอยู่ (กลับไปข้อ 2)
- ยอดรวมที่เก็บไว้ กับยอดที่คำนวณจากรายการ ต้องมีตัวเทียบเป็นรอบ (reconciliation) ไม่ใช่หวังว่าจะตรง
- เงินที่คำนวณแล้วต้องบันทึกว่า **ใช้กฎเวอร์ชันไหน** เพื่อให้ตอบคำถาม "ทำไมใบนี้คิด 7% ใบนั้นคิด 10%" ได้โดยไม่ต้องเดา

## 6. Exception ทางธุรกิจ ไม่ใช่ error ของระบบ

"เครดิตเกินวงเงิน" ไม่ใช่บั๊ก แต่เป็นผลลัพธ์ที่ธุรกิจคาดไว้แล้ว

- แยกให้ชัดระหว่าง *สิ่งที่ระบบปฏิเสธเพราะกฎ* กับ *สิ่งที่ระบบพัง* — คนละ HTTP code คนละช่องทาง alert (ERR-06, ERR-14)
- ทุกการปฏิเสธต้องมี **รหัสคงที่ + เหตุผลที่ผู้ใช้ทำอะไรต่อได้** ไม่ใช่ "บันทึกไม่สำเร็จ"
- ทางออกพิเศษ (ใครอนุมัติข้ามกฎได้) เป็นส่วนหนึ่งของกฎ ต้องออกแบบและบันทึก audit ไม่ใช่ปล่อยให้แก้ในฐานข้อมูลตรงๆ

## 7. กฎเปลี่ยน = เทสต้องเปลี่ยน (TEST-16)

เทสที่เขียนไว้ตอนกฎเก่า จะยังเขียวอยู่หลังธุรกิจกลับด้านไปแล้ว แล้วมันจะทำสองอย่างที่แย่พร้อมกัน: ขวางไม่ให้แก้ให้ถูก และเป็นหลักฐานปลอมว่าระบบยังถูกต้อง

วิธีกัน:

1. ผูกเทสกับ rule id — `test('BR-014 คิดภาษีตามอัตรา ณ วันที่เอกสาร')` เพื่อให้ค้นได้ว่ากฎข้อนี้มีเทสตัวไหนเฝ้าอยู่
2. PR ที่เปลี่ยนพฤติกรรมธุรกิจ แต่ไม่มีไฟล์เทสถูกแตะเลย = ต้องอธิบายเหตุผล
3. เก็บกฎเป็นตารางการตัดสินใจ (input → expected) แล้ว generate เทสจากตาราง เวลากฎเปลี่ยนจะแก้ที่เดียว
4. เทสที่ยืนยันพฤติกรรมเก่าเพื่อการรีแฟกเตอร์ (characterization) ต้องติดป้ายแยกจากเทสที่ยืนยันว่า "ธุรกิจต้องการแบบนี้" — สองอย่างนี้อายุไม่เท่ากัน อันแรกทิ้งได้เมื่อย้ายเสร็จ อันหลังห้ามทิ้ง

- [ ] เจ้าของกฎมีที่เดียว และผู้เรียกทั้งหมดใช้ที่นั้น
- [ ] ถ้าเป็นค่าที่เปลี่ยนตามเวลา มีช่วงเวลาแล้ว และเลือกด้วยวันที่ของรายการ
- [ ] ฝั่งอ่าน (ปุ่ม/รายการ/รายงาน) ใช้เงื่อนไขเดียวกับฝั่งเขียน
